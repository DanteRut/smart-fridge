[Контракт] Какое изменение контракта всегда безопасно?	Аддитивное и необязательное: новое поле/эндпоинт/rpc без ужесточений — старые клиенты его не видят и не шлют. Ломающее: удаление, переименование, смена типа, ужесточение (required, !, валидация)	contract
[Контракт] Универсальный цикл эволюции контракта?	Добавить рядом со старым (@deprecated / алиас / optional / reserved) → окно с метрикой использования → удалить. Анти-паттерн: менять разом	contract
[REST] Убрали поле из JSON-ответа: как ломается клиент?	Тихо: undefined без ошибок и логов. Правильно: перестать заполнять → NON_NULL сам скроет → объявить окно → удалить из DTO	contract rest
[GraphQL] Убрали или переименовали поле схемы: как ломается?	Громко: Cannot query field у всех запрашивающих — валидация схемы до сервера. Цикл: новое поле + @deprecated(reason) на старое (видно в интроспекции) → клиенты переезжают → удалить	contract graphql
[Protobuf] Удаляем поле proto — что обязательно сделать?	reserved номер И имя: reserved 12; reserved 'name'; — компилятор запретит переиспользование; в старых байтах поле станет unknown и не помешает парсингу	contract proto
[REST] Добавили @NotBlank на существующее поле Request: что случится?	Громко: живые клиенты получают 400 по полю, которое не шлют. Required и ужесточение валидации — только через окно; ослабить валидацию — безопасно	contract rest validation
[GraphQL] Добавили required аргумент (!) к существующему полю — что сломается?	Все старые запросы не проходят валидацию по схеме. Required вводят только в новые поля; на живых: optional → окно → !	contract graphql
[Protobuf] Смена типа int32 → int64 → bool при том же номере: что происходит?	Тихий мусор: wire type один (0 = varint), парсинг успешен, значения искажены (усечение, переинтерпретация). Хуже громкого падения — диагноза нет	contract proto
[Контракт] Профиль поломок: кто тихий, кто громкий по технологиям?	REST — тихий чемпион (JSON игнорит лишнее, отсутствующее = null). GraphQL — громкий и ранний (строгая схема, явные поля). proto — зависит от wire: тот же класс = тихий мусор, другой класс = громкое падение парсера; номера — единственная правда	contract
[REST] Новый вариант enum в JSON-ответе: чем опасен?	Типизированные клиенты падают на десериализации (InvalidFormatException: unknown constant). Клиентов учат: unknown → default. Удаление варианта ломает так же	contract rest
[GraphQL] Nullable → Non-Null (!) на живом поле: безопасно ли?	Ужесточение обещания: резолвер вернёт null — ошибка уедет в errors и может обнулить весь data. Менять только когда значение реально всегда есть. Обратное (! убрать) ломает типы кодген-клиентов	contract graphql
[Контракт] Инструменты проверки совместимости по технологиям?	REST: javac-потребители jar + контрактные тесты + OpenAPI-diff. GraphQL: schema-diff (graphql-inspector) + кодген = ошибка компиляции. proto: reserved + buf breaking в CI	contract
