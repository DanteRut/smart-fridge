Перечислите 7 принципов REST	<b>Client-Server, Stateless, Cacheable, Uniform Interface, Layered System, Code on Demand, Null Style</b><br>(последний — необязательный, «стиль по умолчанию»)	rest
Что значит Stateless в REST?	Сервер <b>не хранит состояние сессии</b>: каждый запрос самодостаточен (токен едет в запросе). Следствие — горизонтальное масштабирование без sticky-сессий	rest
Что значит Uniform Interface?	Единый контракт независимо от клиента: <b>ресурсы</b> (URL), <b>методы-глаголы</b> (HTTP), <b>представления</b> (JSON), <b>HATEOAS</b> (ссылки)	rest
Какие методы идемпотентны?	<b>GET, PUT, DELETE, HEAD — да</b>; POST — нет; PATCH — <b>не гарантирована</b> (зависит от реализации)	rest
Что такое идемпотентность?	Повторный вызов даёт тот же результат, что и однократный: <b>f(f(s)) = f(s)</b>. Важно для безопасных ретраев	rest
Уровни зрелости Ричардсона (RMM)?	<b>L0</b> один URL, всё POST, ошибки в теле → <b>L1</b> отдельные URL ресурсов → <b>L2</b> + методы и HTTP-коды → <b>L3</b> + HATEOAS (_links)	rest rmm
Что именно даёт L2 (методы + коды)?	Заработало: <b>кэширование GET</b>, мониторинг по кодам, безопасные ретраи идемпотентных, понимание посредников	rest rmm
Что добавляет L3?	<b>_links</b>: клиент находит действия из ответа; сервер свободно двигает URL (клиент не хардкодит)	rest rmm hateoas
401 vs 403?	<b>401</b> — «кто ты?», не аутентифицирован (+ заголовок WWW-Authenticate, можно повторить после логина). <b>403</b> — «ты известен, но прав нет», повторять бессмысленно	rest codes
400 vs 422?	<b>400</b> — сломан синтаксис/структура (кривой JSON, пустое обязательное). <b>422</b> — синтаксис ок, но предметные правила не прошли (контрольная сумма ISBN)	rest codes
500 vs 502 vs 503?	<b>500</b> — упал сам сервис. <b>502</b> — посредник получил плохой/никакой ответ от нижестоящего. <b>503</b> — временно недоступен (+ Retry-After)	rest codes
Кто ставит 502?	<b>Посредник</b> (шлюз, балансировщик) — сам сервис себе 502 не отдаёт	rest codes
Поля RFC 7807 (Problem Details)?	<b>type</b> (URI типа), <b>title</b>, <b>status</b>, <b>detail</b>, <b>instance</b> (URI запроса); Content-Type: application/problem+json	rest errors
Зачем в RFC 7807 status дублируется в теле?	Статус могут переписать посредники (шлюз/балансировщик) — <b>тело доезжает как есть</b>; клиент решает по телу	rest errors
Семантика RFC 7386 (Merge Patch)?	<b>null = очистить поле</b>; поле отсутствует = не менять. Договор на уровне протокола	rest patch
Семантика RFC 6902 (JSON Patch)?	Тело — <b>массив операций</b> [{op: add/remove/replace, path, value}]; Content-Type: application/json-patch+json. Шлём не данные, а команды правок	rest patch
Три состояния значения поля в JSON?	1) есть значение 2) <b>null</b> 3) <b>поле отсутствует</b>. В Java-объекте состояний только два (значение/null) — отсюда вся боль PATCH	rest patch
Семантика PUT?	<b>Полное замещение состояния</b>: не прислал поле — оно обнуляется. Поэтому идемпотентен	rest patch
Договорённость нашего PatchProductRequest?	<b>null = «не трогать»</b>. Следствие: обнулить поле через PATCH нельзя (осознанный компромисс)	rest patch project
Три способа «стереть поле» через PATCH?	1) RFC 7386 Merge (null=очистить) 2) RFC 6902 (op:remove) 3) своё <b>reset:[]</b> или JsonNullable	rest patch
Что такое JsonNullable?	Обёртка с <b>тремя состояниями</b> ABSENT/NULL/VALUE (org.openapitools.jackson.nullable); absent сериализуется «поля нет». Механизм реализации 7386 в Java	rest patch
Цепочка Bean Validation?	Аннотации на DTO (@NotBlank...) → <b>@Valid</b> на параметре → проверка <b>до входа в контроллер</b> → MethodArgumentNotValidException → @ControllerAdvice → <b>400 + fieldErrors</b>	validation
Поля FieldError у нас?	<b>field, rejectedValue, message</b>. Чего не хватает: машиночитаемого <b>code</b> (REQUIRED/ISBN_INVALID) — готовый ответ «как улучшил бы»	validation errors
Кто сломается при переименовании поля isbn→productIdentifier?	<b>Сервер — нет, клиент — да и молча</b>: маппит fieldErrors[].field на инпут формы строковым совпадением	validation
Роль @ControllerAdvice в одном предложении?	Единая точка превращения исключений в HTTP-ответы: 404/400/500 одним форматом (у нас GlobalExceptionHandler, BASE .../problems/)	errors project
HATEOAS одним предложением?	Представление ресурса содержит <b>ссылки на возможные действия</b>; клиент ходит по href, зная наизусть только один URL	rmm hateoas
Что такое rel?	Имя отношения ссылки (self, items, update, delete) — <b>часть публичного контракта</b>: клиент различает действия по rel, идёт по href	hateoas
Как работает linkTo(methodOn(ProductController.class).get(id))?	<b>Метод НЕ вызывается</b>: Spring HATEOAS строит прокси, читает аннотации маппинга (@GetMapping) и собирает URL. Переименование маппинга обновляет ссылки автоматически	hateoas
4 пункта цены HATEOAS?	1) ссылки и rel — публичный контракт 2) <b>матрица состояние×действие</b> (тестировать) 3) ссылки абсолютны — X-Forwarded-Host/Proto 4) <b>забыл ссылку = действия не существует</b>	hateoas
Конфликт HATEOAS с UI?	UI хочет показывать <b>задизейбленную кнопку с причиной</b>, а «нет ссылки» = действие не существует. Решения: allowed/reason в теле, реестр rel, BFF (canX-флаги)	hateoas
Зачем контракт в отдельном Maven-модуле?	Один источник правды (DTO+эндпоинты+ошибки); <b>javac ловит ломающие изменения</b> у потребителей; OpenAPI из тех же аннотаций. Цена: тащит Spring-зависимости	contract
Три операции GraphQL и порядок исполнения?	<b>Query — параллельно</b>; <b>Mutation — верхнеуровневые поля строго последовательно</b> (порядок в тексте); <b>Subscription — пуш</b> по WS/SSE	graphql
Почему mutation исполняется последовательно?	<b>Целостность</b>: нельзя обновить то, что create ещё не создал; порядок задан порядком полей в тексте запроса	graphql
3 причины variables (не хардкодить значения)?	1) текст запроса — константа → <b>кэш parse/validate</b> (аналог prepared statement) 2) <b>persisted queries/APQ</b> — шлём только хэш 3) типобезопасность: не тот тип отбракован до исполнения (+ нет инъекций)	graphql
Что такое APQ?	Automatic Persisted Queries: первый запрос — текст+hash, дальше — <b>только hash+variables</b>: экономия трафика и фазы парсинга	graphql
Depth vs Complexity?	<b>Depth — вертикаль</b> запроса (слеп к ширине и алиасам). <b>Complexity — сумма весов полей</b>, пагинация умножает цену ветки; ловит то, что depth пропустил	graphql security
4 способа уложить сервер при depth=5?	1) first:100000 (ширина) 2) алиасы a:b:c:... ×200 3) одно поле с дорогим резолвером 4) introspection для разведки схемы	graphql security
Формула N+1 в нашем проекте?	<b>7 = 1 (список продуктов) + 1 (категории) + 4 (items для каждого)</b>; на 50 продуктах — 51 вызов (ProductItemsDataFetcher)	graphql project
Как работает DataLoader?	Копит ключи всех запросивших полей за «тик» → <b>один батч WHERE product_id IN (...)</b> → карта id→значение + кэш на время запроса. 1+N → 1+1	graphql
Формат ошибок GraphQL?	<b>Всегда HTTP 200</b>, ошибки в errors[] (message, path, extensions). В DGS — TypedGraphQLError/GraphQLExceptionHandler; не путать с @ControllerAdvice	graphql errors
input vs type в схеме?	Аргументы мутаций — только <b>input</b> (PatchBookInput); типы-модели в аргументах использовать нельзя. В input absent ≠ null — обнуление штатно	graphql schema
Что значит [Book!]!?	Список <b>не null И элементы не null</b>; ! читается «изнутри наружу»	graphql schema
Лимиты GraphQL в проекте?	<b>MaxQueryDepth(20), MaxQueryComplexity(200)</b>, вес поля по умолчанию 1 (дорогим полям вес повышаем вручную)	graphql security project
Ключевые аннотации DGS?	@DgsComponent, @DgsQuery, @DgsMutation, @DgsSubscription, @DgsData(parentType, field), @InputArgument	graphql dgs
Почему HTTP-кэш не работает для GraphQL?	Всё уходит <b>POST на один URL /graphql</b> — кэшировать нечего. Лечение: APQ + CDN; кэш per-field на клиенте (Apollo)	graphql
Формат провода protobuf?	Пары <b>(номер поля, wire type)</b>; имён полей в байтах нет. Поэтому переименование безопасно, ломают номера и wire type	grpc proto
Wire types protobuf?	<b>0</b> varint (int32/int64/bool/enum), <b>1</b> fixed 64-bit, <b>2</b> length-delimited (string/bytes/message/packed repeated), <b>5</b> fixed 32-bit	grpc proto
Старый клиент читает сообщение с новым полем?	Не знает номер → смотрит wire type → <b>пропускает блок целиком</b>, остальное парсит как раньше. Совместимо	grpc proto
Новый клиент читает старые данные?	Поля в байтах нет → <b>дефолт proto3</b>: 0 / "" / false / enum[0]. Различить «не задано» → <b>optional + hasField()</b>	grpc proto
Почему переименование поля в .proto безопасно?	<b>Имена по сети не ездят</b>, только номера. В JSON — наоборот: имена и есть контракт (отсюда хрупкость FieldError.field)	grpc proto
Что ломает совместимость proto (3 вещи)?	1) смена типа <b>с другим wire type</b> = падение парсера 2) смена в пределах того же wire (int32→int64→bool) = <b>тихий мусор</b> 3) <b>переиспользование номера</b> без reserved	grpc proto
Зачем reserved в proto?	Запрещает переиспользовать удалённые <b>номер и имя</b> — компилятор не даст; плюс buf breaking в CI. Протокол защищает структуру, не смысл	grpc proto
4 типа вызовов gRPC?	unary; <b>server streaming</b> (returns stream X); client streaming (принимает stream); <b>bidi</b> — stream с обеих сторон	grpc
Транспорт и ошибки gRPC?	<b>HTTP/2</b> + бинарный protobuf; мультиплексирование; коды ошибок: NOT_FOUND, INVALID_ARGUMENT, INTERNAL (вместо HTTP-статусов)	grpc
Поток сообщения AMQP?	producer → <b>exchange → binding → queue</b> → consumer. Producer не знает очередей — только exchange и routing key	rabbitmq
Типы exchange?	<b>direct</b> (точный ключ), <b>fanout</b> (копии всем привязанным очередям), <b>topic</b> (паттерны), headers	rabbitmq
Topic-паттерны: какие бинды поймают product.created?	<b>product.* ✓, product.# ✓, *.created ✓, # ✓</b>; *.updated ✗; item.created ✗. * = ровно одно слово, # = ноль и больше	rabbitmq
Поля EventEnvelope?	<b>metadata {eventId, occurredAt, source, routingKey}</b> + payload. eventId (UUID) — ключ дедупликации	events
Синтаксис sealed-иерархии событий?	<b>sealed interface ProductEvent permits ProductEvent.Created, ...</b>; наследники — record со своим payload: record Created(Long id, String name) implements ProductEvent {}	events sealed
Что даёт exhaustive switch?	Компилятор знает закрытый список permits и <b>требует покрыть все ветки без default</b>: забыл — ошибка компиляции (эволюция проверяется на сборке)	events sealed
Старый consumer встречает новый вариант события?	Без default — <b>MatchException</b> (громко, видно в мониторинге); с default — <b>тишина</b> (хуже). Правило: default → warn + метрика + DLQ	events sealed
enum vs sealed — мнемоника?	<b>enum — закрытый список ЗНАЧЕНИЙ при одном наборе полей; sealed — закрытый список ТИПОВ, у каждого свой payload</b>. Одинаковые данные → enum; разные → sealed	events sealed
Правило деплоя consumer/producer?	<b>Consumer'ов деплоить раньше producer'ов</b>: старый consumer + новое событие = беда; новый consumer + старое событие = ок (обратная совместимость)	events sealed
Три звена гарантированной доставки?	1) <b>publisher confirms</b> (брокер квитанцией подтвердил приём) 2) <b>durable exchange/queue + persistent message</b> (delivery mode 2, на диск) 3) <b>manual ack</b> (подтверждение после обработки)	events delivery
Риск auto-ack?	Брокер вычеркнул сообщение при отправке; consumer упал на полпути → «доставлено», работы нет → <b>тихая потеря</b>	events delivery
Что делает basicNack(requeue=false)?	Уводит сообщение в <b>DLQ</b>: очередь не блокируется, разбор руками; рост DLQ = алерт. Тихий сбой → громкий	events delivery
Почему exactly-once невозможен сквозь сеть?	Подтверждение может потеряться ПОСЛЕ применения операции → повтор неизбежен. Стандарт: <b>at-least-once + идемпотентность (дедуп по eventId)</b>	events delivery
Dual write: потеря vs фантом?	<b>Потеря</b> (данных нет, события нет) — тихая, для аудита опаснее. <b>Фантом</b> (событие есть, данных нет) — громкий. Для «денег наружу» наоборот: фантом хуже	events outbox
Шаги outbox-паттерна?	В <b>одной ACID-транзакции</b>: бизнес-данные + INSERT в outbox → отдельный релизер читает и публикует <b>с confirms</b> → помечает PUBLISHED. Плата: at-least-once → дедуп	events outbox
Почему afterCommit-публикация хуже outbox?	Смерть процесса <b>между commit и publish</b> = потеря навсегда; outbox лежит в БД и переживает любое падение	events outbox
Что стоит в аудите у нас и чего нет?	Exchange <b>smartfridge.events</b> (topic, durable), binding <b>"#"</b> (всё), авто-ack. НЕТ: confirms, manual ack, DLQ, дедупа — карта улучшений	rabbitmq project
4 модуля проекта?	<b>smart-fridge-api-contract</b> (REST-контракт) · <b>smart-fridge-service</b> (8080, REST+GraphQL DGS) · <b>smart-fridge-events-contract</b> (события) · <b>smart-fridge-audit-service</b> (8081)	project
Коды GlobalExceptionHandler?	<b>404</b> resource-not-found · <b>400</b> validation-error + fieldErrors · <b>500</b> internal-error; BASE = https://api.example.com/problems/	errors project
События проекта (payload)?	ProductEvent permits <b>Created(id,name,category), Updated(id,name,category), Deleted(id,name)</b>; FridgeItemEvent аналогично + quantity/unit/expiresAt; Deleted — минимальный payload	project sealed
Как разорван цикл ProductService↔FridgeItemService?	<b>@Lazy</b> на одной из инъекций: прокси вместо реального бина до первого использования	project
Живой dual write сбой в проекте?	ProductEventPublisher.send() в <b>try/catch → log.error</b>; демонстрация: docker stop rabbitmq → POST → 201, продукт создан, события нет, в логе строчка	project outbox
Хранилище и стек проекта?	In-memory <b>ConcurrentHashMap</b> (честный компромисс); Spring Boot 4, <b>Java 21</b> (sealed/exhaustive switch), DGS 11, порты 8080/8081	project
