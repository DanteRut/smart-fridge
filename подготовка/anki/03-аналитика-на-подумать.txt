[сквозное] «Сложность переносится, не исчезает» — раскройте на трёх механизмах курса	1) HATEOAS: знание структуры API переехало с клиента на сервер (матрица ссылок) 2) GraphQL: сборка формы ответа — с клиента на резолверы (N+1) 3) BFF: агрегация — с фронтенда в отдельный слой (его отказоустойчивость)
[сквозное] Почему тихий сбой хуже громкого? Приведите примеры с обеих сторон	Тихий не подаёт сигнала: полей нет в JSON, подсказка исчезла, потеря события — узнаем при сверке. Громкий кричит: MatchException, 500, DLQ растёт — есть алерт и лог. Инженерный вывод: делать сбои громкими
[события] Почему exactly-once невозможен через сеть без идемпотентности?	Подтверждение может потеряться после применения операции → отправитель обязан повторить → дубликаты неизбежны. Единственный честный контракт: at-least-once + дедуп по eventId на получателе
[сквозное] «Метрика мерит форму, не стоимость» — расширите за пределы depth/complexity	Любая статическая метрика: LOC, cyclomatic complexity, depth. Дешёвая форма + дорогой резолвер пройдёт. Дополнение: таймауты, лимиты пагинации, профилирование — только они мерят реальную стоимость
[контракт] Почему contract-first выигрывает при нескольких командах?	Контракт = точка синхронизации: команды стартуют параллельно (стабы по контракту), javac ловит рассинхрон, документация генерится из источника и не устаревает. Code-first = правда живёт в коде одного сервиса
[GraphQL] Depth-лимит бесполезен один. Какой общий принцип защиты он иллюстрирует?	Защита слоями: каждая мера отсекает класс атак (вертикаль), следующая — другой (ширина, вес, время). Нет одного замка — есть глубина обороны: depth + complexity + лимит пагинации + таймаут
[RabbitMQ] fanout: очередь отдаёт сообщение одному. Какое архитектурное следствие?	Competing consumers — легальный способ масштабировать обработку одной очереди; а дубликат на сервис = число очередей, не инстансов. Хочешь «всем» — очередь на потребителя
[события] «Consumer'ов деплоить раньше producer'ов» — обобщите правило	Это обратная совместимость чтения: читающий должен понимать старое+новое до того, как пишущий начнёт слать новое. Работает для sealed, proto (номера), JSON (алиасы), схемы БД
[Protobuf] Имена полей не ездят по проводу в proto. Какое следствие для эволюции?	Переименование безопасно (едет только номер) → ломают номера/wire type. В JSON — наоборот: имена и есть контракт → в ошибках валидации нужен стабильный code вместо field
[REST] Зачем POST возвращает 201 + Location, а не просто 200?	201 = «создан новый ресурс» (машина читает семантику), Location = готовый адрес для GET — клиент не строит URL сам (идея HATEOAS), плюс кэши/прокси корректно обрабатывают статус
[REST] Какие слои могут переписать HTTP-статус? Почему семантика едет в теле?	Шлюзы, балансировщики, таймауты, circuit breaker'ы, fallback'и — каждый может подменить статус. Тело (RFC 7807) доезжает как есть → клиент решает по type/status из тела
[Sealed] Sealed (закрыт) vs обычный интерфейс (открыт) — когда какой?	Полный контроль над вариантами и exhaustive-проверка → sealed (доменные события, состояния). Третьи стороны расширяют без твоего ведома → открытый интерфейс (SPI, плагины). Закрытость = сила (проверка) и потолок (не расширить извне)
[GraphQL · контракт] Схема GraphQL рядом с резолверами vs отдельный модуль?	Один сервис → рядом: схема меняется с резолверами одним деплоем, не разъедутся. Отдельный артефакт → федерация, несколько сервисов-владельцев схемы, внешние потребители публикуемой схемы
[BFF] Когда BFF становится анти-паттерном?	Когда домен срастается с UI-экраном: слой знает про кнопки, а не про ресурсы; бизнес-логика дублируется; на каждый фронт — свой BFF (расходятся контракты и релизы)
[REST · PATCH] Почему PATCH не спасает от lost update?	Дельта может вычисляться от устаревшего чтения: «+5» к старому значению затирает чужую правку. Лечится не методом, а version/If-Match (оптимистичная блокировка, 412 при конфликте)
[события] Потеря vs фантом: почему «что хуже» зависит от домена?	Аудит: потеря тише и опаснее (пробел в истории живёт месяцами). Деньги наружу: фантом хуже (двойная выплата видна сразу больно). Вывод: выбор стратегии зависит от цены ошибки в домене, а не от вкуса
[события] Почему дедуп по eventId, а не по содержимому сообщения?	Содержимое может легитимно совпасть у двух разных событий (дважды «К» купил 1 молоко). eventId уникален фактом отправки; это идентификатор факта, а не данных
[REST · RMM] L3 по Ричардсону всем нужен? Честный ответ	Нет: цена (матрица, ассемблеры, тесты) может превысить выгоду. Оправдан: долгоживущие API со сменными клиентами, workflow/состояния. Закрытый CRUD — достаточно L2
[валидация] Почему валидация живёт на контракте, а не в сервисном слое?	Единая точка правды: сервер валидирует ровно то, что задокументировано; сгенерированные клиенты знают те же правила; нет рассинхрона «дока говорит одно, проверяется другое»
[HATEOAS] Чем HATEOAS принципиально отличается от документации API?	Ссылки машинно-исполнимы и всегда актуальны для текущего состояния; документация статична, устаревает и не участвует в рантайме. HATEOAS = «дока, встроенная в каждый ответ»
