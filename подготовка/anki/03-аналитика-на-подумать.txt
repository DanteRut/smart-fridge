«Сложность переносится, не исчезает» — раскройте на трёх механизмах курса	1) <b>HATEOAS</b>: знание структуры API переехало с клиента на сервер (матрица ссылок) 2) <b>GraphQL</b>: сборка формы ответа — с клиента на резолверы (N+1) 3) <b>BFF</b>: агрегация — с фронтенда в отдельный слой (его отказоустойчивость)	analytics
Почему тихий сбой хуже громкого? Приведите примеры с обеих сторон	Тихий <b>не подаёт сигнала</b>: полей нет в JSON, подсказка исчезла, потеря события — узнаем при сверке. Громкий кричит: MatchException, 500, DLQ растёт — есть алерт и лог. Инженерный вывод: <b>делать сбои громкими</b>	analytics
Почему exactly-once невозможен через сеть без идемпотентности?	Подтверждение может потеряться <b>после</b> применения операции → отправитель обязан повторить → дубликаты неизбежны. Единственный честный контракт: at-least-once + <b>дедуп по eventId</b> на получателе	analytics
«Метрика мерит форму, не стоимость» — расширите за пределы depth/complexity	Любая статическая метрика: LOC, cyclomatic complexity, depth. Дешёвая форма + дорогой резолвер пройдёт. Дополнение: <b>таймауты</b>, лимиты пагинации, профилирование — только они мерят реальную стоимость	analytics
Почему contract-first выигрывает при нескольких командах?	Контракт = точка синхронизации: <b>команды стартуют параллельно</b> (стабы по контракту), javac ловит рассинхрон, документация генерится из источника и не устаревает. Code-first = правда живёт в коде одного сервиса	analytics contract
Depth-лимит бесполезен один. Какой общий принцип защиты он иллюстрирует?	<b>Защита слоями</b>: каждая мера отсекает класс атак (вертикаль), следующая — другой (ширина, вес, время). Нет одного замка — есть глубина обороны: depth + complexity + лимит пагинации + таймаут	analytics security
fanout: очередь отдаёт сообщение одному. Какое архитектурное следствие?	<b>Competing consumers</b> — легальный способ масштабировать обработку одной очереди; а дубликат на сервис = число очередей, не инстансов. Хочешь «всем» — очередь на потребителя	analytics rabbitmq
«Consumer'ов деплоить раньше producer'ов» — обобщите правило	Это <b>обратная совместимость чтения</b>: читающий должен понимать старое+новое до того, как пишущий начнёт слать новое. Работает для sealed, proto (номера), JSON (алиасы), схемы БД	analytics sealed
Имена полей не ездят по проводу в proto. Какое следствие для эволюции?	Переименование безопасно (едет только номер) → ломают <b>номера/wire type</b>. В JSON — наоборот: имена и есть контракт → в ошибках валидации нужен стабильный <b>code</b> вместо field	analytics proto
Зачем POST возвращает 201 + Location, а не просто 200?	<b>201</b> = «создан новый ресурс» (машина читает семантику), <b>Location</b> = готовый адрес для GET — клиент не строит URL сам (идея HATEOAS), плюс кэши/прокси корректно обрабатывают статус	analytics rest
Какие слои могут переписать HTTP-статус? Почему семантика едет в теле?	Шлюзы, балансировщики, таймауты, circuit breaker'ы, fallback'и — каждый может подменить статус. <b>Тело (RFC 7807) доезжает как есть</b> → клиент решает по type/status из тела	analytics errors
Sealed (закрыт) vs обычный интерфейс (открыт) — когда какой?	Полный контроль над вариантами и exhaustive-проверка → <b>sealed</b> (доменные события, состояния). Третьи стороны расширяют без твоего ведома → <b>открытый интерфейс</b> (SPI, плагины). Закрытость = сила (проверка) и потолок (не расширить извне)	analytics sealed
Схема GraphQL рядом с резолверами vs отдельный модуль?	Один сервис → <b>рядом</b>: схема меняется с резолверами одним деплоем, не разъедутся. Отдельный артефакт → федерация, несколько сервисов-владельцев схемы, внешние потребители публикуемой схемы	analytics graphql contract
Когда BFF становится анти-паттерном?	Когда <b>домен срастается с UI-экраном</b>: слой знает про кнопки, а не про ресурсы; бизнес-логика дублируется; на каждый фронт — свой BFF (расходятся контракты и релизы)	analytics bff
Почему PATCH не спасает от lost update?	Дельта может вычисляться от <b>устаревшего чтения</b>: «+5» к старому значению затирает чужую правку. Лечится не методом, а <b>version/If-Match</b> (оптимистичная блокировка, 412 при конфликте)	analytics patch
Потеря vs фантом: почему «что хуже» зависит от домена?	<b>Аудит</b>: потеря тише и опаснее (пробел в истории живёт месяцами). <b>Деньги наружу</b>: фантом хуже (двойная выплата видна сразу больно). Вывод: выбор стратегии зависит от цены ошибки в домене, а не от вкуса	analytics outbox
Почему дедуп по eventId, а не по содержимому сообщения?	Содержимое может <b>легитимно совпасть</b> у двух разных событий (дважды «К» купил 1 молоко). eventId уникален фактом отправки; это идентификатор факта, а не данных	analytics events
L3 по Ричардсону всем нужен? Честный ответ	Нет: цена (матрица, ассемблеры, тесты) может превысить выгоду. Оправдан: <b>долгоживущие API со сменными клиентами</b>, workflow/состояния. Закрытый CRUD — достаточно L2	analytics rmm
Почему валидация живёт на контракте, а не в сервисном слое?	Единая точка правды: сервер валидирует <b>ровно то, что задокументировано</b>; сгенерированные клиенты знают те же правила; нет рассинхрона «дока говорит одно, проверяется другое»	analytics validation
Чем HATEOAS принципиально отличается от документации API?	Ссылки <b>машинно-исполнимы и всегда актуальны</b> для текущего состояния; документация статична, устаревает и не участвует в рантайме. HATEOAS = «дока, встроенная в каждый ответ»	analytics hateoas
