[REST] Сервис отдал 404, но шлюз вернул 200 с заглушкой. Что увидит клиент и почему это опасно?	Клиент видит «успех» → парсит тело → пустая карточка товара, ни ретрая, ни алерта; в мониторинге всё зелёное. Тихий сбой. Фикс: семантика в теле (RFC 7807) + шлюз pass-through
[REST] Как curl'ом найти звено, подменяющее статус?	По хопам: curl напрямую в сервис (честный 404) vs curl через шлюз (200). Разница → виноват шлюз; дальше его конфиг/таймауты/fallback
[REST] Поле author есть в БД, но пропало из JSON. Где искать? (4 точки)	Идём от сериализации вглубь: 1) нет поля в DTO 2) маппер не скопировал 3) @JsonInclude(NON_NULL) выкинул null 4) naming strategy сменил имя. Тихо, потому что это конфигурация, а не ошибка
[Валидация] Переименовали isbn → productIdentifier. Что видит старый клиент?	Валидация падает на новом имени → в fieldErrors field='productIdentifier' → фронт не находит инпут с таким name → подсказка молча не показывается. QA не заметит
[REST] PUT {'name':'Колбаса'} без категории по существующему id. Результат?	Категория = null — замещение целиком: не прислал поле = его больше нет. Это не баг, а семантика PUT (клиент обязан слать полное состояние)
[REST] Наш PATCH {'category': null}. Результат?	«Не трогать» — категория осталась. Пользователь думал, что стёр. Обнулить поле через наш PATCH нельзя — договорённость null=не трогать
[REST] Клиенту надо ОЧИСТИТЬ поле через PATCH. Три пути?	1) RFC 7386: null = очистить (перейти на Merge-семантику) 2) RFC 6902: op:remove 3) своё reset:['category'] или JsonNullable (ABSENT/NULL/VALUE)
[REST] Два клиента PUT-ят один продукт параллельно. Что случится?	Lost update: B перезапишет правку A старым значением, не зная о ней. Фикс: оптимистичная блокировка — поле version / заголовок If-Match (412 при конфликте)
[HATEOAS] Сервер переименовал /api/books → /api/catalog. Судьба двух клиентов?	Захардкоженный — 404 до релиза клиента; HATEOAS-клиент работает (взял свежий href из _links). Цена серверу: 301-redirect/двойная маршрутизация для старых ссылок
[HATEOAS] Клиент за прокси получил href='http://localhost:8080/...'. Причина?	Ссылка построена от локального запроса — не учтены X-Forwarded-Host / X-Forwarded-Proto. «Гибкий» клиент сломался так же, как захардкоженный
[HATEOAS] В одном состоянии ресурса забыли ссылку delete. Что для HATEOAS-клиента?	Действия не существует — догадаться он не может: кнопка просто не отрисуется. Полнота матрицы состояние×действие — ответственность сервера
[HATEOAS] UI просит заранее показать задизейбленную кнопку «почему нельзя». Что ответить сервером?	1) allowed:false + reason в теле 2) реестр rel (клиент знает полный словарь действий) 3) BFF с canX-флагами под экран
[GraphQL] GraphQL: MaxQueryDepth(20), атакующий шлёт products(first:100000){items(first:100000)}. Почему depth молчит?	Глубина — 2, работа — сотни тысяч объектов: depth слеп к ширине. Ловит MaxQueryComplexity: пагинация умножает вес ветки
[GraphQL] Запрос с 200 алиасами одного поля: a:products{...} b:products{...}. Что скажет depth?	Глубина не изменилась, работа ×200 — depth не видит повторов; complexity суммирует алиасы. Плюс серверный лимит пагинации
[GraphQL] query { products { items } } на 50 продуктах лёг на БД. Диагноз и лечение?	N+1: резолвер items для каждого продукта (50→51 вызов). Лечение: DataLoader — копит product_id, один батч WHERE IN
[GraphQL] mutation { create(...) update(...) delete(...) }. Порядок исполнения и почему?	Строго последовательно, по порядку в тексте: нельзя обновить то, что ещё не создано. Семантика языка, не договорённость сервера (query — параллельно)
[GraphQL] GraphQL вернул HTTP 200, но данные не пришли. Как клиент узнаёт об ошибке?	По полю errors[] (message, path, extensions): частичный успех возможен — data и errors вместе. Всегда 200 — клиент ветвится по errors, не по статусу
[GraphQL · контракт] Предложение: «схему GraphQL — в модуль REST-контроллеров». Оценка?	REST-контракт = Java-типы → модуль-артефакт осмыслен. GraphQL-контракт = SDL-файл, клиенту Java не нужен → дефолт DGS: схема в resources рядом с резолверами; отдельный модуль — только при федерации/внешних потребителях схемы
[Protobuf] proto: добавили string category = 3. Что видит старый клиент?	Тег 3 неизвестен → wire type 2 (len) → пропускает блок, name/count читает как раньше. Новый на старых данных: category = '' (дефолт)
[Protobuf] proto: сменили поле №2 с int32 на string. Что произойдёт?	Падение парсера у старого кода: ждал varint (wire 0), получил length-delimited (wire 2). Громкий сбой — диагноз виден сразу
[Protobuf] proto: сменили int32 → int64 (тот же номер). Что произойдёт?	Тихий мусор: wire type тот же (0), парсинг «успешен», но значения искажены (усечение/переинтерпретация). Хуже падения
[Protobuf] proto: поле count (№2) удалили, на №2 посадили supplier_id string без reserved. Итог?	Старые сообщения в очереди: varint-байты читаются как length-блок → каша или крэш. Лечение: reserved 2; reserved 'count'; + buf breaking в CI
[RabbitMQ] Продюсер шлёт без publisher confirms, брокер падает «в полёте». Итог?	Сообщение исчезло, продюсер уверен, что отправил — тихая потеря. Фикс: confirms — брокер квитанцией подтверждает приём, нет квитанции — ретрай
[RabbitMQ] Сообщение легло в очередь в памяти, брокер перезапустился. Итог?	Стёрто. Фикс: durable exchange/queue + persistent message (delivery mode 2) — на диск
[RabbitMQ] auto-ack: consumer обработал половину и упал. Сколько сообщений потеряно?	Всё текущее и те, что брокер уже вычеркнул при отправке. Фикс: manual ack — basicAck только после успешной обработки
[RabbitMQ] manual ack: битое сообщение валит обработку каждый раз. Что происходит с очередью?	Бесконечный redelivery-луп, очередь стоит. Фикс: лимит ретраев → basicNack(requeue=false) → DLQ: поток жив, разбор отложен
[События] Доставка at-least-once настроена. Что ОБЯЗАН добавить consumer?	Дедупликацию по EventEnvelope.metadata.eventId (идемпотентность): дубликаты после ретраев — норма, а не авария
[Проект · события] docker stop rabbitmq → POST /api/products в нашем проекте. Что произошло?	save прошёл → send бросил → наш try/catch → log.error → клиенту 201. Продукт есть, события нет — тихая потеря (живой dual write сбой)
[События] Порядок в dual write обратный: сначала send, потом save; save упал. Что в аудите?	Фантом: событие о несуществующем продукте. Громче (замечают быстро); потеря тише и потому для аудита опаснее. Для денег наружу — наоборот
[Sealed] В enum-мире добавили ProductMerged. Что сделает старый switch с default?	Тихо отправит в default: компилятор полноту enum-switch с default не проверяет. Аудит merge не запишет — узнаем при сверке данных
[Sealed] Sealed-мир: добавили record Merged + permits. Что у пересобранного consumer?	Ошибка компиляции: switch не покрывает Merged → разработчик вынужден написать ветку. Проблема поймана на сборке, не в проде
[Sealed] Sealed-мир: producer шлёт Merged, consumer со старым jar без default. Рантайм?	MatchException — обработка падает громко, видно в мониторинге (лучше тишины). Отсюда: consumer'ов деплоить раньше producer'ов
