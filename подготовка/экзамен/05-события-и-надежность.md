## В18 ⭐. Dual write: БД + RabbitMQ без общей транзакции

> *Формулировка прошлого экзамена:* Сервер сохраняет сущность в БД и публикует событие в RabbitMQ — две операции без транзакции. Сбой 1: БД сохранила, RabbitMQ недоступен — событие потеряно. Сбой 2: RabbitMQ отправил, БД не сохранила — потребители видят несуществующее. Какой из сбоев опаснее? Для него — решение, гарантирующее публикацию события или откат обоих действий.

### 🔄 Весь цикл по шагам

**Сценарий.** `POST /api/products` у нас: сначала `productService.save()` в хранилище, затем `productEventPublisher.send(ProductEvent.Created)` в RabbitMQ. Две системы, одной транзакции нет. Инъекция: `docker stop rabbitmq`.

1. save прошёл → `send` бросил исключение → у нас `try/catch → log.error` → клиенту ушёл **201**. Продукт живёт, аудита нет. **Потеря, и тихая**: в логах строчка, расхождение никто не увидит, пока не сверят данные.
2. Обратный порядок (сначала `send`, потом `save`), save упал: событие есть, продукта нет — **фантом**: аудит знает несуществующий продукт. Фантом громче (замечают быстро), потеря тише (и потому для аудита опаснее). Для «денег наружу» — наоборот, фантом хуже.
3. **Почему так:** хранилище и брокер — разные технологии, общего транзакционного механизма нет; 2PC/XA между ними никто не поднимет.
4. Полумеры не спасают: `afterCommit`-хук — упали между commit и publish → та же потеря; бесконечные ретраи `send` — брокер лежит дольше таймаута → потеряли.
5. **Решение — outbox:** в **той же транзакции**, что save, делаем `INSERT` в таблицу `outbox` (атомарно: либо обе записи, либо ни одной) → отдельный publisher вычитывает outbox, публикует **с confirms**, отмечает отправленным. Событие может задержаться, но не теряется — outbox лежит в БД и переживает падение брокера.
6. **Следствие:** доставка становится **at-least-once** (publisher мог отправить и упасть до отметки) → возможны дубликаты → дедуп у консюмера по `EventEnvelope.metadata.eventId`.

**Финал:** в два хранилища атомарно не написать — пишем атомарно в одно и **довозим из него**; платим: задержка события, таблица outbox и дедуп по eventId.

### 📚 Теория

**Почему это происходит:** между БД и брокером **нет общей транзакции в принципе** (2PC/XA с RabbitMQ на практике не применяют — брокер не полноценный XA-участник, а латентность убивает).

**Какой сбой опаснее — рассуждение по критерию «обнаружимость и обратимость»:**

| | Сбой 1 (потеря события) | Сбой 2 (фантом) |
|---|---|---|
| Кто знает о проблеме | **никто**: исключение поймано, в логе строчка, пользователь получил 200 | источник знает: пользователь получил ошибку, операция повторится |
| Самоликвидируется? | **никогда**: аудит неполон, статистика неверна, уведомление не ушло | да: потребитель может отбить фантом проверкой существования / ссылкой в DLQ |
| Тип | **тихий** | громкий |

**Вывод: опаснее сбой 1 — потеря события** (тихий, необратимый, нужен ручной reconciliation, о котором никто не знает). **Честная оговорка на плюс:** если потребители совершают необратимые действия во внешний мир (списание денег, письма клиентам) — фантом может быть опаснее потерянного события; ответ зависит от домена, но дефолт — потеря.

**Решение: Transactional Outbox.**

```
┌──────────── одна локальная ACID-транзакция БД ────────────┐
│  INSERT INTO products (...)                                │
│  INSERT INTO outbox (eventId, type, payload, rk, status)   │
└────────────────────────────────────────────────────────────┘
                        │ коммит
                        ▼
     Релизер (фоновый поллер или CDC/Debezium):
     SELECT ... FROM outbox WHERE status='NEW'
                        │ публикует с publisher confirms
                        ▼
                 RabbitMQ (exchange)
                        │ подтверждение брокера
                        ▼
        UPDATE outbox SET status='PUBLISHED'
```

1. Сущность **и** строка события пишутся в **одной ACID-транзакции**: атомарность гарантирует БД — либо обе записи, либо откат обеих. Это и есть «гарантия публикации или откат обоих действий».
2. **Релизер** выбирает неопубликованные строки и публикует **с publisher confirms** (лекция: «издатель ждёт подтверждения брокера»); после подтверждения помечает PUBLISHED.
3. Сбой 1 невозможен: закоммитилось → событие на диске в outbox → будет опубликовано даже после падения сервиса. Сбой 2 невозможен: откатилось → публиковать нечего.

**Цена (назвать самому):** гарантия **at-least-once**, не ровно-once — релизер может опубликовать дважды (умер между публикацией и UPDATE outbox). **Ровно-once между БД и брокером не существует** → потребители обязаны быть **идемпотентными**: дедупликация по `eventId` (таблица обработанных ID; дубликат → ack без обработки).

**Альтернативы (назвать и объяснить, почему хуже):**
- **`afterCommit`-колбэк:** убирает фантом, но смерть процесса между коммитом и публикацией = снова потеря; обязательство нигде не зафиксировано. Outbox сильнее: обязательство **на диске до** публикации.
- **Транзакции RabbitMQ (tx.select):** объединяются только с собой, не с БД — проблему не решают.
- **2PC/XA:** не с этим брокером, не на этих латентностях.

**Проект (сильнейший ход — показать на своём коде):** `ProductEventPublisher.send()` вызывается из `ProductService.create` сразу после записи в storage и оборачивает отправку в try/catch с `log.error` — это ровно **сбой 1**, воспроизводимый `docker stop rabbitmq`. Улучшение: outbox-таблица + релизер; `EventEnvelope.metadata.eventId` (UUID) уже есть — готовый ключ дедупликации. Также честно: у audit-сервиса нет manual ack и DLQ (см. В20).

### 🧠 Каркас ответа
1. Постановка: общей транзакции нет в принципе (2PC — не вариант).
2. Сравнение сбоев по «тихий vs громкий»: потеря опаснее — необратима и незаметна; оговорка про внешние действия.
3. Outbox: одна транзакция (сущность+обязательство), релизер с confirms, PUBLISHED-статус.
4. Цена: at-least-once → идемпотентные потребители, дедупликация по eventId.
5. Альтернативы и почему нет (afterCommit, tx, 2PC).
6. Проект: показать уязвимую строку в своём Publisher + как бы исправил.

### ⚠️ Вероятные уточняющие
- **«Почему невозможно ровно-once?»** — Подтверждение брокера и отметка в outbox — две несделки в одной атомарной операции; между ними всегда окно сбоя. Ровно-once эффект достигается **эффектом**: at-least-once + дедупликация на потребителе.
- **«Что если сам outbox-релизер умер надолго?»** — События копятся в таблице и уйдут после восстановления; рост очереди outbox — метрика для алерта.
- **«CDC — это что?»** — Change Data Capture: чтение изменений из WAL БД (Debezium) — outbox-строки уезжают в брокер без поллера.

## В19 ⭐. Sealed interface событий: что дал такого, чего не дал бы enum? И чем слабее, чем кажется?

> *Формулировка прошлого экзамена:* События описаны sealed interface с record-наследниками: Created, Updated, Deleted. Consumer пишет switch — компилятор требует покрыть все ветки. Разработчик добавляет default → игнорировать. Выходит новый тип Enriched — consumer не знает о нём и молча игнорирует. Что sealed дал такого, чего не дал бы enum? В чём он слабее, чем кажется?

### 🧩 С нуля: зачем sealed вообще существует

**Задача.** Представить в Java «событие, которое — ОДНО ИЗ трёх видов, и у каждого вида СВОИ данные» так, чтобы при добавлении четвёртого вида компилятор сам заставил всех обработчиков отреагировать.

- **Способ 1 — класс с enum Type + общие поля.** Один набор полей на все виды → у `Deleted` появляются бессмысленные `category` (поля-призраки: где-то null, невалидные состояния возможны). Switch по enum с `default` **не проверяется на полноту** → новый тип молча уходит в default.
- **Способ 2 — обычный интерфейс + наследники-record'ы.** У каждого свои поля (уже хорошо), но интерфейс **открыт**: кто угодно добавит своего наследника; цепочка `if (x instanceof ...)` не проверяется на полноту — забыл ветку, никто не заметит.
- **Способ 3 — sealed.** Закрытый список наследников (`permits`) + у каждого свой payload + **exhaustive switch**: не покрыл всех → ошибка компиляции.

**Мнемоника:** enum — закрытый список **ЗНАЧЕНИЙ** при **одном** наборе полей; sealed — закрытый список **ТИПОВ**, у **каждого** свой набор. У всех вариантов одинаковые данные (день недели) → enum; разные (события) → sealed.

### 🔄 Весь цикл по шагам

**Сценарий.** Аудит-сервис вычитывает `ProductEvent` из очереди и обрабатывает switch'ем. Добавляем новый тип события `ProductMerged` — и смотрим, кто это заметит в мире enum и в мире sealed.

1. **Мир enum:** `enum Type {CREATED, UPDATED, DELETED}` + payload-поля рядом. Расширяем enum. Switch у консюмера: `case CREATED/UPDATED/DELETED` + `default: log.info(...)` → новый вариант **тихо ушёл в default**. Компилятор молчал: полноту покрытия enum он не проверяет.
2. **Мир sealed:** `sealed interface ProductEvent permits Created, Updated, Deleted`, каждый вариант — record **со своим payload** (`Created(Product p)`, `Deleted(Long id)`) — не разводим параллельные структуры. `switch (event) { case Created c -> ...; case Updated u -> ...; case Deleted d -> ...; }` **без default** — компилятор требует полноты: добавили вариант в permits без case → **ошибка компиляции**. Изменение контракта стало проверяемым.
3. Если ветку забыли в рантайме (старый switch против нового класса) → **MatchException** — громко: падение обработки, а не тишина.
4. **«Чем слабее, чем кажется»:** exhaustive работает только у **пересобранного** консюмера. Чужой сервис со старым jar и своим `default`-веткой проглотит новый вариант всё так же тихо. Плюс иерархия запечатана в одном модуле — чужие варианты не добавить (это и сила, и потолок расширения).
5. **Рецепт:** `default` не «глотать», а warn + метрика (+ DLQ при интеграции); консюмеров обновлять и деплоить **раньше** продюсеров.
6. **У нас:** `ProductEvent permits Created/Updated/Deleted`; `EventEnvelope.eventId` — ключ дедупа; audit-listener пока **без switch** (просто лог) — «добавил бы exhaustive-switch» готовый ход на защите.

**Финал:** enum+switch = «незнакомое — молча в default»; sealed = незакрытая ветка — ошибка компиляции, незнакомый класс в рантайме — громкий MatchException. Но защита действует лишь на пересобранном коде — отсюда деплой консюмеров раньше продюсеров и default с алармой.

### 📚 Теория

**Что sealed + records дал по сравнению с enum:**
1. **Разные payload у разных вариантов (алгебраический тип-сумма).** Enum — набор значений **одного** типа с общей формой: для `DELETED` пришлось бы держать общие nullable-поля (`name`, `category` = null) и надеяться, что их не прочитают не у того варианта. У нас: `Created(Long id, String name, String category)` и `Deleted(Long id, String name)` — **свои** поля, компилятор проверяет доступ.
2. **Исчерпывающий switch по типам.** `permits` перечисляет всех наследников — компилятор знает иерархию целиком: switch-выражение **без default** при появлении нового типа **не компилируется**. Эволюция контракта проверяется на сборке — добавил `Enriched` в контракт: все консьюмеры без default падают сборкой и принудительно решают, что делать.
3. **Закрытость:** `permits` запрещает сторонним сервисам подсунуть свой тип события.

**Чем слабее, чем кажется (суть второй половины вопроса):**
1. **`default` гасит всю магию.** Достаточно одной ветки `default -> игнорировать` — компилятор **никогда** больше не напомнит о новых типах. Исчерпываемость — дисциплина команды, не свойство рантайма.
2. **Компилятор защищает только на момент сборки.** Событие приезжает **по сети в рантайме**. Продюсер задеплоил раньше со свежим контрактом → консьюмер работает со **старым** классом, собранным без `Enriched`. Дальше развилка:
   - **без default:** switch-expression бросит **`MatchException`** → сообщение падает → ретрай/DLQ → **проблему заметят** (громкий сбой);
   - **с `default -> игнорировать`:** **тихая потеря** событий — никто никогда не узнает.
   То есть sealed даёт выбор «падать громко / молчать», но не «автоматически понять новый тип».
3. **Централизация:** все наследники в одном модуле — чужой сервис не расширит тип без изменения общего контракта (защита и бюрократия одновременно).

**Инженерный вывод:** правильный default — не молчание: `default -> log.warn + метрика unknown_event + DLQ`. Новый тип хотя бы заметен. Плюс: разворачивать консьюмеров **раньше** продюсеров (сначала все умеют читать новое — потом начинаем писать), версионировать контракт событий.

**Проект:** ровно наш `ProductEvent` — `sealed interface permits Created, Updated, Deleted` с record'ами; рядом `FridgeItemEvent`; возит их `EventEnvelope`. А audit-сервис слушает `#` и логирует конверт **без switch** — «новый тип он не заметит вовсе»; консьюмер со switch+default — «заметит и промолчит». Обе ситуации показать на своём коде.

### 🧠 Каркас ответа
1. Что дал vs enum: типизированные варианты с разными payload + exhaustive switch (эволюция проверяется на сборке) + закрытость permits.
2. Слабости: default гасит проверку; компиляция ≠ рантайм (версии продюсера/консьюмера) — развилка MatchException vs тишина; централизация.
3. Вывод: default = warn+метрика+DLQ; консьюмеры раньше продюсеров; версии контракта.
4. Проект: ProductEvent + audit-listener без switch.

### ⚠️ Вероятные уточняющие
- **«Enum-то тоже exhaustive в switch!»** — Да, но значения одного типа с общей формой: разные payload не выражаешь без nullable-полей; sealed+records — это про данные вариантов.
- **«Как безопасно добавлять типы событий?»** — Цикл: добавить в контракт → пересобрать и **сначала** выкатить консьюмеров (умеют читать новое, игнорируют корректно) → потом продюсер начинает слать.
- **«MatchException — это хорошо?»** — Как минимум честно: громкий сбой попадает в ретрай/DLQ/мониторинг; тихая потеря — худший исход.

## В20 ➕. Гарантированная доставка: три звена, acks, DLQ, идемпотентность

### 🔄 Весь цикл по шагам

**Сценарий.** Сообщение `ProductCreated` едет от сервиса к аудиту. Три звена пути — три способа умереть — три механизма защиты.

1. **Звено 1: продюсер → брокер.** Продюсер кинул в сеть, брокер упал в полёте → сообщение исчезло, а продюсер уверен, что отправил. Защита: **publisher confirms** — брокер квитанцией подтверждает приём; квитанции нет — ретрай. Плюс exchange/queue объявлены **durable**.
2. **Звено 2: брокер хранит.** Сообщение легло в очередь, брокер перезапустился → из памяти всё стёрто. Защита: **durable queue + persistent message** (delivery mode 2) — сообщение пишется на диск и переживает рестарт.
3. **Звено 3: брокер → консюмер.** **auto-ack**: брокер отдал и сразу вычеркнул; консюмер упал на полпути → «доставлено», работы нет → **потеря**. Защита: **manual ack** — `basicAck` только после успешной обработки; не подтвердилось → брокер вернёт в очередь (redelivery). Отсюда гарантия **at-least-once**: дубли возможны → **дедуп по `EventEnvelope.metadata.eventId`** (идемпотентный консюмер).
4. **Ядовитое сообщение:** битая запись валит обработку каждый раз → при manual ack — бесконечный redelivery-луп, очередь стоит. Лечение: ограниченное число ретраев → `basicNack(requeue=false)` → **DLQ**: отдельная очередь для разборки: поток жив, сообщение не потеряно (разбор отложен, а не отменён).
5. **Порядок включения:** confirms → durable/persistent → manual ack → DLQ → дедуп: каждый следующий слой осмыслен только при работающем предыдущем.
6. **В проекте не настроено ничего из трёх звеньев:** auto-ack в листенере, confirms нет, DLQ нет, дедупа нет (аудит просто логирует) — готовая «карта улучшений» на защите.

**Финал:** три звена — три способа умереть — три механизма: confirms (довезли), durable+persistent (пережили рестарт брокера), manual ack (обработали до подтверждения); DLQ — куда падает непереваримое, дедуп — плата за at-least-once.

### 📚 Теория

**Надёжная доставка — трёхстороннее соглашение (выучить таблицей):**

| Звено | Механизм | Закрывает риск |
|---|---|---|
| Producer → Broker | **Publisher Confirms** (`spring.rabbitmq.publisher-confirm-type=correlated`) | издатель не знал, дошло ли; брокер молча потерял |
| Broker (хранение) | **durable** exchange/queue + **persistent** сообщения | потеря при перезагрузке брокера |
| Broker → Consumer | **Acknowledgements** (`acknowledge-mode=manual`) | потребитель взял, упал — а брокер уже удалил |

Одного звена мало: confirms не спасут от недолговечной очереди; durable — от auto-ack; вместе — контракт.

**Manual ack:** по умолчанию Spring Boot подтверждает **автоматически** — брокер считает сообщение обработанным сразу после отправки; упал посреди обработки → потеря навсегда. Ручной режим:
```java
try { process(envelope); channel.basicAck(tag, false); }        // «обработал, удаляй»
catch (Exception e) { channel.basicNack(tag, false, false); }   // requeue=false → в DLQ
```
`basicNack(requeue=true)` — вернуть в очередь (ретрай), `false` — не пытаться снова.

**DLQ (Dead Letter Queue):** основная очередь объявляется с dead-letter-exchange; необработанные/TTL-истёкшие сообщения уезжают в отдельную очередь. Даёт: основную очередь не блокирует «ядовитое» сообщение (иначе цикл requeue-crash парализует обработку); инженеры изучают и переотправляют; рост DLQ = алерт. Формула: *«DLQ превращает тихий сбой в громкий»*.

**Идемпотентность потребителя:** дубликаты неизбежны (at-least-once — см. В18); защита — дедупликация по `EventEnvelope.metadata.eventId` (хранить обработанные; дубликат → ack без обработки) либо идемпотентные операции (upsert вместо insert, set вместо increment).

**Topic-маршрутизация (проговорить в ответе):** `*` — ровно одно слово, `#` — ноль и больше. Для `product.created`: `product.#` ✓, `*.created` ✓, `product.created` ✗ (нужно ровно 3 слова), `#.deleted` ✗. Наш audit слушает `#` (всё), статистика слушала бы `*.created`.

**Проект:** есть durable topic exchange + durable queue + `#`-биндинг; **нет** confirms, manual ack, DLQ, дедупликации — полная карта «что бы я добавил» — это готовый ответ.

### 🧠 Каркас ответа
1. Таблица трёх звеньев + «одного мало» с примером.
2. Auto-ack опасен — почему; два метода канала и их семантика.
3. DLQ: зачем, что даёт, формула «тихий → громкий».
4. Дубликаты at-least-once → идемпотентность по eventId.
5. Проект: что стоит, чего нет, что бы добавил.

### ⚠️ Вероятные уточняющие
- **«Что случится с auto-ack при падении консьюмера?»** — Сообщение уже удалено из очереди в момент отправки → безвозвратная потеря.
- **«Correlated vs simple confirms?»** — correlated позволяет сопоставить подтверждение с конкретным сообщением (CorrelationData) — основа надёжного релизера; simple — просто «ок/не ок».
- **«Что durable, а что persistent?»** — durable — свойства **сущностей** (exchange/queue переживают рестарт брокера), persistent — свойство **сообщения**; работает только в паре с durable-очередью.
