## В1 ⭐. Шлюз отдаёт 200 OK вместо 404 — зависимость клиента от транспорта

> *Формулировка прошлого экзамена:* Сервер возвращает 404 Not Found с телом `{status, title, detail}`. Клиент проверяет HTTP-статус. Если завтра этот сервер обернут за API-шлюзом, который при ошибках всегда отдаёт 200 OK с телом `{"data": null, "errors": [...]}`, клиент сломается. Какое архитектурное решение на стороне сервера предотвратило бы зависимость клиента от транспортного уровня?

### 🔄 Весь цикл по шагам

**Сценарий.** Фронт запрашивает продукт `id=99`, его нет. Между браузером и нашим сервисом — шлюз. Участники: браузер → шлюз → smart-fridge-service:8080.

1. Браузер: `GET /api/products/99`. Ожидает либо 200 + JSON продукта, либо 404 + проблему.
2. Сервис (всё честно): `ProductService.findById(99)` → `ResourceNotFoundException("Product with id=99 not found")` → `GlobalExceptionHandler` → **404** + тело: `{"status":404, "type":"https://api.example.com/problems/resource-not-found", "title":"Ресурс не найден", "detail":"Product with id=99 not found", "instance":"/api/products/99"}`. И статус, и тело кричат «нет».
3. Шлюз между ними: у него свой обработчик/таймаут/fallback. Сервис не ответил за отведённое (или роут не сматчился) → шлюз возвращает **200** и **своё** тело-заглушку (пустой объект / HTML / «cached fallback»). Семантику чужого ответа он переписал своей.
4. Клиент: видит 200 → «успех» → парсит тело как `ProductResponse` → все поля null → пустая карточка товара. Ни ошибки, ни ретрая; в мониторинге 4xx ноль — всё зелёное. **Тихий сбой.**
5. Диагностика «по хопам»: `curl` напрямую сервис → 404 честный; `curl` через шлюз → 200. Сломанное звено — средний.

**Два фикса:** (а) семантику кладём в **тело**: RFC 7807 — клиент проверяет `type`/`status` в теле, а `application/problem+json` шлюз обязан прокидывать как есть; (б) шлюз настраиваем на pass-through: свои сбои шлюза — честными кодами (502/504), а не 200 с заглушкой.

**Финал:** ошибка должна ехать согласованно **и в статусе, и в теле**; клиент доверяет телу (`type`), шлюз не имеет права переписывать чужую семантику.

### 📚 Теория

**Различение двух уровней — сердце ответа:**
- **Транспортный уровень**: HTTP-статус-коды. Ими управляет не только твоё приложение — вся цепочка посредников: прокси, балансировщики, API-шлюзы, обёртки (тот самый шлюз превращает всё в `{data, errors}` — это модель GraphQL, где **всегда 200**, а ошибки — в теле).
- **Прикладной уровень (контракт)**: содержимое тела ответа. Это территория твоего сервиса.

Клиент, который принимает **семантическое** решение («ресурса нет → показать пустое состояние») по **транспортному** признаку (коду), зацеплен за деталь, которой распоряжаются посторонние.

**Решение: ошибка — часть прикладного контракта.** Фиксируется стандартный формат тела ошибки — **RFC 7807/9457 Problem Details**:

```
status    — 404 (код ДУБЛИРУЕТСЯ ВНУТРИ ТЕЛА — ключ к ответу!)
type      — URI типа проблемы ("https://api.example.com/problems/resource-not-found")
title     — краткое человекочитаемое ("Ресурс не найден")
detail    — конкретика ("Product with id=99 not found")
instance  — где произошло ("/api/products/99")
+ fieldErrors — только для ошибок валидации
```

Клиент принимает решение **по содержимому тела**, а статус использует как подсказку/оптимизацию. Если посредник перепишет код — контракт не треснет: тело той же структуры едет дальше.

**Что у тебя в проекте (сильный ход):** `ErrorResponse(status, type, title, detail, instance, timestamp, fieldErrors)` в `smart-fridge-api-contract` — поле `status` дублирует код в теле; обработка через `@ControllerAdvice` (`GlobalExceptionHandler`): 404/400/500 в одном месте. А GraphQL-часть проекта изначально живёт по модели «всегда 200 + errors» (`GraphQLExceptionHandler`, `TypedGraphQLError`).

**Честные компромиссы (назвать самому):**
- «200 OK с ошибкой в теле» кэшируется браузерами/CDN как успех → для таких ответов нужен `Cache-Control: no-store`.
- Мониторинг, алерты на 5xx, ретраи балансировщика — живут по статусам; при «всегда 200» их надо переводить на анализ тела/бизнес-метрики.

### 🧠 Каркас ответа
1. Диагноз: *«клиент зацеплен за транспорт — а статусом управляет любой посредник на пути: прокси, балансировщик, шлюз»*.
2. Решение: *«перенести семантику ошибки в прикладной контракт — машиночитаемое тело по RFC 7807; клиент решает по телу, статус — вспомогательный»*.
3. Подчеркнуть: `status` внутри тела дублирует код — именно это спасает за шлюзом.
4. Ограничение: *«статусы не выбрасываем — они нужны инфраструктуре (ретраи, мониторинг, кэш)»* + два компромисса (кэш, алерты).
5. Проект: ErrorResponse + два обработчика (REST и GraphQL) в моём сервисе — «две модели ошибок, обе прикладные».

### ⚠️ Вероятные уточняющие
- **«Так значит статусы вообще не нужны?»** — Нет: они для инфраструктуры (ретраи, CDN, SLO-алерты). Плохо не использовать статусы, плохо **принимать бизнес-решения только по ним** без проверки тела.
- **«Почему GraphQL всегда 200 — это хорошо?»** — Унификация: одна модель ошибок в теле, частичные ответы (data + errors одновременно). Но платит транспорт: кэширование, инфраструктурные алерты.
- **«Как быть, если шлюз чужой и его не изменить?»** — Именно поэтому контракт и должен жить в теле: ты не контролируешь посредников, ты контролируешь содержимое.

## В2 ➕. HTTP-статус-коды: зачем разнообразие, чем отличаются близкие коды

### 🔄 Весь цикл по шагам

**Сценарий.** Жизнь ОДНОГО запроса `POST /api/products` («Колбаса») через все точки отказа — статус-код это ответ «кто виноват и что делать».

1. Шлюз: нет / просрочен токен → **401 Unauthorized** (+ `WWW-Authenticate`). Смысл: «кто ты?» — залогинься и повтори.
2. Токен валиден, но роль USER, а операция админская → **403 Forbidden**. «Ты известен, прав нет» — повторять бессмысленно, чинит выдача прав.
3. Тело: `{"name": ""}` или кривой JSON → **400 Bad Request** — сломана структура/синтаксис (у нас: `@Valid` → `GlobalExceptionHandler`). Синтаксис ок, но контрольная сумма ISBN не сходится → это уже **422 Unprocessable Entity**: «понял, но по предметным правилам не проходит». Мы оба случая отвечаем 400 — упрощение, честно его признать.
4. Всё хорошо → **201 Created** + `Location: /api/products/7` + тело. POST **не идемпотентен**: повторный клик = второй продукт — поэтому фронт дизейблит кнопку, и клиент не ретраит POST сам.
5. Дальше по жизни ресурса: `GET /api/products/99` → **404**; NPE в сервисе → **500** (наша ошибка, смотри логи + Correlation ID); сервис перезапускается → шлюз отдаёт **502 Bad Gateway** («нижестоящий умер/не понял»); деплой → **503 Service Unavailable** + `Retry-After` («временно, повтори позже»).

**Финал-таблица:** 401/403 — «кто ты / что тебе можно»; 400/422 — «сломано / не проходит по смыслу»; 500/502/503 — «упал я / упал посредник / временно недоступен». 4xx чинит клиент, 5xx — сервер, 3xx — «иди туда».

### 📚 Теория

Пять классов: 1xx информационные (101 Switching Protocols — рукопожатие WebSocket), 2xx успех (200, **201 Created** + заголовок `Location`, **202 Accepted** — принято в обработку, **204 No Content**), 3xx перенаправление/кэш (301, 304 Not Modified), 4xx **ошибка клиента**, 5xx **ошибка сервера**.

Коды, которые спрашивают:

| Код | Смысл | Отличие от соседа |
|---|---|---|
| 400 Bad Request | запрос синтаксически/семантически кривой | 422 — «синтаксис ок, семантика нет» |
| **401 Unauthorized** | «Кто ты?» — не аутентифицирован | 403 — «я знаю, кто ты, но нельзя» |
| **403 Forbidden** | прав нет, и повтор не поможет | 401 — повтор с логином может помочь |
| 404 Not Found | ресурса нет (или скрываем его существование) | — |
| 405 Method Not Allowed | ресурс есть, метод не поддерживается | — |
| **409 Conflict** | конфликт состояния (версия, дубликат) | — |
| 422 Unprocessable | валидация семантики упала | 400 — кривое само сообщение |
| **429 Too Many Requests** | лимит; инструкция — `Retry-After` | — |
| 500 Internal | упало в приложении | — |
| **502 Bad Gateway** | ставит **посредник**: бэкенд недоступен/мусор ответил | 503 — «временно недоступен, попробуй позже» |
| 503 Service Unavailable | перегрузка/обслуживание | — |

**Зачем разнообразие (суть):** точный код = **машинночитаемая инструкция**. 429 → ретрай с паузой; 503 → ретрай позже; 401 → перелогин; 404 → не ретраить никогда. «Всё 200/500» отбирает у клиента и мониторинга возможность реагировать дифференцированно. Реестр — RFC 9110.

**Проект:** `ProductApi` — 201 на создание (+Location через `ResponseEntity.created`), 204 на удаление (`@ResponseStatus(NO_CONTENT)`), 404/400/500 — из `GlobalExceptionHandler`.

### 🧠 Каркас ответа
1. Пять классов одной строкой + «4xx — клиент виноват, 5xx — сервер».
2. 401 vs 403: *«кто ты?» против «я знаю, кто ты, но нельзя»*.
3. 400 vs 422: синтаксис против семантики.
4. Главный тезис: код = инструкция для ретраев/мониторинга; разнообразие — это контракт поведения при ошибках.
5. Проект: 201/204/404/400/500 и где они объявлены.

### ⚠️ Вероятные уточняющие
- **«Почему 502 доказывает, что код ставит не только приложение?»** — 502 генерирует шлюз/прокси, когда **твой** сервис недоступен: приложение могло быть мёртвым, а код клиенту выставил посредник.
- **«Что вернуть на создание?»** — 201 + `Location` на новый ресурс (у нас так: `ResponseEntity.created(selfLink.toUri())`).

## В3 ⭐. 201 Created, а поле `author` есть в БД, но его нет в JSON

> *Формулировка прошлого экзамена:* POST создаёт книгу. Сервер возвращает 201 с `Location` и телом, но поля `author` нет — оно есть в БД. Сервер не падал, логов нет. Причины? Минимум две, не связанные с бизнес-логикой.

### 🔄 Весь цикл по шагам

**Сценарий.** `POST /api/products {"name":"Евгений Онегин","author":"Пушкин"}` → 201. В БД `author` на месте, в JSON-ответе поля нет. Пройдём путь значения «author» от БД наружу и найдём точку, где оно исчезло.

1. БД: `SELECT` → `author = "Пушкин"` лежит. Потеря **не в хранении**.
2. Контроллер возвращает `EntityModel<ProductResponse>`. Наружу едет **НЕ entity, а DTO** (`ProductResponse` из контрактного модуля). Если в record **нет поля author** — Assembler физически не может его переписать: значение выброшено на этом шаге. Самая частая точка.
3. Поле в DTO есть, но маппинг/Assembler забыл скопировать → в DTO уже `null`.
4. У нас `@JsonInclude(NON_NULL)`: null-поля из JSON **выкидываются** при сериализации → клиент видит не `"author": null`, а отсутствие ключа → `undefined`. Вторая точка потери.
5. Третья — именование: naming strategy / `@JsonProperty` превращает `authorName` → `author_name`; ключ в JSON есть, но под другим именем → `reader.author == undefined`.

**Метод «поймай точку потери»:** `curl` → смотрим JSON → идём от сериализатора вглубь: тело ответа → DTO (поле есть? значение есть?) → маппер (копирует?) → entity (заполнили?) → БД. Где цепочка порвалась — там и чиним.

**Финал:** клиент видит **DTO+Jackson, а не таблицу**; между ними две стены — маппинг и сериализация, и на обеих поле теряется молча. Фикс аддитивный: поле в DTO + маппер — старым клиентам не мешает.

### 📚 Теория

Ключ: ответ собирается **не из БД**, а цепочкой **Entity → DTO → Jackson**, и на каждом шаге поле может потеряться **штатно**, без единого лога:

1. **Поля нет в Response DTO.** Сервер отвечает классом контракта (`BookResponse`), а не сущностью: контракт не обновили — поле из БД «не доезжает» до API. Сервер честен по контракту.
2. **`@JsonInclude(JsonInclude.Include.NON_NULL)` + null в DTO.** Класс помечен «null-поля не сериализовать» — если маппинг забыл проставить `author`, Jackson **молча выбросит** поле. Это его штатное поведение, не ошибка.
3. **Несовпадение имён:** `@JsonProperty` или `PropertyNamingStrategies` (SNAKE_CASE) — поле уехало под другим именем (`author_name`), выглядит как «пропало».
4. **Нет публичного геттера / `@JsonIgnore` / `transient`** — Jackson по умолчанию сериализует через геттеры; свойства для него «не существует».
5. **`@JsonView`/фильтры сериализации** — для этого эндпоинта используется view без этого поля.

**Почему ни ошибки, ни лога:** сериализация — слой **после** бизнес-логики; Jackson не считает пропуск поля проблемой (это конфигурация). Тихая деградация.

**Проект:** `ProductResponse` — `@Getter @Builder @JsonInclude(NON_NULL)` — пункты 1–2 применимы буквально: забыл поле в классе или не проставил в билдере → «в БД есть, в JSON нет».

**Как быстро найти (если спросят):** сериализовать DTO юнит-тестом и сравнить с OpenAPI-схемой; контрастный тест «что в entity, что в response»; логирование фактического JSON на тестовом контуре.

### 🧠 Каркас ответа
1. Главная мысль: *«ответ формирует не БД, а слой DTO+сериализация; искать надо в цепочке Entity → DTO → Jackson»*.
2. Причина 1: поле отсутствует в Response DTO (контракт не обновили).
3. Причина 2: `@JsonInclude(NON_NULL)` + null после маппинга — Jackson молча выкидывает.
4. Причина 3 (запас): naming strategy / нет геттера / @JsonIgnore.
5. Объяснить «почему тихо»: это конфигурация сериализации, не исключение.
6. Проект: наш `ProductResponse` с NON_NULL и билдером.

### ⚠️ Вероятные уточняющие
- **«Как предотвратить класс проблемы?»** — Контрактный тест: сериализованный DTO сверяется со схемой OpenAPI в CI; или генерация DTO из схемы.
- **«Почему Response — класс, а не record?»** — Наследование от `RepresentationModel` (HATEOAS-ссылки); record не наследуется.

## В4 ⭐. PUT затирает, PATCH игнорирует null. Клиент хочет обнулить поле — три подхода

> *Формулировка прошлого экзамена:* PUT требует все поля — отсутствующие затираются. PATCH меняет только переданное, null = «не трогай». Клиент хочет явно обнулить одно поле, не зная остальных. Три подхода на уровне контракта, сравнить по сложности и удобству.

### 🔄 Весь цикл по шагам

**Сценарий.** Состояние продукта `{name:"Колбаса", category:"Мясное"}`. Пользователь в форме **стёр категорию** и сохранил. Смотрим, что сделают PUT и наш PATCH.

1. **PUT-цикл:** клиент шлёт `PUT {"name":"Колбаса премиум"}` (забыл категорию) → семантика PUT: «вот НОВОЕ полное состояние, замени целиком» → `category = null` → категория **потеряна**. Это не баг, а семантика: PUT требует присылать всё; забыл поле — ты его обнулил.
2. **PATCH-цикл у нас:** `PatchProductRequest` договорилось: `null = «не трогать»`. Клиент шлёт `PATCH {"category": null}` wanting стереть → сервер считает «не трогать» → «Мясное» **осталось**. Противоположная неудача: пользователь думал, что стёр.
3. **Корень:** в JSON у поля **три** состояния (значение / null / отсутствует), в Java-объекте **два** (значение / null). «Стереть» и «не трогать» одновременно выразить нельзя — нужна договорённость.
4. **Решение 1 — RFC 7386 Merge Patch:** `{"category": null}` теперь официально значит «удали поле», «не трогать» = поле отсутствует в теле. Три состояния различимы; семантику применяет сервер.
5. **Решение 2 — RFC 6902 JSON Patch:** тело — список операций: `[{"op":"remove","path":"/category"}]` — «удалить» сказано отдельной явной командой; `Content-Type: application/json-patch+json`. Минус: шлём уже не данные, а скрипт правок.
6. **Решение 3 — своё:** данные + `reset:["category"]` (список полей к очистке), либо `JsonNullable` в DTO — undefined и null различимы на уровне типа.
7. **Бонус:** в GraphQL (`PatchProductInput`) проблема решена самим языком: absent ≠ explicit null — обнулить категорию можно штатно.

**Финал:** PUT — полное замещение; PATCH обязан **договориться**, что значат null и отсутствие. У нас договорено «null = не трогать», поэтому очистка невозможна — осознанный компромисс, который мы умеем назвать и защитить.

### 📚 Теория

**Корень проблемы:** в JSON «поле отсутствует» и «поле = null» — разные вещи. Но при десериализации в Java-объект (record с nullable-полями) **различие теряется — оба дают null**. PATCH с семантикой «null = не трогать» физически не может отличить «не прислал» от «прислал null, обнули». Вся задача = восстановить различие на уровне контракта.

**Подход 1 — JSON Merge Patch (RFC 7386).** Стандартная семантика: **члена нет = «не менять»; член есть со значением null = «очистить»; есть со значением = «заменить»**.
```json
PATCH /books/5  Content-Type: application/merge-patch+json
{ "bio": null, "title": "Новое" }     // bio очистить, title заменить
```
Клиенту — максимально просто (обычный JSON). Серверу — сложнее: дефолтный биндинг в record стирает различие → нужен `JsonNullable<String>` (обёртка с тремя состояниями absent/null/value), разбор в `JsonNode` или кастомный десериализатор.

**Подход 2 — JSON Patch (RFC 6902).** Тело — **массив явных операций**: `add/replace/remove/test/copy/move` над JSON-Pointer'ами.
```json
[{"op": "replace", "path": "/bio", "value": null},
 {"op": "test", "path": "/state", "value": "draft"}]
```
Намерение выражено явно (неоднозначности нет в принципе), набор применяется атомарно, есть библиотеки и свой content-type. Клиенту тяжелее: строить операции и пути, для «поменять одно поле» громоздко.

**Подход 3 — собственное соглашение.** Например, поле-список сброса: `{"title": "...", "reset": ["bio"]}`. Реализовать тривиально, но: свой нестандартный формат, своя валидация (поле из `reset` не должно приходить со значением), кодогенераторы клиентов не поймут, вся документация на тебе.

**Сравнение** (уметь рисовать по памяти):

| | Merge Patch | JSON Patch | Своё |
|---|---|---|---|
| Стандарт | RFC 7386 | RFC 6902 | нет |
| Просто клиенту | +++ | + | ++ |
| Просто серверу | + (JsonNullable) | ++ (библиотеки) | +++ |
| Атомарность | да | да | да |
| Выразительность | поля | поля+массивы+test | что придумаешь |

**Проект:** `PatchProductRequest` — все поля nullable, `patch()` в `ProductService` = «null → оставить старое». **Честно назвать:** обнулить категорию сейчас нельзя — для этого нужен Merge Patch или JSON Patch.

**Бонус-пункт (производит впечатление):** в GraphQL-части проекта различие есть **из коробки** — `PatchProductInput` отличает отсутствующий аргумент от переданного null, поэтому «обнулить категорию» мутацией `patchProduct` можно. Проблема — чисто REST/Jackson'овская.

### 🧠 Каркас ответа
1. Корень: *«JSON различает «отсутствует» и «null», Java после десериализации — нет; PATCH с «null = не трогать» не может обнулить»*.
2. Три подхода с названиями стандартов (7386, 6902) и семантикой каждого.
3. Таблица сравнения «клиент/сервер/стандарт/выразительность».
4. Вывод: для простых клиентов — Merge Patch; для протокольных правок — JSON Patch; своё — только под контролем.
5. Проект: наша PATCH-семантика + признание ограничения + «а в GraphQL у нас различимо».

### ⚠️ Вероятные уточняющие
- **«Почему серверу Merge Patch сложнее?»** — Нужен `JsonNullable`/JsonNode-парсинг: дефолтный Jackson в record теряет absent.
- **«PATCH идемпотентен?»** — Метод не гарантирует (RFC 5789); абсолютный патч («set name=X») — идемпотентен, дельта («+5») — нет. Наш — абсолютный.
- **«Что такое JsonNullable?»** — Обёртка с тремя состояниями (ABSENT/NULL/VALUE) из OpenAPI-генератора, сериализуется «absent → поля нет».
- **«Для обнуления обязательно JsonNullable?»** — Разделяй уровни: PUT обнуляет и так (нет поля = нет в состоянии, семантика замещения — ничего в DTO не нужно). Для PATCH JsonNullable — лишь **механизм** реализации семантики **RFC 7386** (контракт: null=стереть, absent=не трогать); альтернативы: принять `JsonNode` и разобрать дерево, RFC 6902 (`op:remove` — команда вместо обёрток), своё `reset:[]`. В GraphQL не нужно: absent ≠ null на уровне схемы.

## В5 ⭐. Bean Validation: переименовали `isbn` → `productIdentifier`. Кто сломается?

> *Формулировка прошлого экзамена:* Валидация через @NotBlank/@Size/@Email, @Valid запускает, при провале 400 со списком ошибок полей. Клиент показывает «Поле isbn: некорректный ISBN». Что произойдёт при переименовании? Кто сломается — клиент, сервер или оба? Что изменить в трёх местах и в каком порядке?

### 📚 Теория — весь цикл по шагам

**Вопрос по-человечески.** Есть веб-форма «Добавить продукт». Пользователь оставил поле пустым → сервер отвечает 400 со списком ошибок, форма рисует красные подсказки под полями. Экзаменационная ситуация: серверная команда переименовала поле `isbn` → `productIdentifier` (в DTO и в валидации). Спрашивают: **кто сломается** — сервер, клиент или оба — и **как переименовывать правильно**.

**Действующие лица в программе (4 участника):**
1. **DTO с аннотациями** — контрактный модуль: record, на полях `@NotBlank(message=...)`, `@Size(max=...)`; тексты ошибок придуманы на сервере и уезжают наружу (видны даже в Swagger/OpenAPI).
2. **`@Valid`** — стоит на параметре контроллера (`createProduct(@Valid @RequestBody ProductRequest)`): «перед вызовом метода прогони тело запроса через Bean Validation».
3. **`GlobalExceptionHandler`** (`@ControllerAdvice`) — ловит `MethodArgumentNotValidException` и собирает 400 + `fieldErrors: [{field, rejectedValue, message}]`.
4. **Фронтенд** — после 400 ищет инпут формы по `fieldErrors[].field` и показывает под ним `message`.

**Нормальный цикл — по шагам.** Пользователь нажал «Сохранить» с пустым ISBN:
1. Браузер шлёт `POST /api/products` с телом `{"isbn": "", "name": "Колбаса"}`.
2. Jackson превращает JSON в объект `ProductRequest`. Наш код ещё **ни разу не выполнялся**.
3. `@Valid` запускает валидатор **до входа в контроллер**: `@NotBlank` на `isbn` падает → Spring бросает `MethodArgumentNotValidException`. **Тело контроллера не выполняется вообще** — до бизнес-логики дело не дошло.
4. `GlobalExceptionHandler` перехватывает исключение и собирает ответ:
   `{"status":400, "type":".../validation-error", "detail":"isbn: ISBN не может быть пустым", "fieldErrors":[{"field":"isbn","rejectedValue":"","message":"ISBN не может быть пустым"}]}`
5. Фронтенд: для каждой ошибки `form.querySelector('input[name="' + e.field + '"]')` → показать `e.message`. Совпадение **строковое**: `"isbn" == "isbn"`. Пользователь видит подсказку, исправляет — цикл замкнулся.

**Где мина.** Три имени поля связаны **неявным соглашением**: имя поля в DTO = `field` в ошибке = `name` инпута формы. Оно нигде не зафиксировано и никем не проверяется: ни компилятором (клиент и сервер — разные репозитории), ни OpenAPI (описан формат ошибки, но не «матчить по field»), ни тестами.

**Переименование «одним коммитом» — что произойдёт.** Сервер переименовал `isbn` → `productIdentifier` в DTO, перетащил аннотации, поправил тексты; серверные тесты зелёные, Swagger красивый. Тот же цикл со старым клиентом:
1. Клиент шлёт `{"isbn": ""}` — поля `isbn` в DTO больше нет → Jackson **молча игнорирует** неизвестное поле, `productIdentifier = null`.
2. `@NotBlank` на `productIdentifier` падает.
3. В ответе теперь `field: "productIdentifier"`.
4. Фронт ищет инпут `name="productIdentifier"` — такого нет → подсказка **тихо не показывается**. Ни исключения, ни лога. QA гоняет happy path — баг живёт месяцами.

**Кто сломался:** сервер — нет (честно валидирует новое имя, в ошибках — новое имя); **клиент — да, и молча**, потому что зацеплен строковым совпадением имён. Если переименовано и поле запроса — старый клиент шлёт `isbn`, получает 400 «productIdentifier: не должно быть пустым» и **не может понять, что чинить** (на форме такого поля нет). Заодно слетают SDK, сгенерированные из OpenAPI, контрактные тесты, дашборды — всё, зацепленное за имена. Сломалось неявное соглашение: «имя поля в ошибке = имя поля формы = имя поля запроса».

**Правильная миграция — цикл «аддитивность → депрекация → удаление», три шага:**
1. **Аддитивный шаг (ничего не ломает):** в `FieldError` добавить машиночитаемый **`code`** (`"REQUIRED"`, `"ISBN_INVALID"`) — стабильный якорь, не зависящий от имён; в DTO добавить `productIdentifier`, **оставив** `isbn` deprecated-алиасом: сервер принимает оба, валидирует оба, в ошибке отдаёт новое имя + код. Старые клиенты работают как работали.
2. **Перевод клиентов:** каждый в своём темпе переходит на `code` при показе ошибок и на `productIdentifier` при отправке. Метрика считает, кто ещё шлёт `isbn`.
3. **Удаление** `isbn` после объявленного окна депрекации (например, квартал) — формально ломающее, но пользователей уже нет.

Анти-паттерн: «переименуем разом, клиенты догонят» = гарантированная молчаливая поломка всех. **Финал:** клиенты должны зацепляться за стабильные коды, а не за имена полей — имена для людей, коды для машин.

**Проект:** ISBN у нас нет, но механика один в один: `ProductRequest(name: @NotBlank(message="Название продукта не может быть пустым"), @Size(max=200))` в контрактном модуле → `ProductApi.createProduct(@Valid @RequestBody ProductRequest)` → `GlobalExceptionHandler.handleValidation` → `new FieldError(fe.getField(), fe.getRejectedValue(), fe.getDefaultMessage())` → 400. В нашем `FieldError(field, rejectedValue, message)` **поля `code` нет** — «добавил бы `code`» — готовый ответ на «как бы ты улучшил проект».

### 🧠 Каркас ответа
1. Цепочка валидации в двух предложениях (DTO-аннотации → @Valid → ControllerAdvice → fieldErrors).
2. Ответ на «кто»: *«сервер нет, клиент — да, и молча, потому что маппит по строковому совпадению имён»*.
3. Три места изменений.
4. Три шага: код ошибки + алиас → перевод клиентов в своём темпе → удаление после окна.
5. Обобщение: *«клиенты должны зацепляться за стабильные коды, а не за имена полей»*.
6. Проект: наш FieldError без code — и как я бы его дополнил.

### ⚠️ Вероятные уточняющие
- **«Логика на кодах — а как клиент поймёт, В КАКОМ поле ошибка?»** — Код **не заменяет `field`, а добавляется рядом**: в `FieldError` остаются оба. `field` — ответ на «куда показать» (клиент подсвечивает инпут по имени из `field`; если такого инпута нет — фолбэк: ошибка в общий блок формы, не теряется). `code` — ответ на «что случилось»: по нему клиент выбирает текст/поведение (`TEXTS["REQUIRED"]`), вместо сравнения имён `if (field == "isbn")`. При переименовании ломается только позиционирование подсказки — и то видимо (фолбэк), а не молча; логика выживает. `message` — только для человека, машины его не парсят. Гигиена: новые коды добавлять можно (аддитивно), клиент обязан дефолтить незнакомый код (`?? e.message`). Параллель: RFC 7807 — машины читают `type`/`status`, люди `title`/`detail`.
- **«Почему молчаливая?»** — Ошибки валидации — редкий путь в UI; подсказка просто перестаёт появляться, без исключений и логов.
- **«Что такое окно депрекации?»** — Объявленный период (например, квартал), в котором сервер поддерживает оба варианта; клиенты успевают переехать; после — удаление.
- **«А если клиент не наш?»** — Тем более: поддержка обоих полей + уведомление + метрика использования старого поля (считаем, кто ещё шлёт `isbn`).
