# Пишем контракт руками: REST, GraphQL, gRPC, события

**Что значит «реализовать контракт» в каждом мире** — одна таблица, с неё начни ответ:

| Мир | Контракт — это | Файл(ы) | Кто проверяет |
|---|---|---|---|
| REST | Java-типы: DTO + интерфейс эндпоинтов + ошибки | `XxxRequest/Response.java`, `XxxApi.java`, `ErrorResponse.java` | javac + Spring MVC + Bean Validation |
| GraphQL | SDL-схема: `type`, `input`, `Query`, `Mutation` | `schema.graphqls` | валидация запроса по схеме |
| gRPC | `.proto`: message + service | `book.proto` | protoc + совместимость по номерам полей |
| События | sealed-иерархия + конверт + routing keys | `XxxEvent.java`, `EventEnvelope`, `RoutingKeys` | exhaustive switch |

## Часть 1. REST (главный кандидат)

### Алгоритм из 7 шагов (работает для ЛЮБОЙ сущности)

Дана сущность «Книга» (id, title, author, year, isbn). Пишем:

**Шаг 1. Ресурсы и глаголы — таблица в голове (30 секунд):**

| Операция | Метод + путь | Успех | Ошибки |
|---|---|---|---|
| список | `GET /api/books?page&size` | 200 | — |
| одна | `GET /api/books/{id}` | 200 | 404 |
| создать | `POST /api/books` | **201 + Location** | 400 |
| заменить | `PUT /api/books/{id}` | 200 | 404, 400 |
| патч | `PATCH /api/books/{id}` | 200 | 404, 400 |
| удалить | `DELETE /api/books/{id}` | **204** | 404 |

**Шаг 2. Request-DTO с валидацией:**
```java
public record BookRequest(
        @NotBlank(message = "Название не может быть пустым")
        @Size(max = 200, message = "Название не может превышать 200 символов")
        String title,

        @NotBlank(message = "Автор обязателен")
        String author,

        @Min(value = 0, message = "Год не может быть отрицательным")
        Integer year
) {}
```

**Шаг 3. Response-DTO:**
```java
public record BookResponse(Long id, String title, String author, Integer year) {}
```
(в проекте он extends RepresentationModel<BookResponse> для HATEOAS `_links` — если спросят «а ссылки?», добавляешь это и Assembler.)

**Шаг 4. Patch-DTO с договорённостью** (null = «не трогать»):
```java
public record PatchBookRequest(String title, String author, Integer year) {}
```
Знаешь продвинутое — скажи: «строгая версия — JsonNullable/7386, чтобы различать "не трогать" и "стереть"; здесь выбран компромисс null=не трогать».

**Шаг 5. Интерфейс контракта** (эндпоинты + OpenAPI + @Valid):
```java
@Tag(name = "Books")
@RequestMapping(value = "/api/books", produces = MediaType.APPLICATION_JSON_VALUE)
public interface BookApi {

    @Operation(summary = "Получить книгу")
    @ApiResponse(responseCode = "404", content =
        @Content(schema = @Schema(implementation = ErrorResponse.class)))
    @GetMapping("/{id}")
    BookResponse getBook(@PathVariable Long id);

    @Operation(summary = "Создать книгу")
    @PostMapping(consumes = MediaType.APPLICATION_JSON_VALUE)
    @ResponseStatus(HttpStatus.CREATED)
    ResponseEntity<BookResponse> createBook(@Valid @RequestBody BookRequest request);

    @DeleteMapping("/{id}")
    @ResponseStatus(HttpStatus.NO_CONTENT)
    void deleteBook(@PathVariable Long id);
    // ... PUT/PATCH/GET-список по той же схеме
}
```
Ключевые детали, которые проверяют: **@Valid на параметре** · **201 у POST** (и `Location` в реализации) · **204 у DELETE** · **404/400 задокументированы ErrorResponse'ом** · `consumes/produces`.

**Шаг 6. Ошибки — единый формат (RFC 7807):**
```java
public record ErrorResponse(int status, String type, String title,
                            String detail, String instance,
                            List<FieldError> fieldErrors) {
    public record FieldError(String field, Object rejectedValue, String message) {}
}
```
```java
@ControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(MethodArgumentNotValidException.class)   // 400 + fieldErrors
    @ExceptionHandler(ResourceNotFoundException.class)          // 404
    @ExceptionHandler(Exception.class)                          // 500 — «непредвиденное»
}
```

**Шаг 7. Реализация — контроллер implements интерфейс:**
```java
@RestController
public class BookController implements BookApi {
    private final BookService service;   // in-memory Map достаточно

    @Override
    public ResponseEntity<BookResponse> createBook(@Valid BookRequest req) {
        BookResponse created = service.create(req);
        return ResponseEntity
                .created(URI.create("/api/books/" + created.id()))   // 201 + Location
                .body(created);
    }

    @Override
    public void deleteBook(Long id) {
        if (!service.delete(id)) throw new ResourceNotFoundException("Book " + id + " not found");
    }
}
```

### «От руки за 5 минут» — минимальный состав
Если на комиссии ручка и бумага, полный набор — это **5 кусков**: (1) BookRequest с аннотациями, (2) BookResponse, (3) BookApi с @Valid/@ResponseStatus, (4) ErrorResponse, (5) совет про 201/204/404 словами. HATEOAS-ссылки и пагинацию упомяни устно: «в проекте — RepresentationModel + Assembler + PagedModel, на бумаге опускаю для краткости».

### Фразы-усилители при защите
- «Контракт-первый: интерфейс в отдельном модуле, реализация его implements — javac не даст разойтись» (В9).
- «Валидация объявлена на контракте, поэтому любое потребление получает ту же проверку» (В5).
- «Ошибки — единым форматом RFC 7807 через @ControllerAdvice, клиенты парсят тело, а не транспорт» (В1).
- «PUT — полное замещение, PATCH — дельта с договорённостью null=не трогать» (В4).

## Часть 2. GraphQL (SDL-схема)

### Рецепт: 5 блоков файла `schema.graphqls`

```graphql
type Book {              # 1. Тип-читаемая модель
    id: ID!
    title: String!
    author: String!
    year: Int
}

input CreateBookInput {  # 2. Входы мутаций (отдельный input!)
    title: String!
    author: String!
    year: Int
}

input PatchBookInput {   # 3. Патч: absent ≠ null на уровне схемы
    title: String
    author: String
}

enum SortOrder { ASC DESC }   # перечисления — редко, но спросят

type Query {             # 4. Чтение — ВСЕГДА в Query
    book(id: ID!): Book
    books(first: Int = 20, order: SortOrder = ASC): [Book!]!
}

type Mutation {          # 5. Запись — ВСЕГДА в Mutation
    createBook(input: CreateBookInput!): Book!
    patchBook(id: ID!, input: PatchBookInput!): Book
    deleteBook(id: ID!): Boolean!
}
```

**Правила, за которые цепляют:**
- `!` = non-null: `[Book!]!` — список не null и элементов не null; читается «изнутри наружу».
- Входы — только `input`, типы-модели в аргументах использовать нельзя.
- Subscription, если спросят: `type Subscription { bookEvents: BookEvent! }` — пуш по WS.
- Пагинация — по-взрослому через connection/edge/pageInfo (скажи словами).

### Реализация на DGS (Java 21):
```java
@DgsComponent
public class BookDataFetcher {
    @DgsQuery public Book book(@InputArgument Long id) {
        return repo.findById(id).orElseThrow(() -> new GraphQLError("not found"));
    }
    @DgsMutation public Book createBook(@InputArgument CreateBookInput input) {
        return repo.create(input.title(), input.author());
    }
}
```
- Ошибки: **всегда HTTP 200 + поле `errors`** (TypedGraphQLError) — не путать с REST-обработчиком.
- Защита: `MaxQueryDepth` + `MaxQueryComplexity` — упомяни сам (В11).
- N+1: если в типе есть связь (`books { author }` с отдельным резолвером) — назови DataLoader (В12).

## Часть 3. gRPC / Protobuf (`.proto`)

### Рецепт: файл `book.proto`

```protobuf
syntax = "proto3";              // 1. ВСЕГДА первая строка
package books.v1;               // 2. пакет = пространство имён

option java_package = "ru.books.v1";
option java_multiple_files = true;

message Book {                  // 3. сообщение; У КАЖДОГО ПОЛЯ НОМЕР
    int64 id = 1;
    string title = 2;
    string author = 3;
    int32 year = 4;
    reserved 9, 10;             // 5. удалённые поля — навсегда заняты
    reserved "old_title";
}

message GetBookRequest  { int64 id = 1; }
message ListBooksRequest { int32 page_size = 1; string page_token = 2; }
message ListBooksResponse { repeated Book books = 1; string next_page_token = 2; }

service BookService {           // 4. сервис = набор RPC
    rpc GetBook (GetBookRequest) returns (Book);
    rpc CreateBook (Book) returns (Book);
    rpc ListBooks (ListBooksRequest) returns (stream Book);  // server streaming
}
```

**Правила письма (то, что реально проверяют):**
1. **Номера полей никогда не меняются и не переиспользуются** — удалённое → `reserved` (и номер, и имя).
2. Новое поле = **новый номер** → совместимо в обе стороны (старый клиент пропустит, новый у старых данных прочитает дефолт).
3. Не менять wire type: int32→string = падение парсера; int32→int64/bool = тихий мусор.
4. `repeated` = список; `map<k,v>` есть; `optional` — различить «не задано» от дефолта.
5. 4 типа вызовов: unary / server-stream / client-stream / bidi (`stream` с обеих сторон).

### Реализация (после protoc генерятся классы):
```java
public class BookServiceGrpcImpl extends BookServiceGrpc.BookServiceImplBase {
    @Override
    public void getBook(GetBookRequest req, StreamObserver<Book> response) {
        response.onNext(book);
        response.onCompleted();
    }
}
```
Плюс фразы: HTTP/2 + бинарный wire (varint/length-delimited), коды ошибок `NOT_FOUND`/`INVALID_ARGUMENT` вместо статусов, gRPC внутрь кластера / REST наружу.

## Часть 4. Контракт событий

### Рецепт: три куска

```java
// 1. Иерархия событий: sealed + record = тип и payload вместе
public sealed interface BookEvent permits BookEvent.Created, BookEvent.Updated, BookEvent.Deleted {
    record Created(Long id, String title, String author) implements BookEvent {}
    record Updated(Long id, String title, String author) implements BookEvent {}
    record Deleted(Long id) implements BookEvent {}          // payload минимальный
}

// 2. Конверт: метаданные отдельно от payload
public record EventEnvelope(Metadata metadata, Object payload) {
    public record Metadata(String eventId, Instant occurredAt, String source, String routingKey) {}
    public static EventEnvelope wrap(Object payload, String source, String routingKey) { ... }
}

// 3. Routing keys: константы, точка = иерархия
public final class RoutingKeys {
    public static final String EXCHANGE = "books.events";
    public static final String BOOK_CREATED = "book.created";
    public static final String BOOK_DELETED  = "book.deleted";
    private RoutingKeys() {}
}
```

**Что сказать при защите:** eventId — ключ дедупликации (at-least-once!) · routing key `book.created` ловится топик-паттернами `book.*`/`book.#` · консюмер — exhaustive switch без default (В19) · доставка: confirms/durable/manual-ack (В20) · запись события и бизнес-данных — через outbox (В18).

## Чек-лист самопроверки (пробежаться по контракту перед сдачей)

- [ ] Пути — существительные во множественном числе, глаголов в URL нет
- [ ] POST → 201 (+Location), DELETE → 204, не найдено → 404, валидация → 400
- [ ] @Valid на всех @RequestBody; аннотации на полях DTO
- [ ] Ошибки одним форматом (ErrorResponse), а не произвольными строками
- [ ] PATCH-DTO: договорённость про null названа словами
- [ ] GraphQL: входы через input; Query/Mutation не перепутаны
- [ ] proto: номера полей уникальны; reserved после удалений; syntax/proto3 указан
- [ ] События: у каждого варианта свой payload; eventId в конверте

## Если спросят «contract-first или code-first?»
Наш путь — **contract-first по духу**: контракт (интерфейс/DTO/схема) живёт отдельным артефактом, реализация ему подчинена, документация генерится из него (OpenAPI — из аннотаций, Java — из .proto, типы DGS — из SDL). Разница миров только в том, где физически лежит «первоисточник».
