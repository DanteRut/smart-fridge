## В10 ⭐. Зачем `variables`, если значения можно захардкодить в строку query?

> *Формулировка прошлого экзамена:* GraphQL-запрос передаётся в JSON-теле `{"query": "...", "variables": {...}}`. Зачем поле variables? Все значения можно вшить в query. Назовите техническую причину — не связанную с читаемостью.

### 🔄 Весь цикл по шагам

**Сценарий.** Один и тот же запрос «продукт по id» двумя способами — с захардкоженным значением и с variables.

1. **Без variables:** текст запроса собирается конкатенацией: `'query { product(id: "' + id + '") { name } }'`. Для id=7 и id=8 — **две разные строки**. Следствия: сервер парсит каждую заново (парсинг недешёв); кэш по тексту запроса бесполезен; кавычки/эскейпинг — поле для инъекций; APQ невозможен.
2. **С variables:** текст запроса — **константа**: `query Product($id: ID!) { product(id: $id) { name } }` + отдельно `variables: {"id":"7"}`.
3. Сервер парсит один раз; тот же текст с другими variables переиспользуется — аналог **prepared statements** в SQL.
4. **APQ (Automatic Persisted Queries):** клиент первый раз шлёт текст + hash, дальше — только hash + variables: минус трафик, минус фаза парсинга.
5. **Типобезопасность:** `$id` объявлен `ID!` — не тот тип сервер отвергнет **до исполнения**, на валидации по схеме. Конкатенация так не умеет.
6. Бонус: клиентский кэш строится по ключу (запрос, variables) — так работают нормализованные кэши Apollo/Relay.

**Финал:** запрос — это скомпилированная программа, variables — её аргументы; разделив код и данные, получаем кэш parse, APQ и отбраковку мусора до исполнения.

### 📚 Теория

**Главная техническая причина: variables делают текст запроса константой.** А константу можно кэшировать и идентифицировать:

1. **Кэш parse+validate на сервере (аналог prepared statements).** Исполнение GraphQL = разбор (parse) → валидация по схеме → план → резолверы. Первые два шага **дорогие**. Если текст запроса постоянен, сервер делает parse+validate **один раз**, кэширует скомпилированное представление и исполняет его многократно с разными variables. Точная аналогия — **prepared statements в SQL**: один план, много наборов параметров.
2. **Persisted Queries.** Клиент шлёт вообще **хэш** запроса из белого списка вместо текста. Возможно **только** потому, что текст постоянен — иначе хэш не идентифицировал бы запрос. Эффекты: минус трафик (хэш меньше запроса), плюс безопасность — произвольные запросы блокируются полностью.
3. **Типобезопасная сериализация значений.** Переменные едут отдельно, типизировано по схеме (`$userId: ID!`): не надо строить строку запроса конкатенацией; нет проблем экранирования кавычек/переносов внутри JSON-строки `query`; нет «GraphQL-инъекций» — подставленный в строку текст мог бы **изменить структуру запроса**, а через variables это просто значение объявленного типа.

**Проект:** в `application.properties` включён introspection; persisted queries мы не настраивали — назвать как улучшение для продакшена.

### 🧠 Каркас ответа
1. Ключ: *«variables превращают query в константу»*.
2. Причина 1: кэш parse+validate — prepared statement-аналогия.
3. Причина 2: persisted queries — клиент шлёт хэш из белого списка (заодно безопасность).
4. Причина 3: типобезопасная передача — без конкатенации, экранирования и инъекций структуры.
5. Связка: №2 — развитие №1.

### ⚠️ Вероятные уточняющие
- **«Почему конкатенация — это плохо?»** — Экранирование строк в строке (query — JSON-строка внутри JSON), риск изменить структуру запроса (инъекция), потеря типизации.
- **«Как variables живут у клиента?»** — Переиспользование одного запроса с разными параметрами (детали экрана, пагинация) — запрос хранится как артефакт.

## В11 ⭐. Depth 5 из 20 — сервер всё равно лёг. Почему глубина бессильна?

> *Формулировка прошлого экзамена:* Сервер отклоняет запрос: maximum query depth exceeded 24 > 20. Разработчик сократил запрос до 5 уровней — приняли. Но запрос всё равно положил сервер на 20 секунд. Как при 5 уровнях возможна такая нагрузка? Почему «глубина» как единственная метрика бессильна?

### 🔄 Весь цикл по шагам

**Сценарий.** Стоит `MaxQueryDepth(20)`. Атакующий шлёт запрос глубиной 5 — и кладёт сервер. Смотрим цикл атаки и защиты.

1. Зачем depth вообще: без него `query { products { items { product { items { ... }}}} }` — рекурсия по связи продукт↔единицы — уложит сервер бесконечной вложенностью. Лимит резонный.
2. **Обход №1 — ширина:** глубина 5, зато `products(first: 100000) { name items(first: 100000) { quantity } }` — depth-лимит молчит, а серверу обещаны сотни тысяч объектов на сборку и сериализацию.
3. **Обход №2 — алиасы:** `{ a: products {...} b: products {...} ... 200 раз }` — глубина та же одна и та же, работы в 200 раз больше: depth повторов **не видит**.
4. **Обход №3 — дорогое поле:** одно поле `report` — тяжёлый агрегат по всем складам; depth=1, а это самый дорогой вызов в системе.
5. **Ответ — вторая метрика:** `MaxQueryComplexity(200)`: вес по умолчанию 1 за поле; `first:100000` **умножает** стоимость ветки (пагинация участвует в цене); алиасы суммируются; дорогим полям вес повышаем вручную. Отклонение — на валидации, до резолверов: данных даже не коснулись.
6. **Остаточная честность:** complexity тоже мерит **форму**, а не время исполнения: форма дешёвая, а резолвер тормозит → дальше спасают таймауты, кэш и серверный потолок пагинации.

**Финал:** depth считает вглубь и слеп к ширине и повторам; complexity мерит «сколько полей и по чём», но не время исполнения. Поэтому метрик минимум две, и это нижняя планка защиты.

### 📚 Теория

**Глубина меряет вертикаль документа, а нагрузку создают данные и резолверы.** Четыре способа уложить сервер при глубине 5:

1. **Огромные списки:** `products(first: 100000) { name }` — глубина 2, а резолвер тянет сотни тысяч записей.
2. **Дорогие резолверы:** поле, за которым поход в ML-сервис/агрегацию/полнотекстовый поиск — «один уровень», стоит секунды.
3. **Алиасы:** `a: book(id:"1") b: book(id:"2") … z: book(id:"26")` — 26 подзапросов **на одном уровне**: глубина не растёт, стоимость растёт линейно.
4. **Introspection:** выгрузка всей схемы `__schema { types { fields { ... } } }` — неглубоко, тяжело.

**Почему depth как единственная метрика бессильна:** она считает **структуру** (сколько вложений), игнорируя ширину, размеры списков, стоимость полей. Это как ограничить высоту файла, не ограничив его ширину.

**Правильная защита — Query Cost / Complexity Analysis (лекция называет прямо):** каждому полю назначается **вес**; спискам — множитель по запрошенному лимиту (`first`/`last`); суммарная стоимость считается **до исполнения**; cost > threshold → отказ. Плюс: жёсткие ограничения пагинации, таймауты исполнения, в проде — отключённый introspection и/или persisted queries.

**Проект (`GraphQLSecurityConfig`):** `MaxQueryDepthInstrumentation(20)` + `MaxQueryComplexityInstrumentation(200)`. Комментарий из собственного кода — аргумент: *«по умолчанию каждое запрашиваемое поле весит 1 единицу»* — дефолтный complexity считает **количество полей**, а не стоимость: наш `items` на продукте (поход в сервис) весит столько же, сколько `name`. Для реальной защиты нужны кастомные веса полей.

### 🧠 Каркас ответа
1. Тезис: *«глубина меряет форму документа, стоимость создают данные и резолверы»*.
2. Четыре способа при глубине 5 (списки, дорогие поля, алиасы, introspection) — с примерами.
3. Вывод: нужна cost-метрика — веса полей, множители списков, порог; + лимиты пагинации и таймауты.
4. Проект: два Instrumentation-бина и слабость дефолта «1 за поле».

### ⚠️ Вероятные уточняющие
- **«Как назначать веса?»** — По стоимости резолвера: скаляр из кэша ≈ 1; поле с походом в БД ≈ 5–10; поле с походом во внешний сервис ≈ 20–50; спискам — вес × запрошенный лимит.
- **«Depth вообще зачем тогда?»** — Он дёшев и убивает тривиальную рекурсию `user→posts→author→posts→…`; как единственная метрика — insufficient, как часть набора — полезен.

## В12 ⭐. Легитимный GraphQL-запрос → 7 запросов к БД; REST обошёлся двумя

> *Формулировка прошлого экзамена:* Клиент запрашивает `{ book(id:"1") { title author { books { content { title } } } } }`. Запрос легитимный, проверки прошёл, но в логах backend — 7 запросов к БД. В REST тот же набор данных — 2 запроса. Почему в GraphQL их больше? Как называется?

### 🔄 Весь цикл по шагам

**Сценарий.** Легитимный `query { products { name category items { quantity } } }` порождает 7 вызовов к БД, а REST на том же экране — 2. Разбираем по шагам, откуда берётся 7.

1. Исполнение DGS идёт **деревом вызовов**: резолвер на каждый узел запроса.
2. `productsDataFetcher` → **1** вызов (список продуктов).
3. DGS спускается к детям: для **каждого** продукта зовутся резолверы `category` (+1) и `items` (+1). Мелкий набор из тикета: 4 продукта → +4 на items → итого **7 = 1 + 1×категории + 4**. Классический N+1, развёрнутый в дерево.
4. Почему так вышло: форму запроса выбрал клиент, и каждый узел формы = вызов резолвера = отдельное обращение к БД. Гибкость формы оплачена размножением вызовов.
5. REST на том же экране — **2 запроса**, потому что форму экрана собрали **заранее на бэке**: `/api/products?include=items` (или специализированный ответ) = один SELECT с JOIN.
6. **Лечение — DataLoader:** пока DGS обходит дерево, DataLoader копит ключи `product_id` всех запросивших полей и за один «тик» делает батч: `SELECT ... WHERE product_id IN (...)` → строит карту id→items → раздат резолверам. 7 → 2.
7. **В проекте:** `ProductItemsDataFetcher` — живой N+1 (на 50 продуктах — 51 вызов); DataLoader не заведён. «Как бы сделал»: batchloader по productIds + замер 51→2.

**Финал:** GraphQL перенёс сборку формы с бэка на момент запроса — гибко, но вызовы размножаются деревом; DataLoader — стандартная заплатка батчингом, цена — усложнение кода и ручное управление батч-кэшами.

### 📚 Теория

**Название: N+1 проблема (вложенный N+1).**

**Механика:** GraphQL исполняет **резолвер на каждое поле каждого объекта**: `book` → 1; `author` → 1; `books` автора → 1; `content` → по одному **на каждую книгу автора** (N). Каждый резолвер независим, сам ходит за данными, и GraphQL по умолчанию **ничего не батчит**. 1+1+1+4 = 7.

**Почему REST двумя:** REST-эндпоинты проектировались под конкретные экраны — внутри JOIN'ы, пакетные выборки, агрегация «books+author одним запросом». GraphQL отдал клиенту право собирать форму — и вместе с ним потерял контроль над числом походов за данными. Универсальная формула: *«N+1 возникает везде, где на каждый элемент списка делается отдельный запрос»* — у REST она бывает на уровне HTTP-клиента, у GraphQL — на уровне резолверов.

**Лечение — DataLoader (batch loading):** резолвер **не ходит за данными**, а кладёт ключ в очередь; когда уровень разобран, DataLoader одним пакетным запросом (`WHERE id IN (...)`) грузит всё сразу + кэширует на время запроса (request-scoped cache — повторный ключ в том же запросе не грузится снова).

```java
@DgsDataLoader(name = "directors")
public class DirectorsDataLoader implements BatchLoader<String, Director> {
    public CompletionStage<List<Director>> load(List<String> ids) {
        return CompletableFuture.supplyAsync(() -> directorService.findByIds(ids));
    }
}
// резолвер поля: return dfe.getDataLoader("directors").load(show.directorId());
```
1+N вызовов → 1+1.

**Проект (сильнейший ход):** `ProductItemsDataFetcher` — `@DgsData(parentType="Product", field="items")` — ходит в `FridgeItemService` **на каждый продукт**: `products { items { id } }` при 50 продуктах = 51 вызов. Это наш живой N+1; DataLoader не реализован — назвать как точку роста (`@DgsDataLoader` по productId + `findByIds`).

### 🧠 Каркас ответа
1. Название: N+1 (вложенный).
2. Механика: *«резолвер на каждое поле каждого объекта; по умолчанию без батчей»* + подсчёт до семи на примере из вопроса.
3. Почему REST двумя: эндпоинты проектировались под выборки (JOIN), GraphQL отдал форму клиенту и потерял контроль.
4. Лечение: DataLoader — очередь ключей → один batch-запрос → плюс request-кэш.
5. Проект: наш ProductItemsDataFetcher — честно показать N+1 у себя.

### ⚠️ Вероятные уточняющие
- **«Как найти N+1 в проде?»** — Трассировка (TraceId/SpanId, Zipkin — видно россыпь однотипных спанов), логи запросов, метрики latency на резолверах.
- **«Когда N+1 терпимо?»** — Дешёвый источник (кэш, in-memory), малые N, разовые запросы. Наш in-memory-кейс — дёшево, но архитектурно тот же.
- **«DataLoader решает всегда?»** — Нет: тяжёлые связи лучше агрегировать JOIN'ом прямо в резолвере списка; DataLoader — для раздельных источников.

## В13 ⭐. «Схему GraphQL — в тот же Maven-модуль, что и REST-контроллеры»

> *Формулировка прошлого экзамена:* Команда выбирает между REST и GraphQL. Компромисс: «сделаем GraphQL, но схему — в тот же модуль, что и REST-контроллеры, генерируем оба API из одной кодовой базы». В чём опасность? Два сценария эксплуатации, которые сделают архитектуру проблемной, даже если сейчас всё работает.

### 🔄 Весь цикл по шагам

**Сценарий.** Предложение: «схему GraphQL — в тот же Maven-модуль, что и REST-контроллеры». Разберём, что такое контракт в обоих мирах, и где схеме место.

1. **REST-мир:** контракт — Java-типы (`ProductRequest`, `ProductApi`) в отдельном модуле `smart-fridge-api-contract`. Потребитель импортирует jar → Maven версионирование, компилятор ловит ломающие изменения (В9).
2. **GraphQL-мир:** контракт — **SDL-файл схемы** (`*.graphqls`), а не Java. Его читают: DGS CodeGen (генерит Java-типы при сборке) и клиенты на любом стеке — по интроспекции/схеме. Java-модуль клиенту **не нужен**.
3. Поэтому «в тот же модуль, что REST-контроллеры» (= в smart-fridge-service, рядом с реализацией) — дефолт для DGS: схема в `resources/schema`, датафетчеры `@DgsQuery`/`@DgsData` рядом, CodeGen-типы генерятся при сборке.
4. **Что получаем:** + схема меняется вместе с резолверами и одним деплоем (не разъедутся); + быстрые итерации. **−** нет jar-артефакта контракта: клиентам только интроспекция; **−** нет компиляторной защиты клиентов от breaking change (в REST новая версия модуля просто не соберётся у потребителя); версионирование схемы — вручную, через депрекацию полей в SDL.
5. **Развилка «вынести схему в отдельный модуль»:** осмысленно, если схемой живут несколько сервисов (федерация) или нужен публикуемый артефакт схемы. У нас один сервис — платим модульностью без выгоды.
6. **Контраст с В9:** REST-контракт вынесен, потому что Java-типы переиспользуются потребителями; GraphQL-схема — не Java, переиспользовать в jar нечего.

**Финал:** REST-контракт = код → отдельный модуль с версионированием; GraphQL-контракт = SDL-файл → живёт рядом с резолверами и публикуется как схема. Правила эволюции у обоих одинаковые: аддитивность → депрекация → удаление.

### 📚 Теория

**Опасность: два контракта с разными моделями на одних ресурсах.**

1. **Модели ошибок расходятся:** REST — статусы + `ErrorResponse` через `@ControllerAdvice`; GraphQL — всегда 200 + `errors` через `DataFetcherExceptionHandler`. В проекте это **два разных класса** (`GlobalExceptionHandler` и `GraphQLExceptionHandler` с `TypedGraphQLError`) — уже на двух сущностях понадобились параллельные механизмы; на десятках правила начнут расползаться.
2. **Кэширование расходится:** REST кэшируется по URL (ETag, CDN); GraphQL — нет (всё POST в один эндпоинт). Защита тоже: лимиты «на эндпоинт» против depth/complexity/APQ.
3. **Общие ресурсы:** один пул потоков, одна JVM — деградация одного API валит другой.
4. **Связанность релизов:** оба API уезжают одним артефактом — нельзя выкатить схему без REST и наоборот.

**Сценарий 1 — нагрузочный.** Мобильное приложение массово бьёт в GraphQL тяжёлыми запросами (широкие выборки, батчи). Пул потоков и CPU заняты — **B2B-интеграторы на REST ловят таймауты**, хотя их API никто не трогал. Масштабировать хочется только GraphQL (отдельные инстансы, свои лимиты) — нельзя: один модуль/артефакт. Разделять посреди эксплуатации = резать общие сервисы.

**Сценарий 2 — организационно-эволюционный.** Фронтенд итерирует схему еженедельно (новые поля/типы), а REST v1 заморожен для внешних партнёров со стабильным контрактом на квартал. Один модуль = один релизный цикл: каждая правка схемы тянет деплой REST (регрессии, прогон контрактных тестов, откат тоже обоих). Либо команды блокируют друг друга. У REST-схемы и GraphQL-схемы **естественно разные скорости изменений** — совместное проживание в одном модуле эту скорость убивает.

(Запасной сценарий: безопасность — introspection/GraphiQL нужны внутренним, но наружу тот же сервис смотрит и REST; открыть/закрыть — решение, затрагивающее оба.)

**Как правильно:** резолверы+схема и REST-контракты — в **разных модулях** (или сервисах при разной нагрузке), общие только доменные сервисы. У нас — ровно «упрощённая версия» этого: два API в одном приложении, но ошибки/фетчеры/контроллеры физически разведены по пакетам; признать, что дальше разведены бы модули.

### 🧠 Каркас ответа
1. Тезис: *«два контракта с разными моделями — ошибки, кэш, защита — на одних ресурсах»* + аргумент «у нас уже два обработчика ошибок».
2. Четыре оси расхождения (ошибки, кэш, защита, релизный цикл/ресурсы).
3. Сценарий 1 (нагрузка) и сценарий 2 (скорости изменений) — с деталями.
4. Как правильно: разные модули, общие доменные сервисы; при разной нагрузке — разные сервисы.

### ⚠️ Вероятные уточняющие
- **«А чем хорошо совместное проживание?»** — Один деплой для малых команд, общие доменные сервисы без сетевого хопа, один стек. Для MVP — честный компромисс; вопрос билета — про масштабирование этого решения.
- **«Где граница — когда уже пора делить?»** — Разные SLA/нагрузки, разные команды-владельцы, разная частота изменений, необходимость масштабировать по отдельности.

## В14 ⭐. Три REST-запроса = 2.5 секунды. Один запрос без изменения REST-эндпоинтов

> *Формулировка прошлого экзамена:* Страница «книга» требует GET /books/{id}, GET /authors/{id}, GET /books/{id}/reviews. Три последовательных запроса — 2.5 с. Бэкенд отказывается делать спецэндпоинт под страницу. Какое решение сокращает до одного запроса? В чём его уязвимость?

### 🔄 Весь цикл по шагам

**Сценарий.** Мобильный экран «склад» дёргает три REST-запроса последовательно: `GET /api/products` (0.8с) → `GET /api/products/{id}/items` (0.8с) → `GET /api/fridge/summary` (0.9с) = **2.5с**. Нужно: один запрос, форма «под экран», REST-эндпоинты НЕ трогаем.

1. Почему нельзя просто «добавить поле в ответ»: эндпоинты едят другие клиенты (партнёры, веб) — менять их форму под один экран нельзя. Требование и есть «без изменения REST-эндпоинтов».
2. **Решение — GraphQL-слой сверху (фасад/BFF):** схема описывает **форму экрана**; резолверы внутри зовут **те же** сервисные методы / REST-клиенты, что и контроллеры.
3. Исполнение: клиент шлёт один query → DGS вызывает три источника **параллельно** (независимые поля верхнего уровня исполняются concurrently) → wall time ≈ max(0.8, 0.8, 0.9) ≈ **0.9с** вместо суммы.
4. Подводный камень: items для списка продуктов внутри нового слоя притащит N+1 из В12 → сразу закладываем DataLoader (батч по product_id), иначе «один запрос» породит 50 подзапросов.
5. REST-эндпоинты остались как были — для остальных клиентов; мобильный получил один запрос и ровно свою форму (ничего лишнего не скачает — over-fetching тоже ушёл).
6. **Цена решения:** новый слой = новые лимиты (depth/complexity, В11), свой кэш (HTTP-кэш тут не работает), сквозная трассировка: Correlation ID прокидываем из GraphQL-слоя в вызовы, иначе три источника не собрать в одну трассу.

**Финал:** агрегация переносит сборку ответа с клиента на серверный слой: round-trip'ы схлопываются в один, источники параллятся, старый REST продолжает жить для своих клиентов. GraphQL здесь — не замена REST, а фасад над ним.

### 📚 Теория

**Термин: агрегирующий слой — BFF (Backend for Frontend) / API Gateway с композицией; идиоматичный современный вариант — GraphQL как агрегатор поверх существующих REST-эндпоинтов.** Лекция формулирует идею прямо: *«вместо множества „глупых" эндпоинтов — один „умный" эндпоинт, придающий данным форму, какую запрашивает клиент»*; и в списке «когда GraphQL»: *«агрегация данных из нескольких микросервисов (BFF-паттерн)»*.

**Механика:** новый компонент принимает **один** запрос, сам обходит три эндпоинта — **параллельно**, а не последовательно — и склеивает ответ. Время ≈ max(t₁,t₂,t₃) вместо суммы. Доменные эндпоинты не меняются: знание «что нужно странице» живёт в агрегаторе, а не в доменном сервисе. Именно поэтому спецэндпоинт в бэкенде — анти-паттерн: каждая страница → новый эндпоинт, домен срастается с UI.

**Уязвимости (половина баллов):**
1. Новый компонент = новая точка отказа + лишний сетевой хоп.
2. **Каскадные сбои:** один из трёх сервисов лёг — что отдавать? Нужны таймауты, circuit breaker, политика частичного ответа.
3. **N+1/over-fetching не исчезают — переезжают в агрегатор:** GraphQL над REST без DataLoader даст те же подвызовы, спрятанные от клиента.
4. Дублирование авторизации/лимитов/логирования на слое агрегации.
5. Владение: кто поддерживает BFF (обычно фронтенд-команда, которой приходится знать домен)?
6. Согласованность: три источника могут отдать слегка разное состояние.

**Почему не кэш:** сокращает повторные запросы, но не первый запрос и не связность. **Почему не параллелить на клиенте:** N запросов с мобильного (трафик/батарея — лекция GraphQL), логика склейки размножается по платформам.

**Проект:** REST и GraphQL живут в одном приложении поверх одних сервисов — GraphQL фактически второй фасад; вынеси продукты в отдельный микросервис — наш DGS-слой стал бы классическим BFF (с нашим же N+1 в `ProductItemsDataFetcher` — см. В12).

### 🧠 Каркас ответа
1. Термин: BFF / агрегатор / «один умный эндпоинт».
2. Механика: композиция параллельно, max(t) вместо суммы; домен не знает про страницы.
3. Уязвимости: точка отказа, каскадные сбои (таймауты/частичный ответ), N+1 переезжает, дублирование cross-cutting, владение, согласованность.
4. Ответ на «почему не спецэндпоинт»: связанность домена с UI, экспоненциальный рост эндпоинтов.

### ⚠️ Вероятные уточняющие
- **«Как агрегатор защищается от падения одного из сервисов?»** — Таймауты на подвызовы, circuit breaker, частичный ответ с указанием ошибки по секции, деградация (отдать без рецензий).
- **«Кому отдать владение BFF?»** — Команде фронтенда (форма под её экраны), при общем кэше/авторизации — отдельная платформенная команда.

## В15 ➕. Query vs Mutation vs Subscription + безопасность GraphQL

### 🔄 Весь цикл по шагам

**Сценарий.** Один эндпоинт `/graphql`, три операции — смотрим, как исполняется каждая, и где в этой картине безопасность.

1. **Query:** `query { products { name } }` — только чтение; независимые поля исполняются **параллельно**.
2. **Mutation:** `mutation { create(...) { id } update(id: $id) { ok } }` — верхнеуровневые поля исполняются **последовательно, по порядку в тексте**: нельзя апдейтить то, что ещё не создано. Это семантика языка, а не договорённость сервера.
3. **Subscription:** `subscription { productEvents { type } }` — живое WS-соединение, сервер **пушит** при событиях. По сути наш `ProductEvent` из RabbitMQ, только доставка — клиенту через соединение, а не между сервисами.
4. **Безопасность — стопка слоёв:** транспорт — HTTPS; схема — introspection в проде гасим (не отдавать атакующему карту полей); форма — `MaxQueryDepth`/`MaxQueryComplexity` до исполнения (В11); авторизация — по слоям: токен на API, а права **на поле** — в резолвере (`salary` без роли не вернуть) — гранулярность, которой в REST нет без костылей.
5. **Чего нет из коробки:** HTTP-кэширование (всё уходит POST'ом на один URL) и статус-коды (всегда 200, ошибки в `errors`) → компенсируем APQ/persisted queries + CDN и ветвлением клиента по `errors`.

**Финал:** одна дверь, три операции с разной семантикой исполнения (параллельно / последовательно / пуш); безопасность — не фича, а стопка слоёв: скрытая схема, лимиты формы, авторизация вплоть до поля.

### 📚 Теория

**Три операции — и ключевое отличие в порядке исполнения:**

| | Семантика | Исполнение |
|---|---|---|
| **query** | чтение (R) | поля **параллельно** — читать можно безопасно |
| **mutation** | изменение (C/U/D) | **строго последовательно**, сверху вниз — для целостности: мутация 2 не должна начаться до завершения мутации 1 |
| **subscription** | push-подписка | сервер шлёт данные каждый раз при событии, пока клиент слушает; транспорт — **WebSocket/SSE** |

```graphql
type Query { user(id: ID!): User }
type Mutation { createUser(input: CreateUserInput!): User! }
type Subscription { commentAdded(postId: ID!): Comment! }
```

**Безопасность GraphQL (более уязвим, чем REST, из-за гибкости):**
1. **Depth limiting** — против бесконечной рекурсии `user→posts→author→posts→…` (DoS).
2. **Cost/complexity analysis** — веса полей, множители списков, порог (см. В11 — depth сам по себе бессилен).
3. **Persisted queries** — клиент шлёт хэш из белого списка: произвольные запросы полностью заблокированы (работает в связке с variables — см. В10).
4. В проде: introspection отключать/ограничивать (выгрузка всей схемы), таймауты исполнения.

**Проект:** `GraphQLSecurityConfig` (depth 20, complexity 200); subscriptions не реализованы (в схеме их нет) — честно назвать и объяснить, как бы добавил (`@DgsSubscription` + WebSocket-транспорт).

### 🧠 Каркас ответа
1. Таблица трёх операций + причина последовательности мутаций («целостность: CUD нельзя исполнять вперегонки»).
2. Подписки = pub/sub внутри GraphQL, WS/SSE, аргументами фильтруем, что слушать.
3. Безопасность: depth + cost + persisted queries + introspection — и почему одного depth мало.
4. Проект: security config есть, подписок нет (и как бы добавил).

### ⚠️ Вероятные уточняющие
- **«Почему query можно параллельно?»** — Поля читают, не конфликтуют; порядок полей в ответе всё равно по схеме, не по времени исполнения.
- **«Что вернёт сервер, если одна из мутаций упала посреди запроса?»** — Выполненные до неё результаты останутся в `data`, ошибка — в `errors` (частичный успех — см. В12-блок про ошибки GraphQL в разборе билетов).
