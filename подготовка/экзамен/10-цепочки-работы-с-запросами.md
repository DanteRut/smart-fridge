# Цепочки работы с реальными запросами: REST / GraphQL / gRPC / WebSocket

> Для каждой технологии: полный путь запроса по этапам + живые примеры HTTP/JSON/кода.
> Основано на проекте smart-fridge (Spring Boot 4, DGS 11, RabbitMQ) + примеры билета 5 (стриминг, ресторан).

---

## 1. REST — «создать продукт»

```
Браузер ──POST──▶ Шлюз ──▶ smart-fridge-service:8080
                              │ Jackson → Bean Validation → Контроллер
                              ▼
                        ProductApi (контракт-модуль)
                              │
                              ▼
                     ProductService.save()
                              │ save в хранилище
                              ▼
                     ProductEventPublisher ──▶ RabbitMQ (smartfridge.events)
                              │
                              ▼
                     Assembler (_links) → 201 + JSON
```

**Шаг 1. Запрос клиента:**
```http
POST /api/products HTTP/1.1
Host: api.example.com
Content-Type: application/json
Authorization: Bearer eyJhbGciOi...
```
```json
{ "name": "Колбаса докторская", "category": "Мясное" }
```

**Шаг 2. Шлюз:** проверяет токен (JWT-подпись), маршрутизирует по пути `/api/products/**` → сервис. Здесь может подменить ответ (ловушка В1) — обязан прокидывать тело как есть.

**Шаг 3. Десериализация:** Jackson: JSON → `ProductRequest{name, category}` (record из контракт-модуля).

**Шаг 4. Валидация (@Valid, ДО контроллера):** `@NotBlank` на name — ок. Если бы name="" → `MethodArgumentNotValidException` → сразу 400:
```json
{
  "status": 400, "type": "https://api.example.com/problems/validation-error",
  "title": "Ошибка валидации",
  "detail": "name: Название продукта не может быть пустым",
  "instance": "/api/products",
  "fieldErrors": [
    { "field": "name", "rejectedValue": "", "message": "Название продукта не может быть пустым" }
  ]
}
```

**Шаг 5. Контроллер (реализация контракта):** `ProductController implements ProductApi` → `service.save(request)` → хранилище (ConcurrentHashMap) → событие:
```java
// ProductEventPublisher.send(): ProductEvent.Created(id, name, category)
// упакуется в EventEnvelope{ metadata{eventId:UUID, occurredAt, source, routingKey:"product.created"}, payload }
```

**Шаг 6. Ответ (Assembler добавляет HATEOAS-ссылки):**
```http
HTTP/1.1 201 Created
Location: /api/products/42
Content-Type: application/json
```
```json
{
  "id": 42, "name": "Колбаса докторская", "category": "Мясное",
  "_links": {
    "self":   { "href": "http://api.example.com/api/products/42" },
    "items":  { "href": "http://api.example.com/api/products/42/items" },
    "all":    { "href": "http://api.example.com/api/products" },
    "delete": { "href": "http://api.example.com/api/products/42" }
  }
}
```
Внутри: `linkTo(methodOn(ProductController.class).getProductById(42))` — прокси прочитал `@GetMapping("/{id}")` и собрал абсолютный href (учёл X-Forwarded-Host).

**Ошибки на маршруте:** 404 (`GET /api/products/99` → type: .../resource-not-found) · 400 (валидация, выше) · 500 (handleAll, detail «Обратитесь к поддержке», лог + Correlation ID) · 502/503 от шлюза.

**Событие на другой стороне (аудит:8081):** listener вычитал из очереди `smartfridge.events`, routing key `product.created` прошёл binding `#` → в лог аудита. (Здесь же ловушки В18–В20: ack/auto, подтверждения, дедуп по eventId.)

## 2. GraphQL — «экран склада одним запросом»

```
Клиент ──POST /graphql──▶ DGS (8080)
                            │ parse → validate (по схеме, до исполнения!)
                            ▼
                   query/complexity лимиты (20/200)
                            ▼
                  Дерево резолверов (параллельно поля верхнего уровня)
                            ▼
        productsDataFetcher ──▶ ProductService
        ProductItemsDataFetcher ──▶ FridgeItemService  (N+1! → DataLoader)
                            ▼
                   200 + data (или 200 + errors)
```

**Шаг 1. Запрос (один POST на /graphql):**
```graphql
query WarehouseScreen($limit: Int = 20) {
  products(first: $limit) {
    id
    name
    category
    items { quantity unit expiresAt }
  }
}
```
```json
{ "query": "query WarehouseScreen($limit: Int = 20) { products(first: $limit) { id name category items { quantity unit expiresAt } } }",
  "variables": { "limit": 20 } }
```
Variables: текст запроса — константа → кэш parse; с APQ можно было бы послать только хэш.

**Шаг 2. Валидация по схеме:** каждое поле проверено: `products(first:): [Product!]!`, `items: [FridgeItem!]!`. Опечатка `categry` → запрос отвергнут ЗДЕСЬ, до резолверов: `Cannot query field 'categry' on type 'Product'` (громко и рано).

**Шаг 3. Исполнение деревом:**
- `productsDataFetcher` → 1 вызов: `findAll(limit)` → 4 продукта.
- Для **каждого** продукта резолверы `name`, `category` (из самого объекта — бесплатно) и `items` → 4 вызова `FridgeItemService.findByProduct(id)` → **итого 7 = 1+1+4** (живой N+1; на 50 продуктах — 51).
- **DataLoader** (как надо): резолверы items регистрируют id в `productIds` → один батч за «тик»:
```java
List<FridgeItem> byIds(List<Long> ids); // SELECT * FROM items WHERE product_id IN (11,12,13,14)
// карта id→items → раздат резолверам. 7 → 2
```

**Шаг 4. Ответ — всегда HTTP 200:**
```json
{
  "data": {
    "products": [
      { "id": "42", "name": "Колбаса докторская", "category": "Мясное",
        "items": [ { "quantity": 5, "unit": "шт", "expiresAt": "2026-10-20" } ] }
    ]
  }
}
```
Частичная ошибка: в `errors[]` и данные одновременно:
```json
{ "data": { "products": [ { "id": "42", "name": "Колбаса", "items": null } ] },
  "errors": [ { "message": "items unavailable", "path": ["products",0,"items"],
                "extensions": { "code": "INTERNAL" } } ] }
```

**Мутация (строго последовательно, по порядку в тексте):**
```graphql
mutation {
  createProduct(input: {name: "Сыр", category: "Молочное"}) { id }   # 1-й
  updateProduct(id: 42, input: {name: "Колбаса премиум"}) { id }     # 2-й после него
}
```

**Подписка (пуш):**
```graphql
subscription { productEvents { type id } }
```
WS-соединение держится, сервер шлёт данные при каждом событии RabbitMQ.

**Ловушки на маршруте:** depth=2 пройдёт, а `first:100000` уложит → complexity умножает цену ветки; интроспекция off; HTTP-кэша нет — APQ.

## 3. gRPC — «получить контент стриминга»

```
Клиент (stub) ──HTTP/2 POST /streaming.v1.StreamingService/GetContent──▶ Сервер (ServiceImplBase)
              ▲            │ payload: protobuf-байты (номер+wire type)                 │
              └── ответ ───┘                                                          ▼
                                                                protoc-генерация из .proto (номера!)
```

**Шаг 0. Контракт (фрагмент из билета 5):**
```protobuf
syntax = "proto3";
package streaming.v1;
message Content { int64 id = 1; string title = 2; ContentType type = 3; }
message GetContentRequest { int64 id = 1; }
service StreamingService {
    rpc GetContent (GetContentRequest) returns (Content);
    rpc Search (SearchRequest) returns (stream Content);   // server streaming
}
```

**Шаг 1. Вызов клиента (Java, сгенерировано protoc):**
```java
var channel = ManagedChannelBuilder.forAddress("streaming", 9090).usePlaintext().build();
var stub = StreamingServiceGrpc.newBlockingStub(channel).withDeadlineAfter(500, MILLISECONDS);
Content c = stub.getContent(GetContentRequest.newBuilder().setId(7).build());
```

**Шаг 2. По проводу:** HTTP/2-фреймы на `POST /streaming.v1.StreamingService/GetContent`; тело — бинарный protobuf: `id` = тег (1, varint) + значение; `title` = тег (2, length-delimited) + байты. **Имён полей нет.** Это же упрощает реюз байтов (совместимость В16/17) и делает payload плотнее JSON в ~3–5 раз.

**Шаг 3. Сервер:**
```java
@Override
public void getContent(GetContentRequest req, StreamObserver<Content> resp) {
    Content c = repo.find(req.getId());            // NOT_FOUND: (см. ниже)
    resp.onNext(c);
    resp.onCompleted();                            // статус OK в trailers
}
```

**Шаг 4. Ошибка — кодами, не HTTP-статусами:**
```java
resp.onError(Status.NOT_FOUND.withDescription("Content 7").asRuntimeException());
// клиент: StatusRuntimeException, Status = NOT_FOUND
```

**Server streaming (лента поиска):**
```java
stub.search(SearchRequest.newBuilder().setQuery("боевик").build())
    .forEachRemaining(content -> render(content));   // читаем по мере готовности
```
Сервер шлёт несколько `onNext`, затем `onCompleted` — один HTTP/2-поток, результаты приходят постепенно.

**Ловушки на маршруте:** deadline нужен (без — вечное ожидание); балансировщик должен быть L7/aware; int32→string при эволюции = падение парсера, int32→int64 = тихий мусор; grpc-web для браузера.

## 4. WebSocket (+STOMP) — «живой статус заказа»

```
Браузер ──GET Upgrade──▶ Шлюз/сервис ──101──▶ двусторонние фреймы поверх TCP
   │                                        ▲
   ├── CONNECT / subscribe /order/status ◄──┤ STOMP поверх WS (прикладной слой)
   ▼                                        │
Брокер (RabbitMQ) ──событие OrderStatusChanged──▶ сервис ──пуш──▶ все подписчики заказа
```

**Шаг 1. Рукопожатие (один раз):**
```http
GET /ws/orders HTTP/1.1
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Authorization: Bearer eyJhbGciOi...
```
```http
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```
Дальше этот TCP-сокет живёт: HTTP закончился, начались фреймы. Токен в заголовке handshake (не в query — логи!).

**Шаг 2. Подписка (STOMP поверх WS — из лекции 08):**
```stomp
CONNECT
accept-version:1.2
authorization:Bearer eyJ...

SUBSCRIBE
id:sub-0
destination:/topic/orders/7
```

**Шаг 3. Событие с сервера (пуш, без запроса!):**
```json
{ "orderId": 7, "status": "DELIVERING", "courier": "Игорь", "eta": "12:40" }
```
Клиент не опрашивал — сервер сам послал фрейм. Мелкий фрейм (2–14 байт заголовков + payload), не сотни байт HTTP-заголовков на каждый чих.

**Шаг 4. Отправка от клиента (если надо):**
```stomp
SEND
destination:/app/chat/7
{"text": "Курьер в пути?"}
```
Полнодуплексно: обе стороны шлют когда хотят — отличие от request/response.

**Шаг 5. Обрыв и восстановление:**
- Сеть моргнула → клиент получил код закрытия 1006 (обрыв).
- Переподключение с бэкоффом 1с→2с→4с...
- События, ушедшие в разрыв, **потеряны** → после реконнекта дотягивает REST-запросом текущий статус + дедуп по eventId, если сервер реплеит.

**Масштабирование (stateful!):** сессии живут в памяти инстанса → два клиента одного заказа на разных инстансах не увидят друг друга без брокера: сервис при событии публикует в RabbitMQ, ВСЕ инстансы слушают и пушат СВОИМ сессиям (или sticky-балансировка).

**Heartbeat:** `ping/pong`-фреймы или STOMP heartbeat — иначе NAT/LB тихо порежут «молчащие» соединения, и сервер будет пушить в пустоту.

## Сводная: та же операция «получить X» глазами клиента

| | REST | GraphQL | gRPC | WebSocket |
|---|---|---|---|---|
| Запрос | `GET /api/products/42` | `POST /graphql {product(id:42){...}}` | `stub.getContent(id=42)` | подписка `SUBSCRIBE /topic/orders/7` |
| Транспорт | HTTP/1.1 текст | HTTP (обычно POST на один URL) | HTTP/2 бинарный | TCP-фреймы после Upgrade |
| Контракт | DTO+OpenAPI (jar) | SDL-схема | .proto (номера) | своя схема сообщений |
| Ошибка | 404 + RFC 7807-тело | 200 + errors[] | Status.NOT_FOUND | код закрытия 1006/свой |
| Кэш | есть (GET) | нет (APQ) | нет | нет |
| Push | нет (polling) | subscription | server streaming | полнодуплексный |
