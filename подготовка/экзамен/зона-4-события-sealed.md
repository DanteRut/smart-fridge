## 1. Зачем брокер сообщений

| | Синхронно (REST/gRPC) | Асинхронно (брокер) |
|---|---|---|
| Отправитель ждёт? | да | **нет** |
| Получатель упал | ошибка у клиента | сообщение **ждёт в очереди** |
| Связанность | отправитель знает адрес получателя | знает только обменник |
| Пик нагрузки | бьёт прямо по получателю | очередь сглаживает |

**Три выгоды развязки**: (1) отказоустойчивость — потребитель перезапустился, сообщения накопились; (2) сглаживание пиков; (3) расширяемость — новый потребитель подписывается **без изменения издателя**.
**Цена**: eventual consistency (данные расходятся на время), сложнее отладка, сам брокер как инфраструктура, проблема гарантий (раздел 5–7).

**Запуск**: `docker run -d -p 5672:5672 -p 15672:15672 rabbitmq:management` — 5672 AMQP, 15672 management UI (guest/guest).

## 2. Модель AMQP

```
producer ──(message + routing key)──► EXCHANGE ──(bindings)──► queue ──► consumer
```
- **Producer никогда не пишет в очередь напрямую** — только в exchange: чтобы издатель не знал потребителей; новый сервис = просто своя очередь с биндингом, код издателя не меняется.
- **Exchange** маршрутизирует по routing key и правилам binding; **Queue** — буфер (FIFO); **Binding** — связь exchange↔queue.

**Типы обменников:**

| Тип | Правило | Сценарий |
|---|---|---|
| Direct | routing key = ключу binding | точечная доставка |
| **Fanout** | всем привязанным очередям, ключ игнорируется | всем одно и то же |
| **Topic** | паттерны | срезы потока событий |
| Headers | по заголовкам | экзотика |

**Topic-паттерны** (выучить): `*` — ровно **одно** слово; `#` — **ноль и больше** слов. Для `product.created`: `product.#` ✓ · `*.created` ✓ · `#.deleted` ✗ · `product.created` ✗ (нужно 3 слова для `product.created.*`).

**Fanout vs одна очередь (классика)**: очередь отдаёт сообщение **одному** consumer'у (балансировка!) — «сообщение досталось бы только одному счастливчику». Fanout даёт **копию в каждую** очередь: notification/billing/audit получают одно и то же событие.

## 3. Событийный контракт (у нас в проекте)

- **RoutingKeys**: `smartfridge.events` (exchange) + `product.created/updated/deleted`, `item.*` — соглашение `сущность.действие` → topic-подписки срезами.
- **EventEnvelope** — конверт: `Metadata(eventId: UUID, occurredAt, source, routingKey)` + `payload`.
  - Зачем: **eventId** — ключ идемпотентности потребителя и сквозной трассировки; **occurredAt** — когда произошло (не когда обработано); **source** — кто издал; **routingKey** — событие самоописуемо в логах/DLQ.
- Издатель: `rabbitTemplate.convertAndSend(EXCHANGE, routingKey, envelope)`; consumer: `@RabbitListener(queues = ...)`.

## 4. Sealed interface (билет) ⭐

```java
public sealed interface ProductEvent permits ProductEvent.Created, ProductEvent.Updated, ProductEvent.Deleted {
    record Created(Long id, String name, String category) implements ProductEvent {}
    record Deleted(Long id, String name) implements ProductEvent {}
}
```

**Что дал vs enum — два разных ответа:**
1. **Разные payload у вариантов (тип-сумма, ADT)**. Enum — значения одного типа с общей формой: у `Deleted` пришлось бы держать общие nullable-поля (`name`=null) и надеяться, что их не прочитают не у того варианта. Sealed+records — **свои поля у каждого варианта**, компилятор проверяет доступ.
2. **Исчерпывающий switch**: `permits` перечисляет всех наследников → switch **без default** при появлении нового типа **не компилируется** → эволюция контракта проверяется **на сборке** (добавил `Enriched` — все консьюмеры падают сборкой и принудительно решают). Плюс **закрытость**: чужой тип подсунуть нельзя.

**Чем слабее, чем кажется:**
1. **`default` гасит всю магию** — одна ветка `default -> игнорировать`, и компилятор больше **никогда** не напомнит. Исчерпываемость — дисциплина команды, не рантайма.
2. **Компиляция ≠ рантайм**: событие приезжает **по сети**. Продюсер задеплоил раньше со свежим контрактом → консьюмер работает со старым классом:
   - **без default** → switch бросит **`MatchException`** → сообщение в ретрай/DLQ → **заметят** (громкий сбой);
   - **с `default -> игнорировать`** → **тихая потеря** событий — никто не узнает.
   Sealed даёт выбор «падать громко / молчать», но не «понять новый тип».
3. **Централизация**: наследники только в одном модуле с интерфейсом — чужой сервис не расширит без общего контракта.

**Инженерный вывод**: правильный default — **`default -> log.warn + метрика unknown_event + DLQ`** (новый тип хотя бы заметен); консьюмеров деплоить **раньше** продюсеров (сначала все умеют читать новое — потом шлём); версионировать контракт.

🔗 **Проект**: ровно наш `ProductEvent`/`FridgeItemEvent`; audit-сервис слушает `#` и логирует конверт **без switch** — «новый тип не заметит вовсе»; консьюмер со switch+default — «заметит и промолчит».

## 5. Гарантированная доставка — три звена ⭐

| Звено | Механизм | Закрывает риск |
|---|---|---|
| Producer → Broker | **Publisher Confirms** (`publisher-confirm-type=correlated`) | брокер молча не принял |
| Broker (хранение) | **durable** exchange/queue + **persistent** сообщения | потеря при перезагрузке брокера |
| Broker → Consumer | **Acknowledgements** (`acknowledge-mode=manual`) | взял, упал — брокер уже удалил |

**Одного звена мало**: confirms не спасут от недолговечной очереди; durable — от auto-ack. Гарантия = все три.

- **Confirms**: издатель ждёт подтверждения брокера; `correlated` — сопоставление с конкретным сообщением (CorrelationData), `simple` — просто ок/не ок.
- **Auto-ack опасен**: Spring Boot по умолчанию подтверждает **сразу после отправки** потребителю → упал посреди обработки = **потеря навсегда**.
- **Manual ack**: `channel.basicAck(tag, false)` — «обработал, удаляй»; `channel.basicNack(tag, multiple, requeue)` — «не смог»: `requeue=true` → ретрай, `false` → **dead-lettering**.

## 6. DLQ — Dead Letter Queue

- Основная очередь объявляется с `deadLetterExchange` → необработанные (nack requeue=false) и истёкшие (TTL) сообщения уезжают в отдельную очередь.
- **Даёт**: «ядовитое» сообщение **не блокирует** основную очередь (иначе цикл requeue→crash парализует обработку); инженеры разбирают и переотправляют; **рост DLQ = алерт**.
- Формула: *«DLQ превращает тихий сбой в громкий»*.

## 7. Dual write → Transactional Outbox (билет) ⭐⭐

**Проблема**: сохранить в БД + опубликовать в RabbitMQ — **общей транзакции нет в принципе** (2PC/XA с RabbitMQ не применяют).

**Два сбоя:**

| | Сбой 1: БД сохранила, брокер недоступен → **событие потеряно** | Сбой 2: событие ушло, БД не сохранила → **фантом** |
|---|---|---|
| Кто знает | **никто** (исключение поймано, строчка в логе, пользователь получил 200) | источник знает (ошибка, операция повторится) |
| Самоликвидируется | **никогда**: аудит неполон, статистика неверна | да: потребитель отбивает фантом проверкой / DLQ |
| Тип | **тихий** | громкий |

**Ответ «какой опаснее»**: потеря события — тихий, необратимый, нужен ручной reconciliation, о котором никто не знает. **Оговорка на плюс**: если потребители действуют во внешний мир (деньги, письма) — фантом может быть опаснее; зависит от домена, дефолт — потеря.

**Решение — Transactional Outbox:**
```
┌───────── одна локальная ACID-транзакция БД ─────────┐
│  INSERT INTO products (...)                          │
│  INSERT INTO outbox (eventId, type, payload, rk, status) │
└──────────────────────────────────────────────────────┘
                  │ коммит
                  ▼
   Релизер (фоновый поллер или CDC/Debezium): SELECT ... WHERE status='NEW'
                  │ публикует с publisher confirms
                  ▼
             RabbitMQ ── ack ──► UPDATE outbox SET status='PUBLISHED'
```
1. Сущность **и** обязательство-событие — **в одной транзакции**: атомарность гарантирует БД → **«публикация или откат обоих действий»**.
2. Релизер публикует **с confirms**, потом помечает PUBLISHED.
3. Сбой 1 невозможен (закоммитилось → на диске → уйдёт даже после падения); сбой 2 невозможен (откатилось → публиковать нечего).

**Цена**: гарантия **at-least-once** — релизер может опубликовать дважды (умер между публикацией и UPDATE). **Ровно-once между БД и брокером не существует** → потребители **идемпотентны**: дедупликация по `eventId` (таблица обработанных ID; дубликат → ack без обработки) либо идемпотентные операции (upsert вместо insert, set вместо increment). *Ровно-once достигается эффектом: at-least-once + дедуп.*

**Альтернативы (почему хуже)**:
- **afterCommit-колбэк**: убирает фантом, но смерть процесса между коммитом и публикацией = снова потеря; обязательство нигде не зафиксировано (outbox сильнее: обязательство **на диске ДО** публикации).
- **Транзакции RabbitMQ (tx.select)**: объединяются только с собой, не с БД.
- **2PC/XA**: брокер не полноценный XA-участник + латентность.

**Follow-up**: релизер умер надолго → события копятся в outbox, уйдут после восстановления; рост таблицы outbox — метрика для алерта. CDC — чтение изменений из WAL БД (Debezium) — outbox уезжает без поллера.

🔗 **Проект (сильнейший ход)**: `ProductEventPublisher.send()` — вызывается из `ProductService.create` сразу после записи в storage, отправка в try/catch с `log.error` → это ровно **сбой 1**, воспроизводится `docker stop rabbitmq`. Улучшение: outbox-таблица + релизер + confirms; `EventEnvelope.metadata.eventId` (UUID) уже есть — **готовый ключ дедупликации**. Честно: у audit-сервиса нет manual ack и DLQ.
