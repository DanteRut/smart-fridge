## 1. HTTP-методы

| Метод | CRUD | Идемпотентен | Безопасен | Тело |
|---|---|---|---|---|
| GET | read | да | да | не определено |
| POST | create | **нет** | нет | да |
| PUT | update (замена целиком) | **да** | нет | да |
| PATCH | update (частично) | **не гарантирована** | нет | да |
| DELETE | delete | **да** | нет | обычно нет |

- **Идемпотентность**: повтор = тот же результат, `f(f(s)) = f(s)`.
- **PUT идемпотентен**: «состояние = X», X не зависит от текущего состояния → `f(f(s)) = X`.
- **PATCH не гарантирован**: дельта относительно текущего состояния («+5», add в массив) → каждый повтор меняет результат. **НО**: абсолютный патч («set name=X») идемпотентен — метод не гарантирует, RFC 5789 формулирует так сознательно.
- **GET с телом**: формально можно, семантики нет; кэши/прокси имеют право выбросить тело (Elasticsearch на GET с телом ломался о прокси). Полагаться = контракт на песке.
- **Долгие запросы на REST**: асинхронный REST — `POST /reports` → сразу **202 Accepted** + `Location: /reports/42/status` → клиент поллит → готово: 303/тело. Или webhook (callback-URL). Тяжёлая работа — в очередь (мостик к брокеру).

## 2. HTTP-статусы

| Класс | Смысл | Ключевые |
|---|---|---|
| 1xx | информационные | **101 Switching Protocols** (рукопожатие WebSocket) |
| 2xx | успех | 200 OK, **201 Created** (+`Location`), **202 Accepted**, **204 No Content** |
| 3xx | редирект/кэш | 301, **304 Not Modified** |
| 4xx | ошибка **клиента** | 400, 401, 403, 404, 405, 409, 422, **429** |
| 5xx | ошибка **сервера** | 500, **502**, 503 |

Семь кодов, которые просят различить:
- **400 vs 422**: 400 — само сообщение кривое (синтаксис/структура); 422 — синтаксис ок, семантика нет (валидация).
- **401 vs 403**: 401 — «**кто ты?**» (не аутентифицирован, перелогинься); 403 — «я знаю, кто ты, **но нельзя**» (повтор не поможет).
- **409**: конфликт состояния (устаревшая версия, дубликат).
- **429 Too Many Requests**: лимит; инструкция — `Retry-After`.
- **500 vs 502 vs 503**: 500 — упало в приложении; **502 — ставит посредник** («бэкенд за мной недоступен/ответил мусором»; приложение могло быть мёртвым); 503 — «временно недоступен, попробуй позже».

**Как ответить на «зачем разнообразие»:**
> Точный код = **машинночитаемая инструкция**. 429 → ретрай с паузой; 503 → ретрай позже; 401 → перелогин; 404 → **не ретраить никогда**. «Всё 200/500» отбирает у клиента дифференцированную реакцию, а у мониторинга — реальные метрики. Реестр кодов — RFC 9110.

🔗 **Проект**: `ProductApi` — 201 + Location на создание (`ResponseEntity.created(selfLink.toUri())`), 204 на удаление, 404/400/500 — `GlobalExceptionHandler`.

## 3. Семь принципов REST (по Филдингу, 2000, диссертация)

1. **Client-Server** — разделение: код запросов у клиента, данные у сервера → независимая эволюция.
2. **Stateless** — сервер не хранит состояние клиента; каждый запрос самодостаточен (токен, не сессия) → любой инстанс обрабатывает любой запрос → балансировка без sticky-сессий; падение инстанса не «теряет» пользователей.
3. **Cacheable** — явные метки кэшируемости (Cache-Control, ETag).
4. **Uniform Interface** — единообразие; внутри — разделение **ресурса** (что) и **представления** (JSON/XML — как).
5. **Layered System** — клиент не знает, с кем говорит: сервер, прокси, балансировщик; каждый уровень — только с соседними.
6. **Code on Demand** (опционален) — сервер может прислать исполняемый код (JS).
7. **Starting with the Null Style** — клиент знает **одну** точку входа; знание наращивается из ответов → фундамент HATEOAS.

REST — **архитектурный стиль**, не стандарт/протокол. Поверх HTTP/URL/JSON. Вытеснил SOAP/WSDL.

## 4. Уровни зрелости Ричардсона (RMM)

| Уровень | Что умеет | Пример |
|---|---|---|
| **0** | один URL, всегда POST | `POST /api {"action":"getProduct","id":5}` |
| **1** | URL на ресурсы | `GET /products/5` |
| **2** | глаголы + честные коды | `POST` → **201**+Location; `DELETE` → **204**; нет → **404** |
| **3** | **HATEOAS** — `_links` в ответе | self, collection, related |

Один CRUD × 4 уровня (запомнить на «продукте 5»):

| Операция | L0 | L1 | L2 | L3 |
|---|---|---|---|---|
| создать | `POST /api {action:createProduct}` → 200 | `POST /products` → 200 | `POST /products` → **201**+Location | + `_links` |
| прочитать | `POST /api {action:getProduct}` | `GET /products/5` → 200 | 200 / **404** | + `_links` self, items |
| обновить | `POST /api {action:updateProduct}` | `POST /products/5` | `PUT /products/5` → 200 | + `_links` |
| удалить | `POST /api {action:deleteProduct}` | `POST /products/5/delete` | `DELETE /products/5` → **204** | + self до удаления |

Логика переходов: **0→1** — у каждого ресурса свой URL; **1→2** — правильные глаголы/коды (кэш, ретраи, мониторинг начинают работать); **2→3** — сервер вкладывает следующие действия. L3 = L2 + HATEOAS.

🔗 **Проект**: REST-часть = L2–L3; `RootController` (`/api` отдаёт только ссылки) = Null Style.

## 5. API-контракт как Maven-модуль

- **Контракт** = явное соглашение: какие URL, какие данные, какие ошибки.
- **Сила формы**: контракт — Maven-модуль → сервер реализует интерфейсы → **«сломал контракт — проект не собирается. Точка»**. Ошибка несовместимости переносится с продакшена на компиляцию (тот же ход: sealed switch, кодогенерация gRPC).
- **Структура**:
```
корень (packaging=pom, Maven Reactor сам строит порядок)
├── xxx-api-contract/   dto/ + endpoints/ + exception/ + config/
└── xxx-service/        controllers implements XxxApi / assemblers / service / storage / exception
```
- **Аннотации наследуются с интерфейса** (Spring читает маппинги интерфейса) → контроллер без `@RequestMapping`/`@GetMapping` — только бизнес-логика («тонкий контроллер»).
- **Внутри контракта**: Request DTO — **records** + аннотации валидации; Response DTO — **классы** extends RepresentationModel; свои исключения (`ResourceNotFoundException`); `PagedResponse` — **простой record без Spring Data**: *«иначе контракт зависел бы от Spring Data — лишняя зависимость для клиентов»* (образец мышления: клиенту тащим только необходимое).
- **Цена (назвать самому)**: контракт **зацеплен за Spring MVC** (`@GetMapping` понимает только Spring); клиентам транзитивно едут spring-webmvc, hateoas, swagger. Лечится расслоением «чистое ядро (records + jakarta-validation + jackson-annotations) + привязки по фреймворкам», заморозкой v1 + окном депрекации, Tolerant Reader (`@JsonIgnoreProperties(ignoreUnknown=true)`).

## 6. Request DTO и валидация

```java
public record BookRequest(
    @NotBlank(message = "Название не может быть пустым") @Size(max = 100) String title,
    @NotBlank @ValidIsbn String isbn,           // кастомная валидация
    @Email String email,
    @Past LocalDate publishedAt
) {}
```
- **Почему record**: неизменяемый, компактный, без Lombok.
- **Механика @Valid**: `@Valid` в контрактном методе → Bean Validation выполняется **до входа в контроллер** → провал = `MethodArgumentNotValidException` → 400 с fieldErrors. **Без `@Valid` аннотации декоративны** — проверок нет.
- **Кастомная валидация**: `@Constraint(validatedBy = IsbnValidator.class)` + `@Target(FIELD, PARAMETER)` + `@Retention(RUNTIME)`; внутри — `ConstraintValidator<BookRequest, String>`.

**Переименование `isbn` → `productIdentifier` (билетный вопрос):**
- **Сервер не ломается** (честно валидирует новое), **клиент ломается молча**: маппит `fieldErrors[].field` → инпут формы **строковым совпадением** → подсказки пропали, а на 400 «productIdentifier: не должно быть пустым» клиент не понимает, что чинить. Ломается неявное соглашение «имя в ошибке = имя формы = имя запроса».
- **Три места**: (1) контракт/сервер — DTO, OpenAPI, формат ошибок; (2) клиент — маппинг field→input и отправляемое имя; (3) тесты/дашборды/документация.
- **Порядок (аддитивность → депрекация → удаление)**:
  1. В `FieldError` добавить машиночитаемый **`code`** (`"REQUIRED"`, `"ISBN_INVALID"`) — переживает любые переименования; в DTO добавить `productIdentifier`, `isbn` оставить **алиасом** (принимаем оба, валидируем оба, в ошибке имя + код). Ничего не ломается.
  2. Клиенты мигрируют в своём темпе (на code при показе, на новое поле при отправке); метрика «кто ещё шлёт isbn».
  3. Удалить `isbn` после окна депрекации.
- Анти-паттерн: «переименуем разом» = гарантированная молчаливая поломка всех.

🔗 **Проект**: наш `FieldError(field, rejectedValue, message)` — кода нет; «добавил бы `code`» — готовое улучшение.

## 7. Response DTO и Jackson

```java
@Getter @Builder
@EqualsAndHashCode(callSuper = false)      // _links не в equals
@JsonInclude(JsonInclude.Include.NON_NULL) // null-поля не видны в JSON
@Relation(collectionRelation = "products", itemRelation = "product")  // иначе "productResponseList"
public class ProductResponse extends RepresentationModel<ProductResponse> {
    private final Long id; private final String name; ...
}
```
- **Класс, не record**: нужно наследовать `RepresentationModel` (хранилище `_links`).
- **@Relation**: имена коллекции/элемента в `_embedded` — часть клиентского контракта.

**Билет «поле в БД есть, в JSON нет»** — цепочка **Entity → DTO → Jackson**, поле теряется штатно:
1. **Поля нет в Response DTO** — контракт не обновили, поле «не доезжает».
2. **`@JsonInclude(NON_NULL)` + null** — маппинг не проставил → Jackson **молча выбросил**.
3. **Имена**: `@JsonProperty` / `PropertyNamingStrategies.SNAKE_CASE` — поле под другим именем.
4. **Нет геттера / `@JsonIgnore` / `transient`** — Jackson сериализует через геттеры.
5. **`@JsonView`/фильтры** — у эндпоинта view без этого поля.
Почему тихо: сериализация — конфигурация, не исключение. Профилактика: контрактный тест «сериализованный DTO ↔ OpenAPI-схема» в CI.

## 8. Ошибки

**RFC 7807/9457 Problem Details:**
```
status(404, дублируется В ТЕЛЕ) · type(URI типа проблемы) · title · detail · instance(URI) · timestamp · fieldErrors[]
```
**@ControllerAdvice** — перехват исключений всех контроллеров:
- `ResourceNotFoundException` → **404**; `MethodArgumentNotValidException` → **400** + fieldErrors (из BindingResult: field/rejectedValue/defaultMessage); `Exception` → **500** (обязательно `log.error(..., ex)` — не терять стектрейс).
- Принцип: **контроллер никогда не обрабатывает ошибки сам — только бросает**; политика ошибок в одном месте.

**Билет «шлюз отдаёт 200 OK»** (главный):
- **Диагноз**: клиент принимает семантическое решение («ресурса нет») по **транспортному** признаку (коду), а статусом управляет вся цепочка — прокси, балансировщик, шлюз. Шлюз с моделью `{data:null, errors:[...]}` — это GraphQL-модель: **всегда 200, ошибки в теле**.
- **Решение**: семантика ошибки — **в прикладном контракте**: машиночитаемое тело (RFC 7807), клиент решает по телу. **`status` дублируется внутри тела** — контракт переживает любого посредника.
- **Но статусы не выбрасываем**: они для инфраструктуры (ретраи, CDN, SLO-алерты). Плохо не использовать коды — плохо принимать бизнес-решения только по ним.
- **Компромиссы**: 200-с-ошибкой кэшируется как успех → `Cache-Control: no-store`; алерты по кодам слепнут → мониторить тело/бизнес-метрики.

## 9. PUT vs PATCH — билетный вопрос «обнулить поле»

**Семантика**: PUT = «замени ресурс целиком» (отсутствующее затирается); PATCH = «измени переданное», **null = «не трогать»**: `request.name() != null ? request.name() : existing.getName()`.

**Ловушка**: в JSON «поле отсутствует» ≠ «поле = null», но после десериализации в Java **оба дают null** — различие потеряно. PATCH с «null = не трогать» **физически не может обнулить поле**. Клиент, не знающий остальных значений, не может выразить «очистить одно поле» ни PUT'ом, ни PATCH'ем.

**Три решения:**

| | **Merge Patch (RFC 7386)** | **JSON Patch (RFC 6902)** | **Своё соглашение** |
|---|---|---|---|
| Тело | `{"bio": null, "title": "X"}` | `[{"op":"replace","path":"/bio","value":null}]` | `{"title":"X","reset":["bio"]}` |
| Семантика | **нет члена = не менять; null = очистить; значение = заменить** | массив операций add/replace/remove/test/copy/move | поле-список сброса |
| Клиенту | +++ (обычный JSON) | + (операции, JSON-Pointer) | ++ |
| Серверу | + (нужен `JsonNullable`/JsonNode — дефолтный биндинг стирает различие) | ++ (библиотеки, свой content-type) | +++ |
| Атомарность | да | да | да |
| Для чего | пользовательские правки | протокольные/массовые правки, история изменений | свой велосипед: сам валидируй, кодогенераторы не поймут |

- **JsonNullable** — обёртка с тремя состояниями ABSENT/NULL/VALUE (из OpenAPI-генератора).
- **Бонус**: в GraphQL различие absent/null **есть из коробки** → там обнулить поле можно (в нашем `PatchProductInput`).

## 10. HATEOAS

**Принцип**: клиент взаимодействует через гипермедиа из ответов; API self-discoverable. «**Клиент знает наизусть один URL — все остальные получает из `_links`**».

**Три класса Spring HATEOAS**: `RepresentationModel<T>` (базовый, хранит `_links`) → `EntityModel<T>` (объект + ссылки) → `PagedModel<T>` (страница: `_embedded` + навигация first/prev/self/next/last + метаданные page).

**Assembler** — построение ссылок в одном месте:
```java
EntityModel.of(author,
    linkTo(methodOn(AuthorController.class).getAuthorById(id)).withSelfRel(),
    linkTo(methodOn(BookController.class).getAllBooks(id, ...)).withRel("books"))
```
**linkTo(methodOn) — НЕ вызов метода**: Spring создаёт **прокси**, читает аннотации маппинга (`@GetMapping("/{id}")`), строит URL → переименование маппинга обновляет все ссылки автоматически, типобезопасно.

**Пагинация**: сервис возвращает наш `PagedResponse` → конвертируем в `PageImpl` → `PagedResourcesAssembler.toModel()` строит `PagedModel` с навигационными ссылками.

**Цена HATEOAS серверу (билет)** — «сложность **переносится** на сервер»:
1. **Ссылки и rel — публичный контракт**: переименовать rel/убрать ссылку = ломающее изменение. «Свобода переименовать URL» — только если сервер поддерживает старый путь (redirect).
2. **Матрица «состояние × действие»**: в каждом состоянии — правильный набор ссылок (у отклонённой рукописи нет «опубликовать»). Машина состояний: спроектировать, тестировать, поддерживать.
3. **Ссылки всегда корректны и абсолютны**: за балансировщиком — `X-Forwarded-Host`, иначе клиенту приедет `localhost:8080`.
4. **Забыл ссылку = действия не существует** (догадаться клиент не может).

**Формула**: *«хардкод падает, когда сервер меняет URL; HATEOAS падает, когда сервер построил кривую ссылку. Сложность переехала на сервер»*.

**HATEOAS и UI (билет)**: UI статичен, ссылки появляются в рантайме → «нет ссылки» = **скрытое состояние**, которого нет в макетах; рендер зависит от латентности; комбинаторный взрыв тестов; клиент всё равно знает rel-имена. **Три решения**: (1) ссылка **всегда** + метаданные `{"href":..., "allowed":false, "reason":"MANUSCRIPT_REJECTED"}` → disabled-кнопка с тултипом; (2) **реестр rel** в клиенте: ссылка есть → активна, нет → disabled (сервер меняет правила без правки UI); (3) **BFF** → view-model с флагами `canPublish`. Общий знаменатель: **сервер решает «можно ли», клиент — «как изобразить»**.

## 11. Три REST-запроса → один (билет)

**Ответ**: агрегирующий слой — **BFF (Backend for Frontend) / API Gateway с композицией**; идиоматично — **GraphQL как агрегатор** поверх неизменных REST-эндпоинтов. Лекционная база: «вместо множества „глупых" эндпоинтов — **один „умный"**, придающий данным форму, которую запросил клиент».

**Механика**: агрегатор принимает 1 запрос, вызывает 3 эндпоинта **параллельно**, склеивает → время ≈ **max(t₁,t₂,t₃)** вместо суммы 2.5с. Знание «что нужно странице» — в агрегаторе, доменные эндпоинты не меняются. **Спецэндпоинт под страницу в домене = анти-паттерн** (каждая страница → новый эндпоинт, домен срастается с UI).

**Уязвимости (половина баллов)**:
1. Новая точка отказа + лишний сетевой хоп.
2. **Каскадные сбои**: один из трёх лёг → таймауты, circuit breaker, политика частичного ответа (отдать без рецензий + пометка).
3. **N+1/over-fetching переезжают в агрегатор** (GraphQL над REST без DataLoader — те же подвызовы).
4. Дублирование авторизации/лимитов/логирования.
5. Владение: BFF обычно фронтенд-команде (форма под её экраны).
6. Согласованность: три источника могут отдать разное состояние.
