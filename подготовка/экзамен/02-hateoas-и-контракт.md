## В6 ⭐. Клиент на HATEOAS пережил переименование URL. В чём цена для серверной команды?

> *Формулировка прошлого экзамена:* Ответ содержит `_links` с href. Клиент навигируется по ссылкам. Сервер переименовал `/api/books` в `/api/catalog`. HATEOAS-клиент работает без изменений, захардкоженный — падает. В чём реальная цена HATEOAS для серверной команды, которую обычно не замечают на демо?

### 🔄 Весь цикл по шагам

**Сценарий.** Переезжаем: `@RequestMapping("/api/products")` → `("/api/catalog")`. Смотрим оба клиента и счёт серверу.

1. **До:** `GET /` → `RootController` отдаёт `_links { products: { href: "/api/products" }, ... }`. Фронт нигде не пишет `/api/products` строкой — берёт `href` из ответа.
2. Сервер меняет одну строку маппинга.
3. Следующий `GET /`: `linkTo(methodOn(ProductController.class).all())` — это **не вызов метода**, а прокси, читающий аннотацию маппинга → в ответе уже `href: "/api/catalog"`. Список ссылок **пересчитался сам**, руками не правили ничего.
4. HATEOAS-клиент берёт свежий href → ходит по новому адресу → **работает**. Захардкоженный: константа в коде → 404 → релиз клиента.
5. **Цена №1:** старые закладки, кэш, документация живут долго → нужен 301-redirect или двойная маршрутизация — работа на сервере. «Свобода переименовать» платная.
6. **Цена №2:** каждая ссылка строится Assembler'ом **на каждый элемент каждой страницы**. Забыли rel в каком-то состоянии — для HATEOAS-клиента действия **не существует**: он не догадается.
7. **Цена №3:** за балансировщиком href соберётся `http://localhost:8080/...`, если не учесть `X-Forwarded-Host`/`X-Forwarded-Proto` → «гибкий» клиент ломается так же, как захардкоженный.

**Финал:** клиент пережил переезд — **счёт выставили серверу**: ссылки и имена rel стали публичным контрактом, и их правильность на каждом ответе — наша работа.

### 📚 Теория

**База:** уровень 3 по Ричардсону; «клиент знает наизусть один URL, остальные получает из `_links`». Выгода клиенту очевидна (устойчивость к переездам, self-discovery). Вопрос — про **цену серверу**: HATEOAS не убирает сложность, а **переносит её с клиента на сервер**.

**Четыре пункта цены:**
1. **Ссылки и имена rel стали публичным контрактом.** Клиент различает `rel` и ходит по `href` → переименовать rel, убрать ссылку, поменять структуру — такое же ломающее изменение, как переименовать URL. «Свобода переименовать URL» существует, только если сервер **продолжает поддерживать старый путь** (redirect/двойная маршрутизация) — работа тоже на сервере.
2. **Матрица «состояние × действие».** Сервер обязан в **каждом состоянии** каждого ресурса строить правильный набор ссылок: у книги без рецензий нет ссылки на рецензии; у отклонённой рукописи нет «опубликовать»; у оплаченного заказа появляется «возврат». Это машина состояний, которую надо спроектировать, покрыть тестами и поддерживать. Баг = кнопка, нажимать которую нельзя.
3. **Каждая ссылка всегда корректна и абсолютна.** Строится на каждый объект каждой страницы (Assembler). За балансировщиком — учесть `X-Forwarded-Host`/`X-Forwarded-Proto`, иначе клиент получит `href: http://localhost:8080/...`. Ошибся — «гибкий» клиент сломался так же, как захардкоженный.
4. **Полнота = функциональность.** Забыл ссылку — для HATEOAS-клиента действия **не существует** (догадаться он не может). Ответственность за работоспособность клиентов сместилась на сервер.

**Механика построения (показать понимание):** `linkTo(methodOn(ProductController.class).getProductById(id))` — **не вызов метода**: Spring HATEOAS создаёт прокси, читает аннотации маппинга (`@GetMapping("/{id}")`) и строит URL. Переименование маппинга в контракте обновляет все ссылки автоматически. Логика ссылок инкапсулирована в **Assembler** (`RepresentationModelAssembler`), чтобы не дублировать в контроллерах.

**Формула-финал:** *«Захардкоженный клиент падает, когда сервер меняет URL; HATEOAS-клиент падает, когда сервер неправильно построил ссылку или забыл rel. Сложность никуда не делась — она переехала на сервер»*.

**Проект:** `ProductModelAssembler`/`FridgeItemModelAssembler` + `RootController` (точка входа отдаёт только ссылки) — вся матрица состояний на нас; при том, что хранилище in-memory, стоимость «матрицы» мы честно не прочувствовали.

### 🧠 Каркас ответа
1. Признать выгоду клиента одной фразой (RMM-3, «один URL наизусть»).
2. Главный тезис: *«HATEOAS переносит знание структуры API с клиента на сервер»*.
3. Четыре пункта цены (ссылки=контракт; матрица состояние×действие; абсолютность ссылок и прокси-заголовки; забыл ссылку = нет действия).
4. Механика `linkTo(methodOn)` — прокси, читает аннотации — «как мы это делаем».
5. Финальная формула «кто на чём падает».

### ⚠️ Вероятные уточняющие
- **«Когда HATEOAS оправдан?»** — API с длинным жизненным циклом и сменными клиентами, состояния-машины (заказы, документы, workflow). Для простого CRUD цена может превысить выгоду.
- **«А чем плохи просто захардкоженные ссылки на сервере?»** — Дублированием; Assembler — единое место; прокси-механика обновляет их при рефакторинге маппингов.
- **«Что даёт @Relation?»** — Управление именами коллекций/элементов в `_embedded` (`products`/`product` вместо `productResponseList`) — это тоже часть клиентского контракта.

## В7 ⭐. HATEOAS: ссылки появляются/исчезают по состоянию — и UI

> *Формулировка прошлого экзамена:* Ссылки строятся динамически на основе состояния ресурса: у книги без рецензий нет ссылки на рецензии, у отклонённой рукописи нет «опубликовать». Клиент должен проверять наличие ссылки перед показом кнопки. В чём фундаментальная проблема для UI? Как разрешить конфликт «сервер диктует действия» vs «дизайнер хочет показывать кнопку всегда, даже неактивной»?

### 🔄 Весь цикл по шагам

**Сценарий.** Продукт как машина состояний: «свежий» и «просрочен». Смотрим, как меняется набор ссылок и что это значит для UI.

1. `GET /api/products/7`, йогурт свежий: `_links: self, items, update, delete`. UI рисует по этому ответу активные кнопки «изменить» и «удалить».
2. Срок вышел: сервер отдаёт **тот же ресурс**, но другой набор: `update`/`delete` исчезли, появилась `dispose`. Бизнес-правило «что можно делать с просрочкой» живёт на сервере, в одном месте.
3. UI: есть rel → кнопка есть; нет rel → кнопки нет. UI **не дублирует** правила — он их отображает.
4. **Конфликт с UI:** дизайнер хочет заранее показывать задизейбленную кнопку с тултипом «почему нельзя». HATEOAS отвечает только на «что можно с ЭТИМ представлением»: ссылки нет → клиент не знает, что действие вообще существует, и уж точно не знает, почему оно недоступно.
5. **Три решения:** (а) в теле `allowed: false` + `reason` — сервер явно говорит «нельзя и почему», UI рисует дизейбл с тултипом; (б) **реестр rel** — документированный словарь «какие действия бывают», клиент знает набор заранее; (в) **BFF** — серверная прослойка под конкретный экран, собирающая нужную UI-семантику.

**Финал:** HATEOAS — машина состояний, нарисованная ссылками; сервер отвечает за полноту набора в каждом состоянии, UI — за подачу. Их контракт — rel (или allowed/reason), а не фантазия верстальщика.

### 📚 Теория

**Фундаментальная проблема: UI статичен, HATEOAS — рантаймен.**
- Экран проектируется **заранее**: все кнопки, disabled-состояния, тултипы, вёрстка. А набор аффордансов («что можно сделать») становится известен **только из ответа**. «Нет ссылки» — **скрытое состояние**, которое дизайнер физически не может нарисовать (в макете его нет).
- Кнопки нельзя отрендерить до ответа — зависимость от латентности.
- Число вариантов экрана = произведение состояний всех ресурсов на странице — комбинаторный взрыв при тестировании.
- Ирония: клиент всё равно кодирует знание о **rel-именах** («где-то может быть publish») — часть связности вернулась в другой форме.

**Три решения конфликта:**

1. **Метаданные доступности у ссылки.** Сервер отдаёт ссылку **всегда**, добавляя статус:
```json
"publish": { "href": "/manuscripts/5/publish", "allowed": false, "reason": "MANUSCRIPT_REJECTED" }
```
Клиент рендерит disabled-кнопку с тултипом из `reason`. Цена: контракт толстеет, сервер обязан вычислять доступность всех действий во всех состояниях.

2. **Клиентский реестр rel.** UI знает список rel (стабильнее URL, часть контракта): ссылка есть → кнопка активна; нет → рисуем disabled. Сервер меняет бизнес-правила, не трогая UI. Цена: по rel — жёсткость (новый rel = правка UI); «серый» вид кнопки без объяснения причины (reason негде взять).

3. **BFF/UI-composition слой.** Промежуточный слой переводит гипермедиа во **view-model с флагами** (`canPublish: false`, `reason: "..."`) — UI-команда живёт по-старому (флаги просты), гипермедиа не протекает в компоненты. Цена: ещё один слой (со всеми его уязвимостями: точка отказа, каскадные сбои, отставание от схемы).

**Общий знаменатель (главная мысль):** разделение ответственности — **сервер — источник истины о том, МОЖНО ли действие (бизнес-правила); клиент — о том, КАК его изобразить (disabled, серый, тултип)**. А фундаментальная проблема одна: HATEOAS выражает «что доступно **сейчас**», а UI требует «что существует **в принципе** и как выглядит его недоступность» — значит контракт должен дополняться метаданными или адаптирующим слоем.

### 🧠 Каркас ответа
1. Поставить конфликт: рантайм-набор ссылок против заранее спроектированного экрана.
2. Три следствия: скрытые состояния, латентность, комбинаторный взрыв тестов (+знание rel никуда не делось).
3. Три решения с ценой каждого (allowed/reason; реестр rel; BFF-флаги).
4. Формула: «сервер — можно ли, клиент — как изобразить».
5. Честный итог: HATEOAS сам по себе этого не выражает — надо расширять контракт.

### ⚠️ Вероятные уточняющие
- **«Какое решение выбрал бы ты?»** — Для API с активной фронтенд-командой: №2 (реестр rel) как минимум, №1 если нужна причина недоступности в UI; №3 когда несколько платформ-клиентов.
- **«Чем это грозит серверу?»** — См. В6: матрица состояние×действие теперь ещё и с вычислением allowed для каждого действия.

## В8 ➕. Уровни зрелости Ричардсона (RMM)

### 🔄 Весь цикл по шагам

**Сценарий.** Один и тот же «посмотреть продукт 7 и удалить его» на четырёх уровнях зрелости — видно, что именно добавляет каждый уровень.

1. **L0:** один URL `/api/rpc`, всё POST, действие в теле: `{"action":"getProduct","id":7}` → ответ **всегда 200**, ошибка внутри: `{"ok":false,"error":"not found"}`. HTTP — просто труба: кэши бесполезны, мониторинг видит «всё 200», ретраи небезопасны.
2. **L1:** адресация: `/api/products/7`. Ресурсы появились, но по-прежнему всё POST и ошибки в теле — посредник знает «куда», но не знает «что».
3. **L2:** + методы и коды: `GET /api/products/7` → 200/404; `DELETE` → 204; `POST /api/products` → 201 + Location. GET идемпотентен → заработал кэш; 4xx/5xx видит мониторинг; ретраи GET безопасны.
4. **L3:** + `_links` (из В6/В7): в 200-ответе клиент находит `delete` сам, сервер свободно двигает URL.

**Трюк для экзамена:** таблица «4 операции × L0–L3» — строки GET/POST/PUT/DELETE, столбцы уровни; в каждой клетке — что меняется. Наш проект: **L2 на всём + L3 на продуктах/единицах** (Assembler'ы + RootController).

**Финал:** RMM — это перенос семантики из тела в транспорт: чем выше уровень, тем больше понимают инфраструктурные посредники (кэш, прокси, мониторинг) и тем тоньше клиент.

### 📚 Теория

| Уровень | Что умеет | Пример |
|---|---|---|
| **0** | Один URL на всё, всегда POST | `POST /api {"action": "getProduct", "id": 5}` |
| **1** | Отдельные URL на ресурсы | `GET /products/5` (но глаголы всё ещё «всё через POST») |
| **2** | HTTP-глаголы + честные коды | `POST /products` → **201**+Location; `DELETE /products/5` → **204**; нет ресурса → **404** |
| **3** | HATEOAS — ссылки в ответе | ответ содержит `_links` (self, collection, related) |

Один и тот же CRUD по уровням (запомни на продукте «Молоко», id=5):

| Операция | L0 | L1 | L2 | L3 |
|---|---|---|---|---|
| создать | `POST /api {"action":"createProduct","name":"Молоко"}` → 200 | `POST /products {"name":"Молоко"}` → 200 | `POST /products` → **201** + Location | + тело с `_links` |
| прочитать | `POST /api {"action":"getProduct","id":5}` | `GET /products/5` → 200 | `GET /products/5` → 200 / **404** | + `_links`: self, `items` |
| обновить | `POST /api {"action":"updateProduct",...}` | `POST /products/5 {...}` | `PUT /products/5` → 200 | + `_links` |
| удалить | `POST /api {"action":"deleteProduct","id":5}` | `POST /products/5/delete` | `DELETE /products/5` → **204** | + до удаления в `_links` есть self |

Логика переходов: **0→1** — у каждого ресурса свой URL; **1→2** — правильные глаголы и коды (система становится управляемой для инфраструктуры: кэш, ретраи); **2→3** — сервер вкладывает в ответы возможные следующие действия (уровень 3 = уровень 2 + HATEOAS, не вместо).

**Проект:** REST-часть — уровень 2–3: глаголы и статусы (201/204/404) + `_links` через assemblers; `RootController` — точка входа уровня 3 («Starting with the Null Style»: клиент знает только `/api`).

### 🧠 Каркас ответа
1. Таблица уровней + одна фраза на уровень.
2. Пример «одна операция × 4 уровня» (достаточно «прочитать» и «удалить»).
3. Логика переходов (URL → глаголы+коды → ссылки).
4. Проект: где у нас L2, где L3.

### ⚠️ Вероятные уточняющие
- **«Обязательны ли все уровни?»** — Нет, это шкала «насколько RESTовый» API; многие промышленные API живут на L2.
- **«Что даёт L2 инфраструктуре?»** — Кэшируемость GET, корректные ретраи (404 не ретраят, 503 ретраят), мониторинг по кодам.

## В9 ➕. Контракт как отдельный Maven-модуль: зачем и чем платим

### 🔄 Весь цикл по шагам

**Сценарий.** Фича «добавить `sku` в продукт» — как она проходит через контрактный Maven-модуль и что мы за это платим.

1. Всё структурное живёт в `smart-fridge-api-contract`: `ProductRequest`, `PatchProductRequest`, `ProductResponse`, `ErrorResponse`, интерфейсы `ProductApi`/`FridgeItemApi` с `@Valid` и Swagger-аннотациями. Один jar — единый источник правды.
2. Правим record → `mvn install` контракта → smart-fridge-service пересобирается: `ProductController` **реализует** `ProductApi`; сигнатура не совпала / забыл поле в маппере → **ошибка компиляции**, а не прод-инцидент. Контракт проверяет javac, а не код-ревью.
3. OpenAPI-документация генерится из **тех же** аннотаций DTO — Swagger физически не может разойтись с кодом; фронт регенерит клиента.
4. Валидация (`@NotBlank`) живёт там же: сервер валидирует ровно то, что описано в контракте.
5. **Цена №1:** контракт-модуль тащит **Spring** (webmvc, hateoas, swagger, Lombok) — любой потребитель jar наследует весь стек; отцепиться — переписывать контракт. Мы зацеплены за Spring именно так.
6. **Цена №2:** дисциплина релизов: обновил контракт → пересборка и перевыкладка всех зависимых; аддитивное поле — minor, ломающее — новая версия артефакта + цикл «аддитивность → депрекация → удаление» (В5).

**Финал:** один источник правды для структуры + валидации + документации, проверяемый компилятором; платим общими зависимостями и релизной синхронизацией.

### 📚 Теория

**Зачем:** API-контракт = явное соглашение (URL, данные, ошибки). Когда он — **Maven-модуль-зависимость**, нарушение соглашения ловится **компиляцией**: сервер реализует интерфейсы контракта — поменял сигнатуру → не собирается. «Если сервер нарушил контракт — проект не собирается. Точка». Ошибка переносится с продакшена на этап сборки — тот же ход, что sealed switch (события) и кодогенерация gRPC.

**Структура:**
```
корень (packaging=pom)
├── books-api-contract/   dto/ endpoints/ exception/ config/ validation/
└── demo-rest/            controllers implements XxxApi / assemblers / service / storage / exception
```
**Maven Reactor** строит граф модулей и собирает контракт раньше реализации.

**Что лежит в контракте:** интерфейсы с Spring-аннотациями + OpenAPI-документация; Request DTO — records с Bean Validation; Response DTO — классы extends RepresentationModel; свои исключения; `PagedResponse` — **простой record без Spring Data** («иначе контракт зависел бы от Spring Data — лишняя зависимость для клиентов»).

**Цена (назвать самому):**
- Контракт **зацеплен за фреймворк**: `@GetMapping` поймёт только Spring MVC; клиенту транзитивно едут `spring-webmvc`, hateoas, swagger-аннотации. Клиенту не на Spring — мусор в classpath. Переезд сервера на другой фреймворк ломает модель (полная стратегия — в лекции 10 курса).
- Двойная дисциплина версионирования: контракт меняется = пересборка всех.
- У нас in-memory-хранилище и один потребитель — цену мы не почувствовали; в реальном мире её смягчают расслоением «ядро + привязки».

**Проект:** 4 модуля: `smart-fridge-api-contract` → реализация; `smart-fridge-events-contract` → audit-service (контракт **событий** — тот же принцип в асинхронном мире).

### 🧠 Каркас ответа
1. Определение контракта + «сломал контракт → не собирается» (сместил обнаружение на компиляцию).
2. Структура модулей + Reactor (порядок сборки).
3. Что внутри и почему PagedResponse — record без Spring Data (принцип: только необходимое клиентам).
4. Цена: Spring-зависимости, версионирование.
5. Проект: два контрактных модуля (REST и событий).

### ⚠️ Вероятные уточняющие
- **«Как наследуются аннотации с интерфейса?»** — Spring читает маппинги и с реализуемых интерфейсов; контроллер — только бизнес-логика.
- **«Контракт между микросервисами?»** — Тот же модуль подключают и сервер, и клиент-сервис; события — отдельный контракт-модуль (у нас events-contract с EventEnvelope).
