# Протоколы, глаголы и ошибки: REST / GraphQL / gRPC / WebSocket (+AMQP)

> Сквозная идея: **семантика переезжает из транспорта в приложение.**
> REST — всё в HTTP (глаголы и статусы) → GraphQL — в теле (операции и errors) →
> gRPC — свой словарь поверх HTTP/2 (коды в trailers) → WebSocket — транспорт тупая
> труба, ВСЁ своё (фреймы, живость, ошибки).

---

## 1. REST

- **Протокол:** HTTP/1.1 (или HTTP/2) — текстовый, запрос-ответ.
- **Глаголы — методы HTTP (семантика в транспорте):**

| Глагол | Смысл | Идемпотентен | Успех |
|---|---|---|---|
| GET | читать | да (+кэшируем) | 200 |
| POST | создать/обработать | **нет** | **201 + Location** |
| PUT | заменить целиком | да | 200 |
| PATCH | частичная правка | **не гарантирована** | 200 |
| DELETE | удалить | да | **204** |
| HEAD/OPTIONS | метаданные/возможности | да | — |

- **Ошибки — статус-коды:**
  - 4xx (чинит клиент): 400 структура/валидация · 401 «кто ты» (+WWW-Authenticate) · 403 «прав нет» · 404 нет ресурса · 409 конфликт · 422 смысл не прошёл · 429 throttle (+Retry-After)
  - 5xx (чинит сервер): 500 внутренняя · 502 посредник получил плохой ответ · 503 временно (+Retry-After) · 504 таймаут посредника
  - **Тело ошибки:** RFC 7807 `application/problem+json`: type/title/status/detail/instance (+ наши fieldErrors{field,rejectedValue,message}).
  - Ловушка: статус могут переписать шлюзы → семантика дублируется в тело; клиент решает по type.

## 2. GraphQL

- **Протокол:** транспорт не навязан; де-факто **HTTP(S) POST на один URL `/graphql`** (текст JSON); query можно GET'ом (APQ); **subscription — WebSocket**.
- **«Глаголов» нет — есть операции в теле (семантика переехала в payload):**

| Операция | Смысл | Исполнение |
|---|---|---|
| query | чтение | поля верхнего уровня **параллельно** |
| mutation | запись | верхнеуровневые поля **строго последовательно** (порядок в тексте) |
| subscription | живой пуш | WS-соединение, сервер шлёт при событиях |

- **Ошибки — ВСЕГДА HTTP 200**, ошибки в теле:
  - `errors[]`: `message` · `path` (какой узел сломался) · `extensions` (code и пр.)
  - **частичный успех:** `data` и `errors` одновременно; non-null поле вернуло null → data обнуляется до ближайшего nullable-предка.
  - «Ранняя» ошибка: валидация по схеме ДО исполнения — `Cannot query field` (громко, рано, сервер не тронут).
  - Отбраковка нагрузки: MaxQueryDepth/MaxQueryComplexity — тоже до резолверов.
  - Не путать обработчики: DGS TypedGraphQLError (всегда 200) ≠ Spring @ControllerAdvice (4xx/5xx) — у нас оба.

## 3. gRPC

- **Протокол:** **HTTP/2 + protobuf** — бинарные фреймы, мультиплексирование, **trailers**; всё POST на `/package.Service/Method`; браузеру нужен grpc-web.
- **«Глаголов» HTTP нет — есть rpc-методы контракта, 4 паттерна:**

| Паттерн | Синтаксис .proto | Пример |
|---|---|---|
| unary | rpc Get(Request) returns (Response) | GetContent |
| server streaming | returns (stream X) | лента поиска |
| client streaming | принимает (stream X) | батч-загрузка |
| bidi | stream с обеих сторон | чат |

- **Ошибки — канонические коды статуса gRPC в trailers:**
  - OK(0) · INVALID_ARGUMENT · NOT_FOUND · PERMISSION_DENIED · ALREADY_EXISTS · FAILED_PRECONDITION · UNAVAILABLE (временно → **можно ретраить**) · DEADLINE_EXCEEDED · INTERNAL · UNIMPLEMENTED · UNAUTHENTICATED
  - Едут в **HTTP trailers** (после тела) → посредники/прокси могут терять статус.
  - Маппинг на HTTP для понимания: NOT_FOUND↔404, INVALID_ARGUMENT↔400, UNAVAILABLE↔503, INTERNAL↔500.
  - Ретраи: только UNAVAILABLE + идемпотентные методы; deadline propagation по цепочке.

## 4. WebSocket (+STOMP)

- **Протокол:** рукопожатие — HTTP `GET + Upgrade: websocket` → `101 Switching Protocols`; дальше **свой фреймовый протокол поверх TCP** (RFC 6455: text/binary/ping/pong/close). Поверх часто **STOMP** (pub/sub-команды: CONNECT, SUBSCRIBE, SEND, MESSAGE, ACK/NACK, ERROR).
- **«Глаголов» нет** — типы фреймов / STOMP-команды; направление обмена любое (полнодуплекс).
- **Ошибок в HTTP-смысле нет:**
  - **коды закрытия соединения:** 1000 нормальное · 1001 сервер уходит · **1006 аномальный обрыв** (по проводу не шлётся — диагноз на клиенте) · 1008 нарушение политики (авторизация) · 1011 внутренняя ошибка сервера
  - прикладные ошибки — в сообщениях (STOMP ERROR-фрейм, свой JSON с code)
  - ретраев нет: клиент сам — реконнект с бэкоффом, replay недоставленного, дедуп по eventId
  - отсутствие ответа ≠ ошибка (push-модель); живость следят heartbeat'ом

## 5. Бонус: AMQP (RabbitMQ)

- **Протокол:** AMQP 0-9-1 поверх TCP (5672).
- **«Глаголы»** — методы канала: `exchange.declare`, `queue.declare`, `queue.bind`, `basic.publish`, `basic.consume`, `basic.ack`, `basic.nack/reject`.
- **Ошибки:** закрытие канала/соединения с кодом: 404 NOT_FOUND (нет очереди) · 403 ACCESS_REFUSED · 406 PRECONDITION_FAILED (redeclare с другими параметрами). Прикладной отказ: `basic.nack(requeue=false)` → DLQ.

| | Протокол | «Глаголы» | Ошибки | Где живут глаголы/ошибки |
|---|---|---|---|---|
| REST | HTTP/1.1–2 | GET/POST/PUT/PATCH/DELETE | статусы 4xx/5xx + RFC 7807 тело | **в транспорте** |
| GraphQL | HTTP POST /graphql (+WS для subs) | query/mutation/subscription в теле | **всегда 200** + errors[]{message,path,extensions} | **в теле** |
| gRPC | HTTP/2 + protobuf | rpc-методы (unary/3 стрима) | коды статуса в trailers (NOT_FOUND, UNAVAILABLE…) | **свой словарь поверх HTTP/2** |
| WebSocket | HTTP-Upgrade → фреймы TCP (+STOMP) | фреймы / STOMP-команды | коды закрытия (1000/1006/1011), прикладные в сообщениях | **в приложении целиком** |
| AMQP | AMQP 0-9-1 TCP | basic.publish/consume/ack/nack | закрытие канала с кодом; nack→DLQ | в брокере |

**Финал-фраза:** *«REST держит семантику в транспорте — поэтому шлюзы могут её подменить и ей приходится дублироваться в тело (RFC 7807). GraphQL уже перенёс её в тело: всегда POST и всегда 200, операции и ошибки — поля JSON. gRPC — свой словарь кодов поверх HTTP/2, спрятанный в trailers. WebSocket — транспорт окончательно тупая труба: ошибки, живость и ретраи — всё забота приложения».*

## 6. Что такое «фреймы поверх TCP» (механика)

**Проблема:** TCP — надёжный упорядоченный **поток байтов без границ**: где кончается одно сообщение и начинается другое, он не знает. WebSocket решает это фреймами — каждый кусочек обёрнут мини-заголовком.

**Структура фрейма (RFC 6455):**
```
| FIN | opcode | MASK | длина (7/16/64 бита) | маска 4 байта | payload |
```
- **opcode = «глаголы» WS:** 0x1 text (JSON) · 0x2 binary · 0x9 ping · 0xA pong · 0x8 close (внутри — код: 1000/1011) · 0x0 continuation (большое сообщение дробится; FIN последнего = «всё»).
- **Длина** — в самом заголовке: до 126 байт в 7 битах, больше — 2 или 8 байтами. Итого заголовок 2–14 байт.
- **MASK:** клиент→сервер ОБЯЗАН маскировать payload XOR'ом со случайным ключом — чтобы данные от клиента не были предсказуемыми (защита от отравления кэша старых прокси, спутавших WS с HTTP). Сервер→клиент — нет. Немаскированный клиентский фрейм = close 1002.

**Пример:** сервер шлёт `{"status":"DELIVERING"}` → один фрейм: opcode 0x1, длина 20, payload-JSON; заголовок ~6 байт. Тот же JSON через polling унёс бы 400–800 байт HTTP-заголовков на каждый запрос — отсюда тезис «фреймы 2–14 байт».

**Ping/pong/close — тоже фреймы:** 0x9 раз в N секунд → обязателен 0xA; нет pong — соединение мертво (NAT/LB порезал) → реконнект. Close (0x8) несёт 2 байта кода закрытия.

**Не путать с HTTP/2-фреймами:** там (HEADERS/DATA/SETTINGS) HTTP-запросы дробятся для мультиплексирования потоков; в WS фреймы несут целые прикладные сообщения. Термин общий, механика разная.

**Формула:** *«TCP — поток байтов без границ; WS кладёт на него фреймы: тип + длина + маска + payload. Типы фрейма = глаголы WS: text/binary — данные, ping/pong — живость, close — код ошибки; заголовок 2–14 байт вместо сотен байт HTTP-заголовков на каждый запрос»*.

**Связь с билетами:** подмена статуса шлюзом (Б1.1) · GraphQL 200+errors (Б2.х, Б4.х) · коды gRPC ↔ HTTP (лекция 07) · WS/STOMP и реконнекты (лекция 08, билет 5).
