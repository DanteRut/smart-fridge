## В16 ⭐. Protobuf: добавили поле с новым номером. Что видит старый клиент?

> *Формулировка прошлого экзамена:* В .proto добавили поле с новым номером. Старый клиент не знает о нём. Что происходит при чтении на старом клиенте — ошибка или игнорирование? А обратно: старый клиент шлёт сообщение без этого поля новому серверу — что получает сервер?

### 🔄 Весь цикл по шагам

**Сценарий.** Было `message Product { string name = 1; int32 count = 2; }` — в проде старые клиенты и старые данные. Добавляем `string category = 3;` и деплоим сервер v2. Смотрим в обе стороны.

1. **Старый клиент читает v2-байты:** парсер идёт по тегам «номер + wire type»: тег 1 (string) — знает, тег 2 (varint) — знает, тег **3 — не знает** → смотрит wire type (3 → length-delimited) → **пропускает блок целиком** и продолжает разбирать дальше. `name`/`count` как раньше. Неизвестные поля игнорируются — совмещение работает.
2. **Новый клиент читает старые данные:** тега 3 в байтах нет → `category = ""` — дефолт proto3. proto3 не отличает «не установлено» от «пустая строка»; когда это важно — `optional` + `hasCategory()`.
3. То же с enum/числами: новое значение enum старый клиент видит как число (не падает), отсутствующее число читается как `0`/`false`.
4. **Сравнить с JSON (В3/В5):** там новое поле = новый ключ в DTO → правка маппинга и риск рассинхрона; здесь поле едет **по номеру**, имена по сети вообще не ездят → переименование `category → rubric` при том же номере **безопасно**.
5. Правило эволюции: новые поля = **новые номера** → совместимо в обе стороны (старый↔новое, новый↔старое); номера не переиспользовать (см. В17, reserved).

**Финал:** эволюция в protobuf — это управление номерами: новый номер = аддитивный шаг, совместимый в обе стороны; дефолты (`""`/`0`/`false`) заменяют «поля нет», а `optional` — способ различить «не установлено» и «пусто».

### 📚 Теория

**Как устроен формат (фундамент обоих protobuf-билетов):** на проводе сообщение — последовательность пар **(номер поля, wire type) + значение**. **Имена полей в байтах не передаются.** Wire types:

| Wire type | Кодирует | Размер |
|---|---|---|
| 0 — varint | int32/int64/uint/bool/enum | переменный |
| 1 — 64-bit | fixed64, double | 8 байт |
| 2 — length-delimited | string, bytes, message, repeated | длина + байты |
| 5 — 32-bit | fixed32, float | 4 байта |

Декодер читает пару (номер, wire type) и сверяет со **своей** схемой. Отсюда обе гарантии:

**Направление 1 — старый клиент читает новое сообщение: ИГНОРИРОВАНИЕ, не ошибка.**
Декодер не находит новый номер в своей схеме → **пропускает** поле по его wire type (знает, сколько байт занять) и продолжает разбор. В proto3 (с 3.5) неизвестные поля даже **сохраняются** в памяти и пере-сериализуются при пересылке — данные не теряются. Для старого клиента поля как бы не существует.

**Направление 2 — старый клиент шлёт без поля → новый сервер: ЗНАЧЕНИЕ ПО УМОЛЧАНИЮ.**
Поля в байтах нет → сервер получает дефолт: числовые → **0**; `string` → **""**; `bool` → **false**; `enum` → константа с номером **0**; message → «не установлено».

**Ловушка proto3 (назвать самому):** «0» неотличим от «не задано». Поле «количество на складе» = 0 — это ноль или поле не пришло? Лечение — модификатор **`optional`** (explicit presence): появляется `hasField()`. Именно поэтому enum обязан начинаться с **0** — «неизвестное/дефолтное» значение должно существовать.

**Проект:** gRPC-части в smart-fridge нет (взаимодействие асинхронное через RabbitMQ); пример .proto из курса — `LibraryService`/`Book` с полями `isbn = 1 … genre = 6`.

### 🧠 Каркас ответа
1. Начать с wire format: *«на проводе — пары (номер, wire type); имён нет»* — это ключ к обоим направлениям.
2. Направление 1: незнакомый номер **пропускается** по wire type; proto3 сохраняет неизвестные поля.
3. Направление 2: дефолты по типам (перечислить).
4. Ловушка «0 vs не задано» + `optional`/presence + почему enum с нуля.
5. Правило инженера: номера не менять, новые поля — только новыми номерами.

### ⚠️ Вероятные уточняющие
- **«А если поменять тип нового поля позже?»** — См. В17: при смене wire type ломается, при том же — тихий мусор.
- **«Как отличить „не задано" без optional?»** — Никак в proto3 без optional; обёртки (`google.protobuf.Int32Value`) или `optional`.

## В17 ⭐. Protobuf: действие, ломающее совместимость при неизменных номерах полей

> *Формулировка прошлого экзамена:* Protobuf гарантирует совместимость: старый клиент читает новые сообщения (пропуская неизвестные номера), новый читает старые (получая дефолты). Напишите действие, которое ломает совместимость, хотя номера полей не менялись. Почему Protobuf это не защищает?

### 🔄 Весь цикл по шагам

**Сценарий.** Поле `int32 count = 2;` — ломаем совместимость, **не трогая номер**. Три способа выстрелить и один контраст с JSON.

1. **Смена типа с другим wire type:** `int32 → string`. По сети тег несёт пару (номер=2, wire type): было varint (0), стало length-delimited (2). Старый парсер на теге 2 ждёт varint, видит length-блок → **ошибка парсинга** → падение. Громко — диагноз виден сразу.
2. **Смена типа в пределах того же wire type:** `int32 → int64 → bool` — wire type остаётся 0 → старый парсер **успешно** прочтёт: int64 молча усечётся (переполнение), bool выведется из «0/не-0». **Тихий мусор** — хуже громкого падения.
3. **Переиспользование номера:** `count` удалили, на номер 2 посадили `supplier_id` (string), без `reserved`. Старые сообщения в очереди читаются новым кодом: varint-байты трактуются как length-блок → каша или крэш. Лечение: `reserved 2; reserved "count";` — компилятор не даст переиспользовать; `buf breaking` в CI ловит смены типов.
4. **Бонус:** singular ↔ repeated — старый код увидит несколько блоков на «одно» поле и возьмёт одно из них: данных молча меньше.
5. **Контраст с JSON:** в JSON ломает **переименование** (В5: `isbn → productIdentifier`); в proto переименование безопасно (имена не ездят по сети), ломают **номера и wire type**.

**Финал:** протокол защищает **структуру, а не смысл** — гарантирует разбор байтов, но не поймёт, что «count» стал «supplier_id». Совместимость определяет человек (номера не переиспользуем, wire type не меняем), проверяет — `reserved` + buf breaking в CI.

### 📚 Теория

**Ответ: сменить тип поля при том же номере.**

```proto
// было:  string isbn = 1;
// стало: int64 isbn = 1;
```

Две степени беды:
1. **Другой wire type** (`string` = length-delimited, `int64` = varint): старый декодер встречает **неожиданный wire type у знакомого номера** → ошибка декодирования или мусор.
2. **Тот же wire type, другой смысл** — хуже: `int32 → int64 → enum` — все varint. **Декодируется молча, без ошибок**, но значения искажаются: усечения, «мусорные» enum-константы, отрицательные числа при zigzag-кодировании sint. Тихий сбой хуже падения (не детектируется).

**Прочие ломающие действия при тех же номерах:**
- `singular ↔ repeated`: одно значение станет списком из одного / наоборот;
- `message ↔ скаляр`;
- **удалить поле без `reserved` и занять номер новым типом**: старый клиент читает **новые байты по своей старой схеме** — тихий мусор;
- переименование: бинарно **безопасно** (имён на проводе нет), но ломает JSON-маппинг и компиляцию зависимого кода.

**Почему Protobuf это не защищает (суть):** его гарантия **структурная** — «одинаковый номер + одинаковый wire type = совместимо». Декодер работает с (номер, wire type) и ничего не знает о **смысле**: для старого кода «int64 по номеру 1» — то же самое поле №1. Схема не версионируется автоматически и не проверяется на совместимость — совместимость является **дисциплиной владельца контракта**:
- номера не переиспользовать; удаления — через `reserved`:
```proto
message Person {
  reserved 2, 15, 9 to 11;
  reserved "isbn";
  string name = 1;
}
```
- типы полей не менять;
- ломающие изменения схем ловить в CI (**buf breaking** и аналоги).

**Проект-мост:** тот же принцип «ошибка несовместимости — на этапе сборки», что контракт-Maven-модуль (REST) и sealed switch (события); в protobuf-мире роль «проверки на сборке» играет CI-проверка схем.

### 🧠 Каркас ответа
1. Главное действие: смена типа при том же номере — и сразу два случая (другой wire type → падение/мусор; тот же wire type → **тихие** искажения).
2. Остальные: singular↔repeated, message↔скаляр, переиспользование номера без reserved, (переименование — только JSON/код).
3. Ответ на «почему не защищает»: *«гарантия структурная — (номер, wire type), декодер не знает смысла; совместимость — дисциплина владельца»*.
4. Защита: reserved + запрет смены типов + CI-проверки.

### ⚠️ Вероятные уточняющие
- **«Что даёт reserved?»** — Номер/имя резервируется навсегда: компилятор отклонит его повторное использование — защита от «переиспользовал номер под другой тип».
- **«Как проверить совместимость автоматически?»** — buf breaking: сравнение новой схемы с прошлой версией, падение CI на ломающих изменениях.
- **«Почему enum с 0 важен для совместимости?»** — Дефолт enum = 0; если 0 нет в новой схеме, старое сообщение с «пустым» enum не смэппится корректно.
