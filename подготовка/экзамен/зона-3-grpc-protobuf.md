## 1. RPC: удалённый вызов процедур

- **RPC** — технологии, позволяющие вызывать функции в **другом адресном пространстве** (на удалённых машинах) так, чтобы это выглядело **как локальный вызов**. Цель — **прозрачность**: вызывающий не знает, что процедура на другой машине.
- Черты локального вызова: **асимметричность** (одна сторона — инициатор) и **синхронность** (вызывающий приостанавливается до возврата).
- **Сложности удалённого вызова**: разные адресные пространства (указатели не передать — параметры **копируются по сети**); машины неодинаковы (нужен единый формат); RPC обязан использовать сеть, но это **не должно быть видно** в сигнатурах.
- **Stub (заглушка)** — механизм прозрачности:
```
клиент → client stub (упаковывает параметры = marshal) → сеть
       → server stub (распаковывает = unmarshal, вызывает настоящую функцию) → результат обратно
```
- Исторические RPC (узнавать в лицо): DCE/RPC, DCOM, CORBA, Java RMI, SOAP, XML-RPC, JSON-RPC. Идея stub + IDL триумфально вернулась в gRPC.

## 2. Почему возник gRPC: боли REST

- Много сервисов → много API → много интеграций и **обвязки** (HTTP-клиент, сериализация, форматы дат, кейсинг, транспортные DTO) — «много возможностей для ошибок».
- **REST — не Contract First**: целостность контрактов не контролируется; Swagger генерирует документацию **по коду**, а хотелось бы **наоборот — код по документации**.
- JSON/XML громоздки — трафик и парсинг.

## 3. Что даёт gRPC

1. **Contract First**: сначала строго описываем контракт в .proto, кладём в репозиторий — «зафиксирован».
2. **Строгая типизация** + автоматическая валидация.
3. **Кодогенерация клиента и сервера**: сгенерированные заглушки при билде → **«нельзя сбилдить проект, не поменяв клиент и сервер, если поменялся контракт»** — несовместимость ловится на компиляции (триумвират с contract-Maven-модулем и sealed switch).
4. **Сериализация из коробки** — Protobuf: компактный бинарный формат.
5. **HTTP/2**: мультиплексирование (много запросов в одном соединении), бинарные фреймы → скорость.
6. **Стриминг** в обе стороны + встроенные балансировка, трассировка, аутентификация, health-check.

## 4. proto3: синтаксис

```proto
syntax = "proto3";
option java_multiple_files = true;
option java_package = "edu.rutmiit.demo.grpcservicedemo";
import "google/protobuf/empty.proto";
package library;

service LibraryService {
  rpc AllBooks (google.protobuf.Empty) returns (GetBooksResponse) {}
  rpc GetBook  (GetBookRequest)        returns (GetBookResponse)  {}
  rpc CreateBook (CreateBookRequest)   returns (google.protobuf.Empty) {}
}

message Book {
  string isbn = 1;        // НОМЕРА ПОЛЕЙ — идентичность на проводе
  string title = 2;
  int32  year = 5;
  enum BookGenre {
    FICTION = 0;          // первая константа ОБЯЗАНА быть 0 (= значение по умолчанию)
    NON_FICTION = 1;
  }
  BookGenre genre = 6;
  repeated string tags = 7;   // repeated = список
}
```
- `service` — контракт (набор rpc); `message` — структура (как DTO с номерами); `Empty` — «ничего»; `repeated` — список; enum с **0** — требование proto3 (дефолт должен существовать).

## 5. Wire format — ФУНДАМЕНТ ⭐

На проводе сообщение = последовательность пар **(номер поля, wire type) + значение**. **Имена полей в байтах НЕ передаются.**

| Wire type | Кодирует | Размер |
|---|---|---|
| 0 — varint | int32/int64/uint/bool/**enum** | переменный |
| 1 — 64-bit | fixed64, double | 8 байт |
| 2 — length-delimited | **string**, bytes, **message**, repeated | длина + байты |
| 5 — 32-bit | fixed32, float | 4 байта |

Декодер читает пару (номер, wire type) и сверяет со **своей** схемой. Из этого следуют обе гарантии совместимости (раздел 6) и все способы её сломать (раздел 7).

## 6. Совместимость: новое поле ⭐ (билет В16)

**Направление 1 — старый клиент читает новое сообщение: ИГНОРИРОВАНИЕ (не ошибка).**
Незнакомый номер → декодер **пропускает** поле по его wire type (знает длину) и продолжает разбор. Proto3 (с 3.5) неизвестные поля даже **сохраняет** в памяти и пере-сериализует — данные не теряются. Для старого клиента поля «не существует».

**Направление 2 — старый клиент шлёт без поля → новый сервер: ДЕФОЛТ.**

| Тип | Дефолт |
|---|---|
| числовые | **0** |
| string | **""** |
| bool | **false** |
| enum | константа **0** |
| message | «не установлено» |

**Ловушка proto3 (назвать самому)**: «0» неотличим от «не задано» («количество = 0» — это ноль или поле не пришло?). Лечение — **`optional`** (explicit presence): появляется `hasField()`. Альтернативы — обёртки `google.protobuf.Int32Value`.

**Правила инженера**: номера не менять; новые поля — только новыми номерами; удалять через `reserved`.

## 7. Что ломает совместимость при НЕизменных номерах ⭐ (билет В17)

**Главный ответ: сменить тип поля при том же номере.**
```proto
// было:  string isbn = 1;
// стало: int64 isbn = 1;
```
Две степени беды:
1. **Другой wire type** (`string`=length-delimited vs `int64`=varint) → старый декодер видит **неожиданный wire type у знакомого номера** → ошибка декодирования или мусор.
2. **Тот же wire type, другой смысл** — **хуже**: `int32 → int64 → enum` (все varint) → **декодируется молча, без ошибок**, но значения искажаются: усечения, «мусорные» enum-константы, знаковые проблемы. **Тихий сбой хуже падения** — не детектируется.

**Прочие ломающие действия при тех же номерах:**
- `singular ↔ repeated`: одно значение станет списком из одного / наоборот;
- `message ↔ скаляр`;
- **удалить поле без `reserved` и занять номер новым типом** → старый клиент читает **новые байты по своей старой схеме** — тихий мусор;
- переименование: **бинарно безопасно** (имён на проводе нет!), но ломает JSON-маппинг и компиляцию зависимого кода.

**Почему Protobuf это не защищает (суть ответа):**
> Его гарантия **структурная**: «одинаковый номер + одинаковый wire type = совместимо». Декодер работает с парами (номер, wire type) и **не знает смысла** — для старого кода «int64 по номеру 1» то же поле №1. Совместимость — **дисциплина владельца контракта**, а не свойство библиотеки.

**Инструменты дисциплины:**
```proto
message Person {
  reserved 2, 15, 9 to 11;
  reserved "isbn";
  string name = 1;
}
```
- `reserved` — номер/имя резервируются навсегда, компилятор отклонит повторное использование;
- типы полей не менять;
- ломающие изменения ловить в **CI**: `buf breaking` (сравнение с прошлой версией схемы, падение сборки).

## 8. Кодогенерация

- Из .proto генерируются: **DTO (с Builder'ами), клиентские stub'ы, серверные базовые классы, сериализация/десериализация** — весь транспортный слой. Языки: Java, Kotlin, C#, Go, Python, PHP, Ruby + мобильные.
- Maven: `protobuf-maven-plugin` + `os-maven-plugin` (детект платформы для protoc); Gradle: `./gradlew generateProto`. Spring-интеграция — `net.devh:grpc-server-spring-boot-starter` + `@GrpcService`.

## 9. Сервер

```java
public class LibraryService extends LibraryServiceGrpc.LibraryServiceImplBase {
    @Override
    public void getBook(GetBookRequest request, StreamObserver<GetBookResponse> observer) {
        Book book = books.get(request.getIsbn());
        if (book == null) {
            observer.onError(new StatusException(Status.NOT_FOUND));   // код ошибки
        } else {
            observer.onNext(GetBookResponse.newBuilder().setBook(book).build());
        }
        observer.onCompleted();
    }
}
```
- Три метода observer: **onNext(значение)** → **onCompleted()** / **onError(StatusException)**.

**Коды ошибок gRPC (аналоги HTTP):**

| Код | Смысл | HTTP |
|---|---|---|
| OK | успех | 200 |
| INVALID_ARGUMENT | кривые параметры | 400 |
| NOT_FOUND | нет сущности | 404 |
| ALREADY_EXISTS | конфликт создания | 409 |
| PERMISSION_DENIED | нет прав | 403 |
| UNAVAILABLE | недоступен | 503 |
| INTERNAL | внутренняя | 500 |

💡 Опять **прикладная модель ошибок независимо от транспорта** — параллель с RFC 7807 (REST) и `errors` (GraphQL).

## 11. Четыре типа вызовов

| Тип | Направление | Сценарий |
|---|---|---|
| **Unary** | запрос → ответ | CRUD (всё выше) |
| **Server streaming** | сервер шлёт поток | котировки, логи, обновления |
| **Client streaming** | клиент шлёт поток | батчи, файлы, телеметрия |
| **Bidirectional** | оба потока независимо | чаты, live-синхронизация, «пинг-понг» |

## 12. Interceptors и балансировка

- **Interceptors** — аналог middleware: перехват вызовов для логирования, метрик, аутентификации (на сервере и клиенте).
- **Балансировка** — **на стороне клиента**: round-robin по списку адресов от LB; источник живых адресов — service registry (мостик к Consul). Политики выдачи — на стороне LB.

## 13. Критика gRPC (называть самому)

- Сложный runtime — при багах внутри «непонятно, что делать».
- Проблемы с load balancing.
- Streaming большинству не нужен, а усложняет рантайм.
- **Бинарный протокол мешает дебагу** (в tcpdump мусор), инструменты сырые (grpcurl + .proto).
- **Не работает поверх HTTP/1.1** → балансировщики/прокси без HTTP/2 — проблема.
- Часто время соединения/передачи — не бутылочное горлышко, выигрыш не так велик.

**Вывод**: gRPC — для **внутреннего** межсервисного трафика (кластер, свой контроль инфраструктуры, скорость + типизация); REST — для **внешних** API (браузеры, CDN-кэш, читаемость). В реальных системах живут оба (наша практика СОП 9: gRPC внутрь кластера + события наружу).

- В проекте gRPC **нет** — межсервисное взаимодействие асинхронное (события в audit-service), синхронных вызовов между сервисами нет.
