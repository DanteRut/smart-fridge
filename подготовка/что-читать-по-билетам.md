## Б1.4. Dual write: БД + RabbitMQ без общей транзакции

**🧪 Практика «СОП 7» (`практики/СОП 7.pdf`), слайды 1–3 — главное чтение, «Контракт гарантированной доставки»:**
- сл. 1–2: трёхстороннее соглашение: **Producer → Broker** (Publisher Confirms: «издатель ждёт от брокера подтверждения»), **Broker** (durable очереди/обменники + persistent сообщения: «переживёт перезагрузку»), **Broker → Consumer** (Acknowledgements).

**📖 Лекция RMQ (`лекции/RMQ.pdf`), слайды 5–6:** паттерны Publish/Subscribe и Observer — база, чтобы объяснить, зачем вообще брокер в этой схеме.

## Б2.1. Зачем `variables`, если можно захардкодить в `query`?

**📖 Лекция 3, слайд 20 «Аргумент и переменные»:** «Переменные передаются отдельно (обычно JSON)» + пример `query GetUser($userId: ID!, $postsLimit: Int = 10)`. Заметь типизацию переменных в скобках — `$userId: ID!`.

**📖 Лекция 3, слайды 32–33 «Безопасность GraphQL» — вот техническая причина, просто лектор не назвал её прямо:**
- сл. 33: «**Persisted Queries (сохранённые запросы)**: клиент отправляет не текст запроса, а **хэш**; сервер выполняет только запросы из „белого списка"». Подумай: почему хэш вообще может идентифицировать запрос? Потому что текст запроса — **константа**, а всё переменное вынесено в variables. Без variables persisted queries невозможны.
- сл. 32–33: depth limiting и cost analysis — это про соседний вопрос Б2.2, читай сразу.

**Мостик для ответа (сформулируй сам):** запрос с variables = константа → сервер может разобрать (parse) и провалидировать (validate) его **один раз** и кэшировать, исполняя с разными значениями — точный аналог **prepared statements в SQL**. Плюс: значения едут по типам схемы (сл. 20), а не конкатенируются в строку — нет проблем экранирования и подмены структуры.

# Дополнения: темы, которых нет в лекциях

## Доп. 1. JSON Merge Patch (RFC 7386) и JSON Patch (RFC 6902) — для Б1.3

**JSON Merge Patch (RFC 7386).** Семантика: клиент шлёт обычный JSON-PATCH-подобный объект; **члена нет = «не менять», член есть с `null` = «очистить», есть со значением = «заменить»**. Ровно то, чего не хватает обычному PATCH из лекции 2 (сл. 10–11), где null после десериализации неразличим с «отсутствует». Пример: `{"title": "Новое", "bio": null}` — title заменить, bio очистить, остальные не тронуть. Цена для сервера: дефолтный Jackson-биндинг в record стирает различие — нужен `JsonNullable<T>` (обёртка из OpenAPI-генератора: три состояния — absent/null/value), парсинг в JsonNode или кастомный десериализатор. Цена небольшая, семантика стандартная.

**JSON Patch (RFC 6902).** Тело — **массив операций**: `[{"op":"replace","path":"/bio","value":null},{"op":"test","path":"/title","value":"Старое"}]`. Операции: add/replace/remove/test/copy/move. Плюсы: намерение выражено явно (нет неоднозначности вообще), набор применяется атомарно, есть готовые библиотеки и content-type `application/json-patch+json`. Минусы: клиенту тяжелее (строить операции и JSON-Pointer'ы `/a/b`), для «поменять одно поле» громоздко.

**Третье (своё соглашение).** Например, отдельное поле-список сброса: `{"bio":"текст","reset":["email","phone"]}`. Реализовать просто, но: свой стандарт, своя валидация («поле в reset не должно приходить со значением»), своя документация, кодогенераторы клиентов его не поймут. Сравнение трёх подходов — таблицей из разбора (Б1.3).

## Доп. 2. Transactional Outbox — для Б1.4

Проблема: БД и брокер — два разных хранилища, общей транзакции нет (2PC с RabbitMQ на практике не используют). Решение — паттерн **Transactional Outbox** (классика из «Microservices Patterns» Криса Ричардсона, microservices.io → patterns → transactional outbox):

1. В **одной локальной ACID-транзакции** пишем сущность И строку события в таблицу `outbox` (поля: `eventId`, тип, payload, routing key, статус). Атомарность даёт сама БД: либо обе записи, либо откат — «гарантия публикации или откат обоих действий» из вопроса.
2. Отдельный процесс-**релизер** (поллер или CDC типа Debezium, читающий WAL) забирает неопубликованные строки и публикует в RabbitMQ. Публикация — с **publisher confirms** (это ты знаешь из СОП 7!); после подтверждения брокера запись помечается опубликованной.
3. Гарантия = **at-least-once**: релизер может умереть между публикацией и апдейтом outbox → продублирует. Поэтому потребители **идемпотентны** — дедупликация по `eventId`. Ровно-once между БД и брокером не бывает, проектируем под дубликаты.

Альтернатива-родственник: публикация в `afterCommit`-колбэке ( TransactionSynchronization после коммита) — убирает фантомы, но процесс может умереть после коммита до публикации → событие потеряно навсегда, обязательство не зафиксировано. Outbox устойчивее, потому что обязательство **записано на диск до** публикации.

## Доп. 3. Sealed interface + switch — для Б2.3

Java 17+. `sealed interface X permits A, B, C` — компилятор знает **полный** список наследников (они обязаны быть в том же модуле). Это делает осмысленным **exhaustive switch**: если switch-выражение по `X` покрывает A, B, C и не имеет `default`, то при добавлении наследника D **проект не скомпилируется**, пока ты не решишь, что делать с D. Это «принудительное обновление» при эволюции контракта — то, чего нет у enum? Нет, стоп: у enum switch тоже исчерпывающий. Разница в другом:
- **enum** — фиксированный набор значений **одного типа**; данные вариантов — общие поля (nullable). **sealed + records** — алгебраический тип-сумма: у каждого варианта **свой набор полей своего типа**, паттерн-матчинг деструктурирует их: `case Created(Long id, String name, ...) -> ...`.
- sealed можно строить иерархии (вложенные суммы), enum — плоский список.
Слабости sealed (суть билета): (1) один `default -> {}` навсегда гасит проверку исчерпываемости; (2) проверка — на компиляции, а события приходят по сети в рантайме: между версиями продюсера и консьюмера компилятор бессилен; без default консьюмер упадёт с MatchException (громко, заметно в DLQ), с default — молча проглотит (тихая потеря); (3) все наследники в одном модуле — чужой сервис не расширит тип без изменения контракта. Инженерный вывод: `default` писать можно, но только как `log.warn + метрика unknown_event + dead-letter`, не молча.

## Доп. 4. Proto3: правила совместимости — для Б3.1 и Б3.4

**Как устроен формат.** На проводе сообщение — последовательность пар **(номер поля, wire type)** + значение. Имена полей в байтах НЕ передаются. Wire types: 0 = varint (int32/int64/uint/bool/enum), 1 = 64-bit (fixed64/double), 2 = length-delimited (string/bytes/repeated/message), 5 = 32-bit (fixed32/float).

**Почему совместимо «в обе стороны» (Б3.1):** декодер нового формата читает пару; если номер ему незнаком — пропускает по wire type (знает длину) и идёт дальше; если знакомого поля в байтах нет — берёт значение по умолчанию: `0` / `""` / `false` / enum с номером 0 / «message не задано». В proto3 с модификатором `optional` отсутствие отличимо (`hasField()`); без него — ноль неотличим от «не задано» (известная ловушка).

**Чем ломается при тех же номерах (Б3.4):** (1) смена **типа поля** с другим wire type (`string` ↔ `int64`) — декодер натыкается на неожиданный wire type: ошибка декодирования или мусор; (2) смена типа **внутри одного wire type** (`int32 → int64 → enum`, все varint) — декодируется молча, но значения искажаются (enum не из схемы → неизвестная константа, отрицательные числа, усечения); (3) `singular ↔ repeated` — одно значение станет списком из одного/наоборот; (4) message ↔ скаляр; (5) удаление поля **без `reserved`** и переиспользование номера под другой тип — старые клиенты читают новые байты по старой схеме (тихий мусор); (6) переименование поля — бинарно безопасно (имён на проводе нет), но ломает JSON-маппинг и код. Правила дисциплины: номера не переиспользовать, удалять через `reserved 5, 12–15; reserved "isbn";`, типы не менять, ломающие проверки — в CI (buf breaking).
