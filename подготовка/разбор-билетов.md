# Разбор билетов пересдачи по СОП

Контекст: в прошлый раз — 4 билета, каждый из двух частей (Часть 1 — два вопроса по 1 баллу, Часть 2 — два вопроса по 2 балла). Все вопросы **ситуационные**: дана ситуация → спросили «что сломается / почему / какое решение / какова цена». Ни одного вопроса «расскажи про X».

## 0. Формула ответа на любой вопрос этого экзамена

Каждый ответ строится по одному скелету, всегда из четырёх шагов:

1. **Термин.** Назвать механизм одним-двумя словами («transactional outbox», «JSON Merge Patch», «N+1»). Это показывает, что ты в контексте.
2. **Механика.** Объяснить *своими словами*, как это работает внутри — как если объясняешь одногруппнику. Именно здесь «звук инженера», а не нейронки.
3. **Компромисс.** Назвать цену решения. Преподаватель почти всегда спрашивает «а чем это плохо?» — если ты сам её назовёшь до вопроса, это сильнейший ход.
4. **Пример из проекта.** «Вот у меня в smart-fridge это сделано вот так, и вот известный компромисс этого решения». Ты писал этот код — на нём ты звучишь уверенно.

### Шесть сквозных идей, которыми закрываются почти все билеты

| # | Идея | Где в билетах |
|---|------|---------------|
| 1 | **Контракт живёт на прикладном уровне.** HTTP-статусы, порты, транспорт — детали; семантика (ошибки, поля, действия) должна быть в теле/схеме, описанной контрактом | Б1.1.1, Б3.1.1 |
| 2 | **Ломающие изменения — только через аддитивность + депрекацию + удаление.** Сначала добавить новое рядом со старым, потом перевести клиентов, потом убрать старое | Б2.2.2, Б3.2.1 |
| 3 | **Надёжная асинхронность = at-least-once + идемпотентные потребители.** Ровно-once между БД и брокером не бывает, поэтому проектируем под дубликаты | Б1.2.2 |
| 4 | **Опасен тихий сбой, а не громкий.** Громкий падает в лог/DLQ и чинится; тихий расходит состояния навсегда незаметно | Б1.2.2, Б2.2.1 |
| 5 | **Абстракция не убирает сложность — она её переносит.** HATEOAS переносит знание URL с клиента на сервер; BFF переносит N+1 в агрегатор; sealed переносит проверку с рантайма на компиляцию (и та утекает через `default`) | Б1.1.2, Б3.1.2, Б2.2.1 |
| 6 | **Метрика должна мерить стоимость, а не форму.** Глубина GraphQL ≠ стоимость запроса; количество полей ≠ вес резолвера | Б2.1.2 |

Держи эти шесть в голове: если забудешь конкретику, рассуждение от общей идеи всё равно приведёт к правильному ответу.

## Билет 1

### 1.1 (1 балл). Шлюз отдаёт 200 OK вместо 404 — как отучить клиента зависеть от транспортного уровня?

**Ситуация.** Сервер возвращает 404 с телом `{status, title, detail}`. Клиент проверяет HTTP-статус. Завтра сервер прячут за API-шлюзом, который на любые ошибки отдаёт **200 OK** с телом `{"data": null, "errors": [...]}` — клиент ломается. Какое архитектурное решение на стороне сервера предотвращает зависимость клиента от транспортного уровня?

**Что спрашивают.** Видишь ли ты разницу между *транспортным уровнем* (HTTP-статусы — это транспорт) и *прикладным контрактом* (тело ответа). Клиент, принимающий решения по статусу, зацеплен за деталь транспорта, которой распоряжается не сервер, а любой посредник на пути.

**Ответ.**

- Проблема: клиент принимает *семантическое* решение («ресурса нет») по *транспортному* признаку. Статусом управляет вся цепочка: прокси, балансировщики, API-шлюзы, GraphQL-обёртки. Любой из них может переписать код — и контракт треснет.
- Решение: **ошибка должна быть частью прикладного контракта, машиночитаемой в теле ответа**. То есть фиксируем в контракте формат ошибки (стандарт — RFC 7807/9457 Problem Details: `type`, `title`, `status`, `detail`, `instance`; либо свой `ErrorResponse`), и клиент решает «ошибка или нет» по содержимому тела, а не по коду. Это ровно модель GraphQL: статус всегда 200, а `errors` — массив в теле, часть схемы.
- Важно не скатиться в крайность «статусы вообще не нужны»: инфраструктура (ретраи, circuit breaker'ы, мониторинг, кэши браузера/CDN) живёт по статусам. Правильная формулировка: контракт фиксирует **оба** уровня, а клиент обязан быть устойчивым к трансляции статусов посредником — при 2xx проверять тело на наличие ошибки, при не-2xx тоже парсить тело по одному и тому же формату.

**Компромиссы (назвать самим).**
- «200 OK с ошибкой в теле» кэшируется браузерами и CDN как успех — на такие ответы нужен `Cache-Control: no-store`.
- Мониторинг и SLO-алерты, построенные на кодах ответов, перестают видеть ошибки — метрики надо снимать по содержимому/бизнес-метрикам.

**Если копнут глубже.**
- «Так что же, всегда отдавать 200?» — Нет: выбор модели фиксируется *в контракте API целиком*. Если контракт говорит «ошибки — в теле по RFC 7807, статусы могут переписываться шлюзом», клиент пишется под это и не ломается ни при каком шлюзе.
- «Где в моём проекте?» — `ErrorResponse(status, title, detail, instance, timestamp, fieldErrors)`: поле `status` дублирует код в теле — клиент может сверяться с телом даже получив 200. А GraphQL-часть уже живёт в модели «ошибки в теле» (`TypedGraphQLError`, массив `errors`).

**Устно за 30 секунд.** «Клиент зацеплен за транспорт, а статусом управляет любой посредник. Решение — перенести семантику ошибки в прикладной контракт: машиночитаемое тело ошибки по RFC 7807, клиент принимает решение по телу. Статусы остаются для инфраструктуры — ретраев и мониторинга, — но не для бизнес-логики клиента. У меня в проекте ErrorResponse содержит status и detail в теле, а GraphQL-часть изначально работает по модели "всегда 200 + errors"».

### 1.2 (1 балл). Три REST-запроса = 2.5 секунды. Как получить данные одним запросом, не трогая REST-эндпоинты?

**Ситуация.** Страница «книга» требует `GET /books/{id}`, `GET /authors/{id}`, `GET /books/{id}/reviews`. Три последовательных запроса — 2.5 с. Бэкенд отказывается делать специальный эндпоинт под страницу. Что сокращает до одного запроса? В чём уязвимость решения?

**Ответ.**

- Термин: **агрегирующий слой — BFF (Backend for Frontend) или API Gateway с композицией**; современный вариант — **GraphQL как агрегатор поверх существующих REST-эндпоинтов** (это буквально сценарий «агрегация данных из нескольких микросервисов» из лекции про GraphQL).
- Механика: новый компонент принимает один запрос от клиента, сам вызывает три эндпоинта — причём **параллельно**, а не последовательно — и склеивает ответ. Время становится ≈ max(t₁,t₂,t₃), а не сумме. Доменные эндпоинты не меняются: знание «что нужно странице» живёт в агрегаторе, а не в доменном сервисе. Именно поэтому «спецэндпоинт под страницу в бэкенде» — анти-паттерн: каждая страница порождает новый эндпоинт, домен срастается с UI.

**Уязвимости (обязательно назвать — это половина баллов).**
1. Новый компонент = новая точка отказа и лишний сетевой хоп.
2. **Каскадные сбои:** один из трёх бэкендов лёг — что отдавать? Нужны таймауты, circuit breaker, политика частичного ответа.
3. **N+1 и over-fetching не исчезают — они переезжают в агрегатор.** Если это GraphQL над REST, резолверы ходят в те же три эндпоинта, и без DataLoader'ов получим те же три (или больше) подвызова, просто спрятанные от клиента.
4. Авторизация, лимиты, логирование дублируются на слое агрегации.
5. Организационно: кто владеет BFF? Обычно фронтенд-команда, которой приходится знать домен.
6. Согласованность: три источника могут дать слегка разное состояние (книгу обновили между вызовами).

**Если копнут.** «Почему не кэш?» — Кэш сокращает латентность повторов, но не решает ни первый запрос, ни связность. «Почему не параллелить на клиенте?» — Можно, но тогда N запросов с мобильного клиента (дорого по батарее/трафику, о чём лекция GraphQL), и клиент сам склеивает — логика композиции размножается по платформам.

**Связь с проектом.** В smart-fridge REST и GraphQL живут в одном приложении поверх одних сервисов — GraphQL там фактически играет роль «второго фасада». Если бы продукты жили в отдельном микросервисе, наш DGS-слой стал бы классическим агрегатором с N+1 в `ProductItemsDataFetcher` (см. Б4.1.2).

### 1.3 (2 балла). PUT затирает, PATCH игнорирует null. Клиент хочет обнулить одно поле. Три подхода.

**Ситуация.** `PUT /books/{id}` — полная замена, отсутствующие поля затираются. `PATCH /books/{id}` — меняет только переданное, `null` = «не трогай». Клиент хочет **явно обнулить** одно поле, не зная остальных. PUT нельзя (не знает остальные значения), PATCH нельзя (null игнорируется). Три подхода на уровне контракта + сравнение.

**Ключевая мысль.** В JSON при десериализации в Java-объект различие «поле отсутствует» и «поле = null» **теряется** — оба дают `null`. Вся задача — восстановить это различие на уровне контракта.

**Подход 1. JSON Merge Patch (RFC 7386) с семантикой «отсутствует ≠ null».**
- По стандарту merge patch: отсутствующий член = «не менять», явно переданный `null` = «очистить поле». Ровно нужная семантика, стандартная, клиенту обычный JSON.
- Сложность на сервере: дефолтный десериализатор в record сотрёт различие. Нужен wrapper-тип (`JsonNullable` из OpenAPI-генератора), парсинг в `JsonNode`/`Map` с проверкой `has(field)`, или кастомный десериализатор. Реализация средней сложности, клиент — максимального простого.
- В OpenAPI выразить «присутствует vs отсутствует» тоже сложно — документация требует оговорок.

**Подход 2. JSON Patch (RFC 6902) — массив явных операций.**
```json
[{"op": "replace", "path": "/bio", "value": null},
 {"op": "replace", "path": "/title", "value": "Новое"}]
```
- Каждое намерение выражено явно: replace/add/remove/test. Однозначно, атомарно (применяется весь набор или ничего), есть стандартный content-type `application/json-patch+json` и готовые библиотеки.
- Сложность: клиенту строить массив операций и знать пути — порог входа выше; для простых «поменял два поля» это тяжеловесно. Зато идеально для массовых/протокольных правок и для читаемой истории изменений.

**Подход 3. Собственное соглашение в контракте.**
- Вариант A: PATCH-DTO с полями-обёртками (`JsonNullable<String> category`) — тот же принцип, что подход 1, но своими типами.
- Вариант B: отдельное поле-список сброса: `{"bio": "текст", "reset": ["email", "phone"]}` — реализация тривиальна, но это свой велосипед: надо документировать, валидировать (поле в `reset` не должно одновременно приходить со значением), тестировать; клиенты на кодогенерации такое не поймут без ручной доработки.

**Сравнение (таблица — её удобно воспроизвести по памяти).**

| | Merge Patch | JSON Patch | Свое соглашение |
|---|---|---|---|
| Стандарт | RFC 7386 | RFC 6902 | нет |
| Просто клиенту | да | нет (массив операций) | средне |
| Просто серверу | нет (различение absent/null) | да (библиотека) | да |
| Атомарность | да | да | да |
| Выразительность | поля | поля+массивы+test | что придумаешь |
| Документация | оговорки по null | стандартная | вся своя |

**Связь с проектом.** В `PatchProductRequest`/`PatchItemInputGql` у нас `null` = «не трогать» (проверка `request.name() != null ? ... : existing...`). Честное признание: в текущей реализации **обнулить категорию нельзя** — это известный компромисс, для чистого решения нужен `JsonNullable` или JSON Patch.

### 1.4 (2 балла). Двойная запись: БД + RabbitMQ без общей транзакции. Какой сбой опаснее и что делать?

**Ситуация.** Сервис сохраняет сущность в БД и публикует событие в RabbitMQ, операции не объединены транзакцией. Сбой 1: БД сохранила, брокер недоступен — событие потеряно. Сбой 2: событие ушло, БД не сохранила — потребители видят несуществующее. Какой опаснее? Для опаснейшего — решение с гарантией публикации или откатом обоих действий.

**Рассуждение: какой опаснее.** Критерий — *обнаружимость и обратимость*.
- Сбой 1 — **тихий**: никто не получил ошибки, лог чистый, а мир разошёлся. Аудит не узнал о факте, статистика навсегда неверна, уведомление не ушло. Расхождение не самоликвидируется — нужен ручной reconciliation, о котором никто не знает. Это нарушение eventual consistency с нулевым шансом её достигнуть.
- Сбой 2 — **громкий**: источник знает, что запись не прошла (пользователь получил ошибку и повторит), потребитель, обработав фантом, может обнаружить отсутствие сущности (проверка по источнику / ошибка ссылочной целостности) и отклонить событие в DLQ. Фантом компенсируем.
- **Вывод: опаснее сбой 1 — потеря события.** (Честная оговорка, добавляющая баллы: если потребители совершают необратимые внешние действия — списание денег, письма клиентам — фантом опаснее потерянного события, потому что действует в реальный мир. Ответ зависит от домена, но по умолчанию в учебной трактовке — потеря.)

**Решение: Transactional Outbox.**
1. В **одной локальной ACID-транзакции БД** пишем: сущность + строку в таблицу `outbox` (payload события, `eventId`, routing key, статус). Атомарность гарантирует сам БД: либо обе записи, либо откат обеих. Это и есть «гарантия публикации или откат обоих действий» — обязательство публикуется в той же транзакции, что и основное действие.
2. Отдельный **релизер**: фоновый поллер выбирает неопубликованные строки и публикует в RabbitMQ с **publisher confirms**; получив подтверждение брокера — помечает запись опубликованной. (Промышленный вариант — CDC: Debezium читает outbox из WAL.)
3. Гарантия получается **at-least-once**: релизер может издать дважды (упал между публикацией и апдейтом outbox) — поэтому потребители обязаны быть **идемпотентными**, дедуплицируя по `eventId`. Ровно-once между БД и брокером не существует — проектируем под дубликаты.

**Альтернативы (назвать и объяснить, почему хуже).**
- `afterCommit`-колбэк (публикация после коммита): убирает фантомы (сбой 2 невозможен), но если процесс умрёт между коммитом и публикацией — снова потеря, durable-обязательства нет.
- Транзакции RabbitMQ (tx.select): не объединяются с транзакцией БД — проблемы не решают.
- Распределённая транзакция/2PC через брокер: RabbitMQ не участник XA, на практике не применяется.

**Связь с проектом.** `ProductEventPublisher.publishCreated(...)` вызывается из `ProductService.create` сразу после записи в storage, а `send` оборачивает всё в try/catch и при ошибке брокера лишь пишет `log.error` — это ровно dual write со сбоем 1, воспроизводимым одной командой `docker stop rabbitmq`. Улучшение: outbox-таблица + релизер, а `EventEnvelope.metadata.eventId` (уже есть!) — готовый ключ дедупликации для audit-сервиса, который сейчас, кстати, не подтверждает сообщения вручную и не имеет DLQ — тоже честно назвать как точки роста.

## Билет 2

### 2.1 (1 балл). Зачем в GraphQL-запросе `variables`, если всё можно захардкодить в `query`?

**Техническая причина (просят не про читаемость).**

Разделение текста запроса и значений превращает `query` в **константу**:
1. **Кэширование и переиспользование запроса на сервере.** Parse + validate — дорогие шаги. Одинаковый текст запроса можно разобрать и провалидировать **один раз**, закэшировать скомпилированное представление и исполнять его с разными variables — это аналог **prepared statements** в SQL. Развитие идеи — Persisted/Automatic Persisted Queries: клиент шлёт вообще только **хэш** запроса из белого списка (заодно и защита: произвольные запросы невозможны).
2. **Типобезопасная сериализация значений.** Значения через variables проходят по объявленным в схеме типам — не надо строить строку запроса конкатенацией, нет проблем экранирования кавычек/переводов строк внутри JSON-строки `query`, нет «GraphQL-инъекций» (подстановка `$userId` как текста изменила бы структуру запроса; через variables это просто значение).

**Устно за 20 секунд.** «Variables делают текст запроса константой: сервер кэширует разобранный и провалидированный запрос и исполняет с разными параметрами — как prepared statement; плюс значения сериализуются по типам схемы, без конкатенации строк и проблем экранирования. Продвинутый случай — persisted queries, когда клиент шлёт только хэш».

### 2.2 (1 балл). Depth 5 из 20 — сервер всё равно лёг на 20 секунд. Как? Почему глубина бессильна?

**Ответ.** Глубина меряет *вертикаль* запроса, а не *стоимость*. При 5 уровнях вложенности можно:
- **Огромные списки:** `products(first: 100000) { name }` — глубина 2, а резолвер тянет сотни тысяч записей и на каждый считает поля.
- **Дорогие резолверы:** поле, за которым поход в ML-сервис/агрегацию/полнотекстовый поиск — один вызов = секунды, а по метрике глубины это «1 уровень».
- **Алиасы:** `a: book(id:"1") b: book(id:"2") ... z: book(id:"26")` — 26 подзапросов на одном уровне; глубина не растёт, стоимость растёт линейно. Так же размножаются тяжёлые поля.
- **Introspection:** `__schema { types { fields { args { ... } } } }` — глубина маленькая, а выгрузка всей схемы тяжёлая.

**Почему глубина как единственная метрика бессильна:** она считает структуру документа, а нагрузку создают *данные и резолверы* — ширина, размеры списков, дороговизна полей. Нужен **Query Cost/Complexity Analysis**: каждому полю — вес, спискам — множитель по запрошенному лимиту (`first`/`last`), суммарная стоимость сравнивается с порогом; плюс жёсткие ограничения пагинации, таймауты выполнения, в проде — отключённый introspection и/или persisted queries.

**Связь с проектом.** В `GraphQLSecurityConfig` стоят `MaxQueryDepthInstrumentation(20)` и `MaxQueryComplexityInstrumentation(200)` — но дефолтный complexity считает каждое поле = 1 и не знает, что `items` на продукте — поход в сервис с пагинацией. Для реальной защиты нужны кастомные веса полей. Это отличный пример «метрика есть, а стоимости не измеряет».

### 2.3 (2 балла). Sealed interface событий: что дал такого, чего не дал бы enum? И чем слабее, чем кажется?

**Ситуация.** `sealed interface Event` с record-наследниками `Created`, `Updated`, `Deleted`. Consumer пишет `switch` — компилятор требует покрыть все ветки. Разработчик добавил `default -> игнорировать`. Выходит новый тип `Enriched` — consumer молча его игнорирует. Что sealed дал, чего не дал бы enum? В чём слабость?

**Что sealed дал по сравнению с enum.**
1. **Разные типы с разными payload** (алгебраический тип-сумма): `Created(Long id, String name, String category)` и `Deleted(Long id)` несут разные поля, и компилятор это проверяет. У enum все константы — значения *одного* типа с общей формой; данные вариантов пришлось бы хранить в общих nullable-полях.
2. **Исчерпывающий `switch`**:sealed-иерархия известна компилятору (`permits`), поэтому `switch`-выражение без `default` **не скомпилируется**, если появился новый наследник. Эволюция контракта становится проверяемой на этапе сборки: добавил `Enriched` в контракт — у всех консьюмеров без `default` падает сборка, они принудительно решают, что делать.
3. **Закрытость**: `permits` запрещает кому-то снаружи подсунуть свой тип события.

**В чём слабее, чем кажется (суть вопроса).**
1. **`default` убивает всю магию.** Exhaustiveness — опциональная гарантия: достаточно одной ветки `default -> {}`, и компилятор больше *никогда* не напомнит о новых типах. Это дисциплина команды, а не свойство рантайма.
2. **Компилятор защищает только то, о чём знает на момент сборки.** Событие приходит по сети в рантайме: продюсер задеплоил `Enriched` раньше консьютера — консьютер работает со старым классом, скомпилированным без нового типа. И тут интересная развилка: если `default` **нет**, switch-expression бросит `MatchException` — сообщение упадёт, уйдёт в ретрай/DLQ, проблему заметят. Если `default` есть — тишина, события молча теряются. То есть sealed даёт выбор между «падать громко» и «молчать», но не «автоматически понять новый тип».
3. **Централизация.** Все наследники обязаны жить в одном модуле с интерфейсом — сторонний сервис не может добавить свой тип события, не изменив общий контракт. Это одновременно защита от «своих» типов и бюрократия эволюции.

**Инженерный вывод.** Правильный стиль для консьюмера: не `default -> игнорировать`, а явная ветка `default -> log.warn + метрика/unknown-events + dead-letter` — новый тип тогда хотя бы заметен. Плюс версионирование контракта событий и развёртывание консьютеров раньше продюсеров (сначала все умеют читать новое, потом начинаем писать).

**Связь с проектом.** В `smart-fridge-events-contract`: `public sealed interface ProductEvent permits ProductEvent.Created, Updated, Deleted` с record'ами — один в один вопрос экзамена. А audit-сервис слушает `#` и просто логирует `EventEnvelope` — у него нет switch, он «не заметит» новый тип вовсе; а консьюмер со switch и `default` — «заметит и промолчит». Обе ситуации можно показать на своём коде.

### 2.4 (2 балла). Контракт — Maven-модуль со Spring-аннотациями. Переезд сервера на Quarkus/Micronaut. Стратегия миграции.

**Что произойдёт.**
- Контракт зацеплен за **Spring MVC**: `@GetMapping` на интерфейсе сработает только там, где фреймворк умеет читать Spring-аннотации. Quarkus из коробки — это JAX-RS (Jakarta REST), Micronaut — свои аннотации (у Quarkus есть расширение совместимости со spring-web, но ограниченное). Значит `implements ProductApi` на новом фреймворке маппинги не подтянет — контракт придётся переписывать.
- Клиенты, подключившие модуль, **транзитивно тянут** `spring-webmvc`, `spring-boot-starter-hateoas`, swagger-аннотации, Lombok. Клиенту не на Spring (или мобильному/JS-клиенту, генерирующему код из OpenAPI) это лишний мусор в classpath; `RepresentationModel` в DTO — тоже Spring-тип.
- Итого: «переиспользуемый контракт» на практике переиспользуем только внутри Spring-мира. Цена решения, которое в курсе подавалось как преимущество.

**Стратегия миграции (требования: клиенты работают, сервер меняет фреймворк, новые поля без блокировки).**
1. **Расслоить контракт на ядро и привязки.** Ядро: чистые DTO (records), исключения, enum'ы — зависимости только `jakarta.validation-api` + `jackson-annotations` (стандарты, не фреймворк). Привязки: `contract-spring-web` (старые интерфейсы с `@GetMapping` и HATEOAS-моделями) и `contract-resteasy` (для Quarkus). Оба реализуют одно ядро. Клиенты зависят от ядра + нужной привязки.
2. **Версионировать по-крупному.** Spring-привязку заморозить как v1: только критические фиксы, статус deprecated с объявленной датой заката. Новый сервер живёт на v2 (Quarkus/JAX-RS). Переходный период — обе версии: либо Quarkus-приложение держит оба набора эндпоинтов (старые через адаптер), либо старое и новое приложения работают параллельно за общим шлюзом/балансировщиком.
3. **Аддитивная эволюция ядра.** Новые поля — только добавлением опциональных (nullable) полей; все клиенты обязаны быть **Tolerant Reader** (Jackson: `@JsonIgnoreProperties(ignoreUnknown=true)`, `FAIL_ON_UNKNOWN_PROPERTIES=false`) — тогда добавление поля ничего ни у кого не ломает и ничего не блокирует. Переименования/удаления/сужение типов — только через цикл «аддитивность → депрекация → удаление» (см. идею №2).
4. **Нейтральное представление ссылок.** HATEOAS-`RepresentationModel` из ядра убрать: в ядре — свой тип `Link`/`Map<String, Link>`, конвертация в Spring HATEOAS — в spring-привязке. Тогда ядро честно без Spring.
5. **Контрактные тесты** (consumer-driven: Spring Cloud Contract / Pact) — страховка, что обе привязки совместимы с ожиданиями клиентов во время всего перехода.

**Связь с проектом.** `smart-fridge-api-contract` зависит от `spring-webmvc`, `spring-boot-starter-hateoas`, swagger-аннотаций и Lombok — «зацепленный» вариант. Вопрос экзамена — это цена нашего решения, и честный ответ: в учебном проекте, где все на Spring, компромисс оправдан; в индустрии ядро делали бы чистым.

## Билет 3

### 3.1 (1 балл). Protobuf: новое поле. Старый клиент читает новое сообщение; старый клиент шлёт новому серверу. Что происходит?

**Ответ.** В обоих направлениях **ошибки не будет** — это и есть гарантия совместимости protobuf:
- **Старый клиент читает новое сообщение:** декодер читает пары (номер поля, wire type), поле с новым номером не находит в своей схеме — **пропускает** неизвестное поле по его wire type (varint / 64-bit / length-delimited) и продолжает разбор. Неизвестные поля в proto3 (начиная с 3.5) даже сохраняются в памяти и пере-сериализуются при пересылке. Для клиента поля просто не существует.
- **Старый клиент шлёт новому серверу сообщение без нового поля:** сервер получает **значение по умолчанию**: числовые — `0`, `string` — `""`, `bool` — `false`, enum — первое значение (0), message — «не установлено» (в proto3 c `optional`-полями это видно через presence: `hasField() == false`, иначе о присутствии вообще нельзя спросить).

Отсюда правила инженера: не менять номера полей и wire types, удалённые номера объявлять `reserved`, добавлять поля только новыми номерами. А «значение по умолчанию неотличимо от явно заданного нуля» — известная ловушка proto3 (лечится `optional`/presence).

### 3.2 (1 балл). HATEOAS: клиент на ссылках пережил переименование `/api/books` → `/api/catalog`. В чём реальная цена HATEOAS для серверной команды?

**Ответ.** HATEOAS не убрал сложность — он **перенёс её на сервер** (идея №5). Клиентская экономия оплачена серверной работой, которую обычно не замечают:

1. **Ссылки стали публичным контрактом.** Раз клиент различает `rel` и ходит по `href`, то имена отношений и структура ссылок — такой же контракт, как URL и поля. Переименовать `rel`, убрать ссылку, поменять структуру — то же ломающее изменение, что и переименование эндпоинта. «Свобода переименовать URL» существует только если сервер *продолжает поддерживать старый путь* (redirect/двойная маршрутизация) — это работа тоже на сервере.
2. **Матрица «состояние × действие».** Сервер обязан в **каждом состоянии** каждого ресурса строить правильный набор ссылок (у отклонённой рукописи нет «опубликовать», у оплаченного заказа есть «возврат»). Эту машину состояний надо спроектировать, покрыть тестами и поддерживать; баг = кнопка у клиента, нажимать на которую нельзя.
3. **Каждая ссылка всегда корректна и абсолютна.** Строится через assemblers на каждый элемент каждой страницы; за балансировщиком нужно учитывать `X-Forwarded-*`/Host, иначе клиент получит `localhost:8080`. Ошиблись — «гибкий» клиент сломался так же, как захардкоженный.
4. **Полнота = функциональность.** Забыл ссылку — действия для клиента *не существует*: у HATEOAS-клиента нет способа «догадаться». Ответственность за работоспособность клиентов сместилась на сервер.

**Устно одной фразой.** «Захардкоженный клиент падает, когда сервер меняет URL; HATEOAS-клиент падает, когда сервер неправильно построил ссылку или забыл rel. Сервер теперь владеет машиной состояний и отвечает за её гипермедийное представление — вот цена».

**Связь с проектом.** `ProductModelAssembler`/`FridgeItemModelAssembler` + `RootController` — ссылки через `linkTo(methodOn(...))`: типобезопасно и обновляется вместе с маппингами, но каждая ссылка в каждом состоянии — наша ответственность и наши тесты.

### 3.3 (2 балла). Bean Validation: переименовали `isbn` → `productIdentifier`. Кто сломается? Что менять в трёх местах и в каком порядке?

**Кто сломается.**
- **Сервер — нет.** Он честно валидирует новое поле и отдаёт `fieldErrors` с новым именем.
- **Клиент — да, и молча.** Он маппит `fieldErrors[].field` на поля формы («подсветить инпут isbn»). После переименования имя в ошибке не совпадает — подсказка просто перестаёт показываться. Хуже: если переименовано и поле в `BookRequest`, старый клиент продолжает слать `isbn`, сервер отвечает 400 «productIdentifier: не должно быть пустым» — клиент не может понять, что чинить. Ломается неявное соглашение «имя поля в ошибке = имя поля формы = имя поля в запросе».
- Также ломаются все, кто зацеплен за имена: сгенерированные из OpenAPI клиенты, контрактные тесты, мониторинг.

**Три места:**
1. **Контракт/сервер:** DTO (`isbn` → `productIdentifier`), аннотации валидации, схема OpenAPI, тексты сообщений — и, главное, **формат ErrorResponse**: сейчас `FieldError(field, rejectedValue, message)` — имена полей и человекочитаемые тексты хрупки.
2. **Клиент:** маппинг `field → input` и подсказки; отправка поля с новым именем.
3. **Документация/тесты/мониторы**, зацепленные за имена.

**Порядок миграции (это и есть главный ответ).**
1. **Аддитивный шаг:** в `ErrorResponse.FieldError` добавить машиночитаемый **код ошибки** (`code: "INVALID_ISBN"`, `"REQUIRED"`), независимый от имён полей; в DTO добавить новое поле `productIdentifier`, **оставив** `isbn` как deprecated-алиас: сервер принимает оба, валидирует оба, в ошибке отдаёт и имя, и код. Ничего не ломается.
2. **Миграция клиентов:** клиенты переходят с имён полей на коды ошибок и начинают слать `productIdentifier`. Каждый — в своём темпе.
3. **Удаление:** после объявленного окна депрекации убрать `isbn`. Изменение формально ломающее, но к этому моменту никто его не использует.
Анти-паттерн: «переименуем всё разом в новом релизе» — гарантированная молчаливая поломка всех.

**Связь с проектом.** Ровно наш `ErrorResponse.FieldError(field, rejectedValue, message)`: имена полей + текст сообщения («Некорректный ISBN») — оба хрупкие; улучшение — поле `code`.

### 3.4 (2 балла). Protobuf: действие, ломающее совместимость, при неизменных номерах полей. Почему Protobuf это не защищает?

**Ответ. Классика — сменить тип поля при том же номере.**
```proto
// было:  string isbn = 1;
// стало: int64 isbn = 1;
```
- Если wire type различается (`string` length-delimited vs `int64` varint) — старый парсер натыкается на неожиданный wire type у знакомого номера: ошибка декодирования или мусор.
- Хуже, когда wire type **совпадает, а семантика нет**: `int32 → int64 → enum` (все varint) — старый клиент молча прочитает байты по-старому: усечение, отрицательные числа у `sint32` (zigzag) вместо ожидаемых, «мусорные» значения без единой ошибки.
- Другие ломающие действия при тех же номерах: `singular ↔ repeated` (одно значение станет списком из одного или наоборот), message ↔ скаляр, map ↔ repeated message, а ещё — **удалить поле без `reserved` и переиспользовать номер под другой тип**: старый клиент интерпретирует новые байты по своей старой схеме — тихий мусор. Отдельно: **переименование** поля бинарный формат не ломает (на проводе только номера), но ломает JSON-маппинг и перекомпиляцию зависимого кода.

**Почему Protobuf это не защищает.** Его гарантия — **структурная**: «поля с одинаковым номером и wire type совместимы». Декодер работает с парами (номер, wire type) и ничего не знает о *смысле*: для старого кода «int64 по номеру 1» — то же поле №1. Схема не версионируется и не проверяется на совместимость автоматически — совместимость является **дисциплиной владельца контракта**: не менять типы/номера, `reserved` на удаления, и проверки ломающих изменений в CI (buf breaking / protolint) в репозитории `.proto`-файлов.

4. **Нет публичного геттера / `@JsonIgnore` / `transient`** — Jackson по умолчанию сериализует через геттеры; свойства для него не существует.

### 4.2 (1 балл). GraphQL: запрос легитимный, а в логах 7 запросов к БД; REST обошёлся двумя. Что это и почему?

**Ответ.** Это **N+1 проблема** (точнее — вложенный N+1). Механика: GraphQL исполняет **резолвер на каждое поле каждого объекта**: `book` (1 запрос) → `author` (1) → `books` автора (1) → для каждой книги автора — `content` (N запросов)... Каждый резолвер сам, независимо, ходит за данными, GraphQL по умолчанию **ничего не батчит**. REST-эндпоинты проектировались под конкретные выборки (JOIN'ы, пакетные запросы), поэтому там 2 запроса. Гибкость клиента куплена ценой потери контроля над числом походов за данными.

**Лечение:** **DataLoader** (batch loading): резолвер не ходит в БД, а ставит ключ в очередь; после разбора запроса DataLoader одним пакетным запросом (`WHERE id IN (...)`) грузит всё + кэширует на время запроса (request-scoped cache). Плюс: тяжёлые связи агрегировать JOIN'ами в самих резолверах.

**Связь с проектом.** `ProductItemsDataFetcher` с `@DgsData(parentType = "Product", field = "items")` ходит в `FridgeItemService` на **каждый** продукт в списке: `products(first: 50) { items { ... } }` = 1 + 50 вызовов. Это и есть наш N+1: на in-memory-хранилище дёшево, в проде — DataLoader по `productId` (`findByIds`).

### 4.3 (2 балла). «Схему GraphQL — в тот же Maven-модуль, что и REST-контроллеры». В чём опасность? Два сценария эксплуатации.

**Опасность (по существу).** Два разных контракта с разными моделями на одном коде:
- **Расходится модель ошибок:** REST — статусы + `ErrorResponse` через `@ControllerAdvice`; GraphQL — всегда 200 + `errors`, обработка через `DataFetcherExceptionHandler`. В нашем проекте для этого уже есть два отдельных класса (`GlobalExceptionHandler` и `GraphQLExceptionHandler`) — на двух эндпоинтах это терпимо, на десятках — дублирование и расхождение правил.
- **Расходится кэширование и защита:** REST кэшируется по HTTP (ETag, CDN), GraphQL — нет; REST лимитируется по эндпоинтам, GraphQL — depth/complexity/APQ/persisted queries. Общие сервисы и общая авторизация должны обслуживать обе модели — правила начинают ветвиться по типу API.
- **Общие ресурсы:** один пул потоков, одна JVM — нагрузка одного API деградирует в другой.
- **Связанность релизов:** оба API уезжают в прод одним артефактом.

**Сценарий 1 — нагрузочный.** Мобильное приложение массово ломится в GraphQL тяжёлыми запросами (батчи, широкие выборки). Пул потоков и CPU заняты — B2B-интеграторы на REST ловят таймауты, хотя их API никто не менял. Масштабировать хочется только GraphQL-часть (отдельные инстансы, отдельные лимиты) — нельзя: один артефакт. Разделять потом = болезненный разрез общих сервисов посреди эксплуатации.

**Сценарий 2 — организационно-эволюционный.** Фронтенд-команда итерирует схему еженедельно (новые поля, новые типы), а REST v1 заморожен для внешних партнёров, которым обещан стабильный контракт на квартал. Один модуль = один релизный цикл: каждая правка схемы тянет деплой REST (регрессии, прогон контрактных тестов, откат в случае проблемы — тоже обоих). Либо команды блокируют друг друга в одном модуле. Для GraphQL-схемы и REST-контракта естественны **разные** скорости изменений — совместное проживание в одном модуле эту скорость убивает.

(Запасной сценарий — безопасность: introspection и GraphiQL нужны внутренним разработчикам, но наружу тот же сервис смотрит и REST; открыть/закрыть introspection — решение, которое затрагивает оба API сразу.)

**Как правильно:** резолверы+схема и REST-контракты — в разных модулях/слоях, общие только доменные сервисы; при разной нагрузке — вообще разные сервисы (или BFF).

### 4.4 (2 балла). HATEOAS: ссылки появляются/исчезают по состоянию. Клиент должен проверять наличие ссылки перед показом кнопки. Фундаментальная проблема для UI? Конфликт с дизайнером.

**Фундаментальная проблема.** UI по природе **статичен**, а HATEOAS отдаёт аффордансы **в рантайме, по состоянию ресурса**:
- Экран проектируется заранее: все кнопки, все disabled-состояния, тултипы, вёрстка. А «набор ссылок» становится известен только из ответа — дизайнер физически не может нарисовать состояние, которого нет в макете: **отсутствие ссылки — скрытое состояние**.
- Кнопки нельзя отрендерить до ответа сервера (зависимость от латентности).
- Число вариантов экрана = произведение состояний всех ресурсов на странице — тестировать UI становится экспоненциально тяжелее.
- И ирония: клиент всё равно кодирует знания о **rel-именах** («где-то может быть ссылка publish») — часть связности возвращается, просто в другой форме.

**Конфликт «сервер диктует действия» vs «кнопка всегда видна».** Разделение ответственности: **сервер — источник истины о том, можно ли действие** (бизнес-правила), **клиент — о том, как его изобразить** (disabled, серый, тултип). Практические решения:
1. **Сервер отдаёт ссылку всегда + метаданные доступности:**
```json
"publish": { "href": "/api/manuscripts/5/publish", "allowed": false, "reason": "MANUSCRIPT_REJECTED" }
```
Клиент рендерит кнопку disabled с тултипом из `reason`. Договорённость фиксируется в контракте.
2. **Клиентский реестр известных rel:** UI знает список rel (это часть контракта, стабильнее URL); ссылка есть — кнопка активна, ссылки нет — кнопка рисуется disabled. Компромисс: жёсткость по rel, гибкость по URL и условиям — сервер меняет бизнес-правила, не меняя UI.
3. **BFF/UI-composition слой:** переводит гипермедиа в view-model с булевыми флагами (`canPublish: false`) — UI-команда живёт по-старому, гипермедиа не протекает в компоненты.

**Честный итог для ответа.** Проблема в том, что HATEOAS выражает только «что доступно **сейчас**», а UI требует «что существует **в принципе** и как выглядит его недоступность». Значит, контракт должен дополнительно выражать доступность явно (метаданные ссылки) либо нужен адаптирующий слой. Это ещё одно проявление цены HATEOAS из Б3.2.

### Как не звучать «как нейронка» на пересдаче
- Отвечай **скелетом**: термин → механика своими словами → компромисс → «вот как это у меня в проекте». Не заучивай тексты — заученные абзацы и есть тот самый запах.
- Вплетай свой код: `EventEnvelope` с `eventId`, два обработчика ошибок, sealed `ProductEvent`, `@Lazy` из-за циклической зависимости сервисов, `ConcurrentHashMap` вместо БД. Никто не отвечает так, кроме автора кода.
- Признавай компромиссы своих решений («в моём проекте audit-сервис без DLQ и manual ack — в проде я бы добавил») — инженеры так и говорят.
- Если не помнишь точно — рассуждай вслух от общей идеи (шесть идей из раздела 0): это ровно то «умение рассуждать», которое преподаватель и проверяет.
