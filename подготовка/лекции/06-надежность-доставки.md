# Лекция 6. Надёжная доставка: confirms, acks, DLQ, Transactional Outbox

> В прошлой лекции события просто летали. Теперь главный вопрос реальных систем: «что будет, если что-то пойдёт не так?». Потребитель упал посреди обработки? Сеть моргнула? Битое сообщение заблокировало очередь? И самый коварный сбой — двойная запись в БД и брокер (❗Б1.4, экзаменационная классика).

---

## 1. Контракт гарантированной доставки ❗

Надёжная доставка — **трёхстороннее соглашение**. Выучи как таблицу:

| Звено | Кто обязан | Механизм | Что гарантирует |
|---|---|---|---|
| Producer → Broker | издатель | **Publisher Confirms** | брокер получил и сохранил |
| Broker (хранение) | брокер | **durable** очереди/обменники + **persistent** сообщения | сообщение переживёт перезагрузку/сбой |
| Broker → Consumer | потребитель | **Acknowledgements (acks)** | брокер удалит только после успешной обработки |

💡 Важная логика: каждое звено закрывает свой риск. Confirms не помогут, если очередь не durable (перезагрузка брокера — и всё стёрто). Durable не поможет, если потребитель взял сообщение, упал, а брокер уже удалил (auto-ack). Гарантия — только **все три звена вместе**.

---

## 2. Publisher Confirms

По умолчанию брокер не подтверждает приём. Издатель шлёт «в пустоту» — если брокер не принял, издатель об этом **не узнает**.

Включение (application.properties):

```properties
# correlated — с отслеживанием (какое именно сообщение не дошло), simple — просто true/false
spring.rabbitmq.publisher-confirm-type=correlated
# знать, если сообщение не дошло до очереди (ушло в обменник, но не маршрутизируется)
spring.rabbitmq.publisher-returns=true
```

Callback в `RabbitTemplate` (из практики СОП 7):

```java
rabbitTemplate.setConfirmCallback((correlationData, ack, cause) -> {
    if (!ack) {
        // сообщение НЕ подтверждено брокером — ретрай/лог/алерт
        System.out.println("NACK: Message delivery failed! " + cause);
    }
});
```

`correlated`-режим позволяет через `CorrelationData` сопоставить подтверждение с конкретным сообщением — основа для outbox-релизера (раздел 5).

## 3. Acknowledgements: auto vs manual ❗

### 3.1 Почему auto-ack опасен

**По умолчанию Spring Boot подтверждает автоматически**: как только брокер **отправил** сообщение потребителю — сразу считает его обработанным и удаляет. Если твой сервис упал **после получения, но до завершения обработки** — сообщение потеряно навсегда.

### 3.2 Ручное подтверждение

```properties
spring.rabbitmq.listener.simple.acknowledge-mode=manual
# отключаем встроенные ретраи, чтобы сразу видеть работу DLQ
spring.rabbitmq.listener.simple.retry.enabled=false
```

Потребитель сам решает судьбу сообщения через канал:

```java
@RabbitListener(queues = "audit.queue")
public void onMessage(EventEnvelope envelope, Channel channel,
                      @Header(AmqpHeaders.DELIVERY_TAG) long tag) throws IOException {
    try {
        process(envelope);
        channel.basicAck(tag, false);                        // «обработал, удаляй»
    } catch (Exception e) {
        channel.basicNack(tag, false, false);                // requeue=false → в DLQ
    }
}
```

- **`basicAck`** — «успешно обработал, можешь удалять».
- **`basicNack(tag, multiple, requeue)`** — «не смог»; `requeue=true` — вернуть в очередь (ретрай), `requeue=false` — не пытаться снова → сообщение уходит в **dead-lettering**.

---

## 4. Dead Letter Queue (DLQ) ❗

### 4.1 Идея

Что делать с сообщением, которое получило nack, или у которого истёк TTL? **Dead Letter Exchange / Queue** — «очередь для мёртвых писем».

Настройка: основная очередь объявляется с аргументом «если сообщение не удалось обработать — отправь его в вот этот dead-letter-exchange»:

```java
@Bean
public Queue auditQueue() {
    return QueueBuilder.durable("my-queue")
            .deadLetterExchange("my-queue.dlx")     // куда уносят «мертвые»
            .build();
}

@Bean
public Queue deadLetterQueue() {
    return QueueBuilder.durable("my-queue.dlq").build();
}

@Bean
public DirectExchange deadLetterExchange() {
    return new DirectExchange("my-queue.dlx");
}

@Bean
public Binding dlqBinding(Queue deadLetterQueue, DirectExchange deadLetterExchange) {
    return BindingBuilder.bind(deadLetterQueue).to(deadLetterExchange).with("my-queue");
}
```

### 4.2 Что это даёт ❗

- Основная очередь **не блокируется** битым сообщением (иначе:consumer падает → requeue → снова падает → бесконечный цикл «ядовитого сообщения» и паралич очереди).
- Инженеры **изучают** проблемные сообщения в DLQ, чинят баг и **переотправляют** на обработку.
- DLQ — это мониторинговая точка: рост её глубины = алерт.

💡 Формула для устного ответа: «DLQ превращает тихий сбой (сообщение исчезло / заблокировало очередь) в громкий (сообщение лежит в отдельной очереди, на неё алерт)». Помни сквозную идею курса: **опасен тихий сбой**.

## 5. Dual Write и Transactional Outbox ❗❗ (центральный экзаменационный сюжет)

### 5.1 Проблема

Сервер сохраняет сущность в БД и публикует событие в RabbitMQ — **две операции, не объединённые транзакцией** (общей транзакции между БД и брокером не существует в принципе).

Два сценария сбоя:

| | Что произошло | Последствие | Тип сбоя |
|---|---|---|---|
| **Сбой 1** | БД сохранила, брокер недоступен → событие **потеряно** | потребители навсегда не узнают о факте: аудит неполон, статистика неверна, уведомление не ушло | **тихий**: никто не получил ошибки, расхождение не самоликвидируется |
| **Сбой 2** | Событие ушло, БД **не сохранила** | потребители видят событие о несуществующей сущности | **громкий**: источник знает об ошибке (пользователь получил 500 и повторит), потребитель может отбить фантом проверкой |

**Какой опаснее?** ❗ Рассуждение по критерию *обнаружимость и обратимость*: сбой 1 — тихий и необратимый (нужен ручной reconciliation, о котором никто не знает); сбой 2 — громкий и компенсируемый (фантом можно отбить в DLQ, операция источника повторится). **По умолчанию опаснее потеря события.** Честная оговорка на плюс: если потребители совершают необратимые действия во внешний мир (списание денег, письма клиентам) — фантом может оказаться опаснее; ответ зависит от домена.

В **твоём проекте** это ровно `ProductEventPublisher.send` с try/catch → `log.error`: сбой 1 воспроизводится командой `docker stop rabbitmq` + создание продукта.

### 5.2 Решение: Transactional Outbox

Ключевая идея: **обязательство опубликовать событие записывается в ту же БД, в той же транзакции, что и основное действие**. Атомарность обеих записей гарантирует сама СУБД.

```
                    ┌─────────────────── одна ACID-транзакция БД ───────────────────┐
                    │   INSERT INTO products (...)                                   │
                    │   INSERT INTO outbox (eventId, type, payload, rk, status)      │
                    └────────────────────────────────────────────────────────────────┘
                                        │  (коммит)
                                        ▼
              Relicher (фоновый поллер / CDC): SELECT ... FROM outbox WHERE status='NEW'
                                        │
                                        ▼  publisher confirms (лек. 6, разд. 2)
                                 RabbitMQ (exchange)
                                        │ ack от брокера
                                        ▼
                          UPDATE outbox SET status='PUBLISHED'
```

Шаги:
1. В **одной локальной ACID-транзакции**: INSERT сущности + INSERT строки в таблицу `outbox` (payload, eventId, routing key, статус NEW). Либо обе записи, либо откат — **«публикация или откат обоих действий»** из билета.
2. **Релизер** (отдельный фоновый процесс/поток, либо CDC — Debezium, читающий изменения из WAL БД) выбирает неопубликованные строки и публикует в RabbitMQ **с publisher confirms**.
3. Получив подтверждение брокера — помечает строку PUBLISHED.

Что гарантируется:
- **Сбой 1 невозможен**: если транзакция закоммитилась — событие лежит в outbox на диске и рано или поздно будет опубликовано (хоть после рестарта сервиса).
- **Сбой 2 невозможен**: если транзакция откатилась — outbox-строки нет, публиковать нечего.

### 5.3 Цена: at-least-once и идемпотентность ❗

Релизер может **опубликовать дважды**: опубликовал → умер до UPDATE outbox → после рестарта увидит NEW и опубликует снова. Гарантия получается **at-least-once** (не менее одного раза), а не «ровно один раз».

**Ровно-once между БД и брокером не существует.** Поэтому потребители обязаны быть **идемпотентными**: повторная обработка события не меняет результат. Механизм — дедупликация по `eventId`: таблица обработанных ID (или уникальный индекс) — пришёл дубликат → ack без обработки.

🔗 В твоём проекте фундамент уже заложен: `EventEnvelope.metadata.eventId` (UUID) — готовый ключ дедупликации. Чего не хватает: outbox-таблицы, релизера и проверки eventId в `AuditEventListener` — вот честная «дорожная карта улучшения», которую стоит озвучивать.

### 5.4 Альтернативы и почему хуже

- **`afterCommit`-колбэк** (публиковать после коммита транзакции): убирает сбой 2 (событие не уйдёт до коммита), но между коммитом и публикацией процесс может умереть → снова потеря события, обязательство нигде не зафиксировано. Outbox сильнее тем, что обязательство **записано на диск до** публикации.
- **Транзакции RabbitMQ** (`tx.select/commit`): объединяются только с самим собой, не с транзакцией БД — проблему dual write не решают.
- **2PC / XA-транзакции**: RabbitMQ не полноценный XA-участник, а распределённые транзакции ради каждого события — производственный суицид по латентности. На практике не применяется.

## 6. Topic-маршрутизация и Fanout в экосистеме

### 6.1 Topic: разные сервисы — разные срезы (СОП 7)

Практика стройла систему из трёх потребителей:
- `demo-rest` публикует `book.created` / `book.deleted`;
- `audit-service` слушает **все** события о книгах: биндинг `book.#`;
- `statistics-service` слушает только создание: биндинг `book.created` (или `*.created`).

Один обменник, три очереди, три среза потока. Издатель про всё это не знает.

### 6.2 Fanout: всем одно и то же (СОП 9)

Задача: после синхронного gRPC-расчёта в analytics-service основной сервис публикует `ReportGenerated`, и **три** сервиса (Notification, Billing, Audit) должны получить **одно и то же** сообщение.

❗ Почему не одна очередь на всех: **очередь отдаёт сообщение одному consumer'у** (балансировка, а не копирование) — «сообщение досталось бы только одному счастливчику». Решение — **Fanout exchange**: каждая очередь получает копию:

```
                     ┌─► notification.queue ─► NotificationService
ReportGenerated ─► fanout exchange
                     ├─► billing.queue ─────► BillingService
                     └─► audit.queue ───────► AuditService
```

Гибрид из практики: **gRPC для синхронного** (быстрый расчёт внутри кластера, строгая типизация) + **Fanout для асинхронного** (событие всем) — так и живут реальные системы (пример из практики: Uber, Netflix).

## 7. Сводка «кто за что отвечает»

| Компонент | Конфигурация | Защищает от |
|---|---|---|
| Издатель | `publisher-confirm-type=correlated` | молчаливой потери при отправке |
| Брокер | durable exchange + durable queue + persistent message | потери при перезагрузке |
| Потребитель | `acknowledge-mode=manual` + basicAck/basicNack | потери при падении посреди обработки |
| Очередь | `deadLetterExchange` аргумент | паралича ядровитым сообщением |
| Архитектура | Transactional Outbox | dual write (сбой 1 и 2) |
| Потребитель | дедупликация по eventId | дубликатов at-least-once |
