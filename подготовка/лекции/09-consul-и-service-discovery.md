# Лекция 9. Consul и Service Discovery

> Микросервисы дают масштабирование, переиспользование и свободу технологий — и цену: «сложность межсервисного взаимодействия, управления конфигурацией и сегментации сети». Как только сервисов становится десятки и они меняют адреса, умирают и переезжают — вручную конфигурировать их друг для друга невозможно. Решение — Service Registry. Consul — его промышленная реализация + service mesh.

---

## 1. Проблема (история из лекции) ❗

Магазин работает на **тысяче серверов** приложений за **двумя балансировщиками**. Нужно нарастить мощность — добавили ещё тысячу серверов. Что дальше?

> «Нужно пойти в настройки балансировщика и **вписать там руками** адреса новых машин».

Можно разок напрячься. А если балансировщиков **500**, а серверов **100 000**? И они «меняют адреса, умирают, переезжают»?

**Вывод:** ручное управление адресами не масштабируется вообще.

---

## 2. Решение: Service Registry / Service Discovery ❗

### 2.1 Идея

**Service Discovery (SD) / Service Registry** — специальный **журнал (реестр)**, в который серверы и компоненты инфраструктуры **сообщают о своих адресах и состоянии**, как только появляются в кластере. Все, кому нужен список живых серверов, узнают его из этого журнала.

Принципы шаблона **«Service Registry»**:
1. **Метаданные**: перед регистрацией определяются данные идентификации — имя сервиса, версия, IP, порт и др.
2. **Регистрация**: сервис сам отправляет метаданные в реестр (self-registration; или это делает сторонний механизм — third-party registration, например, платформа сама регистрирует контейнеры).
3. **Health-check'и / heartbeat**: регистрация предполагает **периодическое обновление** — так реестр знает, кто жив.
4. **Обнаружение**: чтобы соединиться с другим сервисом, сервис сначала спрашивает реестр о его адресах и состоянии.

### 2.2 Как это выглядит в истории с балансировщиком ❗

1. Каждому новому серверу при развёртывании задают адрес Service Discovery.
2. Сервер шлёт: «Привет, я сервер приложения, я готов к работе, вот мой адрес».
3. SD принимает такие запросы **от любых инфраструктурных компонентов** и всегда может сказать, какие серверы есть, что делают, где живут.
4. **Балансировщик вместо своих конфигов раз в N секунд запрашивает у SD список живых серверов** — и распределяет нагрузку по всем, включая новые.

И бонус: в SD можно «запихивать любые компоненты инфраструктуры» — БД, кэши, микросервисы, резервные машины. Мониторинг хочет знать наблюдаемых, приложения хотят знать свои СУБД — все получают живое состояние. Изменения — не только появление, но и смерть/переезд серверов.

### 2.3 Существующие решения

**ZooKeeper** (старейший), **etcd** (движок Kubernetes), **Consul** (HashiCorp), **Kubernetes** (свой встроенный SD).

---

## 3. Consul: история и сущность

- Представлен **HashiCorp в 2014** как решение для обнаружения сервисов и конфигурации — в эпоху, когда облака и SOA стали мейнстримом, а маршрутизация и обработка сбоев — болью.
- **Революция: DNS-based service discovery + надёжное обнаружение сбоев.** Сервис регистрируется — и доступен по **DNS-записи**: `frontend.service.consul`. Упал — Consul быстро удаляет его из DNS.
- Health-check'и и распределение информации — через **gossip-алгоритм (библиотека Serf)**.
- С приходом Docker/Kubernetes развился в **service mesh**: 2018 год — **Consul Connect** (sidecar-прокси, шифрование трафика), затем полноценный mesh: безопасность, наблюдаемость, надёжность, управление трафиком.

### 3.1 Три лица Consul (запомнить!) ❗

| Функция | Что это |
|---|---|
| **Service Discovery** | реестр сервисов + DNS (`*.service.consul`) |
| **Key/Value store** | хранилище конфигурации (ключ-значение) |
| **Service mesh** | управление трафиком между сервисами через sidecar-прокси (Envoy) |

---

## 4. Архитектура Consul ❗❗

Три компонента: **Consul серверы**, **Consul клиенты**, **sidecar-прокси**. Прокси общаются с локальными клиентами, клиенты — с серверами.

```
┌─ узел A ──────────────┐      ┌─ узел B ──────────────┐
│ backend ─┬─ sidecar   │      │ frontend ─┬─ sidecar  │
│          └─ client ───┼──────┼───────────└─ client ──┼───┐
└───────────────────────┘      └───────────────────────┘   │
                                          ▲                │ gossip/RPC
                                          ▼                ▼
                        ┌── Consul servers (3–5, Raft) ──┐
                        │ каталог, конфиги, health-статусы│
                        └─────────────────────────────────┘
```

### 4.1 Consul серверы ❗

- **База данных всей системы**: каталог всех узлов и сервисов, конфигурации, статусы здоровья.
- В продакшене — **несколько серверов (3 или 5)** для высокой доступности: один умер — остальные работают, данные не теряются.
- **Всегда нечётное количество** ❗: при чётном отказоустойчивость не растёт (кворум всё равно требует большинство: из 4 серверов большинство = 3, выносливость = 1 отказ, как и у 3), лишний сервер — впустую потраченные ресурсы.
- Для работы требуется **большинство (кворум)** работающих серверов: из трёх — два; из четырёх — три.

**Raft** ❗ — протокол согласованности:
- **выбор лидера**: один сервер главный, **все записи идут через него** — предотвращает конфликты одновременной записи разных значений на разные серверы;
- **репликация**: записи копируются с лидера на остальных — данные целы при смене лидера.

Физически данные на диске (в Kubernetes — StatefulSet + PersistentVolumes; на VM — тома, переживающие перезагрузку; прод: отдельный узел под каждый сервер).

### 4.2 Consul клиенты ❗

- Запускаются **на каждом рабочем узле** кластера.
- Задача: **следить за здоровьем сервисов своего узла** (и узлов) и постоянно докладывать серверам, чтобы каталог был актуален.
- ❗ Почему бы серверам самим не проверять всех? **Централизованный health-check не масштабируется** до десятков тысяч узлов/сервисов. Клиент на каждом узле = **распределённая** проверка здоровья. (В Kubernetes клиенты работают как **DaemonSet** — один pod на каждый узел.)

**Serf и gossip ❗** — обнаружение сбоев узлов:
- gossip = **эпидемический алгоритм**: каждый клиент передаёт сообщения **небольшому числу случайных клиентов (по умолчанию трём)**; те — ещё по три; информация распространяется как слухи/вирус;
- клиенты постоянно проверяют друг друга; о неработающем «узнаёт весь кластер»;
- хотя теоретически распределённое обнаружение медленнее централизованного, **на практике сбой расходится по кластеру из тысяч узлов менее чем за 2 секунды**.

### 4.3 Sidecar-прокси (Envoy) ❗

- **Каждый экземпляр сервиса имеет выделенный sidecar-прокси**: перехватывает запросы к сервису и от него, выполняет правила конфигурации — **шифрование TLS**, отказ запросов от неавторизованных сервисов, наблюдаемость.
- ❗ **Сам Consul не является прокси** — он управляет прокси **Envoy** (изначально Lyft, теперь CNCF): написан на C++ (производительность, малый расход памяти), сотни функций балансировки/наблюдаемости/health-check'ов; **Consul-клиенты настраивают Envoy через его gRPC API**.
- В Kubernetes sidecar — отдельный контейнер **внутри пода** сервиса (общая локальная сеть пода); на VM — отдельный процесс рядом с каждым экземпляром сервиса.

### 4.4 Сквозной пример (из лекции) — расскажи по картинке

1. На узле стартует сервис **backend**, регистрируется со своим IP (1.2.3.4) в **локальном Consul клиенте**.
2. Клиент докладывает **серверам** → сервис попадает в каталог.
3. Запускается sidecar-прокси backend'а; открывает соединение с локальным клиентом; клиент настраивает прокси и держит соединение открытым (для будущих изменений конфигурации).
4. Сервис **frontend** на другом узле должен вызвать backend. **Локальный клиент frontend'а постоянно следит за каталогом**: как только появился экземпляр backend — серверы присылают адрес, клиент **обновляет конфигурацию прокси frontend'а**.
5. frontend делает запрос → его прокси перехватывает, знает адрес backend (1.2.3.4) → перенаправляет → на backend запрос перехватывает его прокси, **проверяет источник** (разрешено ли frontend) → пропускает к сервису.

### 4.5 DNS-режим vs service mesh ❗

- **DNS-discovery**: sidecar-прокси **не используются** — запросы идут напрямую между сервисами; следствие: **нет автоматического шифрования, наблюдаемости и управления трафиком**.
- **Service mesh**: весь трафик через sidecar'ы — TLS, авторизация, метрики.

И уникальность Consul среди mesh'ей (Istio, Linkerd): **control plane может работать полностью независимо от Kubernetes** — если у тебя кластер VM, Kubernetes не обязателен.

### 4.6 Запуск для разработки

```bash
docker pull hashicorp/consul:1.19
docker run -d -p 8500:8500 -p 8600:8600/udp --name=my-consul \
  hashicorp/consul:latest agent -server -ui -node=server-1 \
  -bootstrap-expect=1 --client=0.0.0.0
# UI: http://localhost:8500
```

Один агент `-server` — только для теста (прод: 3–5!).

## 5. Как Consul вписывается в остальной курс ❗

| Связь | Как |
|---|---|
| **REST, недостаток «клиент узнает о падении не скоро»** (лекция 1) | health-check'и Consul убирают мёртвые адреса из выдачи |
| **gRPC клиентская балансировка** (лекция 7) | клиенту нужен живой список адресов — его даёт registry |
| **Брокер сообщений** (лекции 5–6) | другая модель развязки: не «найди адрес», а «брось в обменник». Registry для синхронных вызовов, шина — для асинхронных |
| **Correlation ID / трассировка** (лекция 10) | sidecar'ы mesh'а раздают контекст запросов между сервисами |

💡 Одним предложением: **Consul отвечает на вопрос «где живёт сервис и жив ли он», брокер — «как передать ему работу, не зная, жив ли он»**. Оба закрывают цену микросервисов из лекции 1: сложность взаимодействия и управления.
