# Лекция 1. Архитектура клиент-сервер и REST

> Основа всего курса. Из этой лекции должно остаться: почему приложения делят на звенья, что такое REST по Филдингу, зачем уровни зрелости Ричардсона, и почему HTTP-методы — это про семантику, а не про синтаксис.

---

## 1. Зачем вообще делить приложение на части

### 1.1 Веб-приложение как клиент-сервер

**Веб-приложение** — это клиент-серверное приложение, где клиентом выступает браузер, а сервером — веб-сервер.

**Архитектура «клиент-сервер»** определяет принципы организации взаимодействия в сети: есть **серверы** — узлы-поставщики специфичных функций (сервисов), и **клиенты** — потребители этих функций. Практические реализации называют клиент-серверными технологиями.

Ключевая идея, которую студенты упускают: **клиент и сервер — это роли, а не машины**. Когда один веб-сервер обращается к другому, он в этот момент — клиент. Микросервис, дёрнувший REST-эндпоинт соседа, — клиент. Это пригодится в лекции про gRPC.

### 1.2 Двухзвенная архитектура (2-tier)

Все три базовых компонента — представление, прикладная логика, управление данными — распределяются между **двумя** узлами: клиентом и сервером. Сервер отвечает на запросы напрямую и в полном объёме.

Основные модели того, что кладут на клиента, а что на сервер:

| Модель | Кто что делает |
|---|---|
| Сервер терминалов | весь ввод-вывод рисует терминал, вся логика на сервере |
| Файл-сервер | клиент читает файлы с удалённого сервера и сам всё обрабатывает |
| Сервер БД | логика на клиенте, данные обслуживает СУБД («удалённое представление данных») |
| Сервер приложений | прикладная логика вынесена на выделенный сервер |

### 1.3 Трёхзвенная (3-tier) и многозвенная (N-tier)

**Трёхзвенная**: представление — на клиенте; прикладной компонент — на сервере приложений; управление ресурсами — на сервере БД. Части приложения могут работать на разных компьютерах и общаются сообщениями в согласованном формате.

**Многозвенная (N-tier, Multi-tier)** — расширение 3-tier: выделяются дополнительные серверы, каждый представляет свои сервисы и пользуется услугами прочих серверов своего уровня.

### 1.4 2-tier vs 3-tier — сравнение ❗

| | 2-tier | 3-tier / N-tier |
|---|---|---|
| Сложность | проще (один сервер) | сложнее |
| Надёжность | ниже — всё зависит от одного сервера | выше — функции распределены |
| Производительность | требования к одному серверу высокие | выше — задачи распределены |
| Масштабируемость | слабая | высокая |
| Безопасность | защита «целиком» | защита для каждого сервиса/уровня отдельно |

💡 Инженерный вывод, который надо уметь формулировать: **каждое звено — это цена (сеть, развёртывание, отладка), купленная за качество (гибкость, масштабирование, изоляция сбоев)**. Эта формула «сложность против гибкости» повторяется во всём курсе: микросервисы, брокер сообщений, HATEOAS, service mesh — везде одно и то же.

### 1.5 Эволюция архитектур

Традиционная цепочка выглядит так:

```
N-tier (монолит + БД + тонкий клиент)
        ↓  эпоха микросервисов
много маленьких сервисов, каждый со своей БД, общаются по сети
        ↓  serverless
код по функциям, инфраструктуру (серверы, масштабирование) берёт на себя платформа
```

Микросервисы дают: **масштабирование** (каждый сервис масштабируем отдельно), **переиспользование**, **свободу технологий**. Цена: **сложность межсервисного взаимодействия, управления конфигурацией, сегментации сети** — и именно из этой цены рождаются темы лекций 5, 6 и 9 (брокер сообщений, надёжность, Consul).

## 2. Типы серверов и «толщина» клиентов

### 2.1 Типы сервисов в сети (кратко, одним взглядом)

- **Веб-сервер** — принимает HTTP-запросы, отдаёт HTTP-ответы (Apache, IIS, NGINX). Изначально гипертекст, сейчас — любые ресурсы, включая бинарные.
- **Сервер приложений** — централизованно решает прикладные задачи; снижает требования к клиентам, упрощает управление сетью.
- **Сервер БД** — обрабатывает SQL-запросы; СУБД на сервере, к ней подключаются клиенты.
- **Файл-сервер** — хранит информацию файлами, даёт доступ + защиту.
- **Прокси-сервер** — посредник между клиентами и интернетом: защита + **кэш** часто запрашиваемого.
- **Файрвол** — фильтрует проходящий трафик.
- **Почтовый сервер** — отправка/получение почты (SMTP/POP3/IMAP).
- **Сервер удалённого доступа (RAS)** — связь с сетью по коммутируемым линиям.

❗ Запомни прокси-сервер: он — первый пример того, что **между клиентом и сервером стоят посредники**, которые могут менять поведение сети (кэшировать, фильтровать, переписывать). На экзамене это превращается в вопрос «кто ещё, кроме твоего сервера, управляет HTTP-ответом?» (см. билет про шлюз, отдающий 200 OK).

### 2.2 Тонкий, толстый и rich-клиент

| | Тонкий | Rich | Толстый |
|---|---|---|---|
| Где UI | браузер (HTML+JS) | XML-описание интерфейса (XAML/XUL/Flex) | локальное приложение |
| Где прикладная логика | **на сервере** | **на сервере** | **на клиенте** |
| Ресурсы клиента | минимальные | средние | полноценная рабочая станция |
| Обмен данными | HTML/JSON | XML (SOAP, XML-RPC) | что угодно |
| Пример | веб-банк | Thunderbird (XUL) | 1С, десктопный клиент БД |

Браузер называют **«универсальным клиентом»**: достаточно браузера — работает любое приложение.

💡 Обрати внимание на rich-клиент: логика всё равно на сервере, отличается только способ отрисовки интерфейса. Сегодняшние SPA (React/Vue) — по сути эволюция этой идеи: рендеринг на клиенте, логика и данные — на сервере.

### 2.3 Протоколы — словарь

**Протокол передачи данных** — набор соглашений логического уровня, определяющих обмен данными между программами: единообразный способ передачи сообщений и обработки ошибок. **Сетевой протокол** — правила соединения и обмена между устройствами сети.

- **TCP/IP** — базовый набор протоколов интернета; TCP — надёжная доставка с соединением, IP — адресация и маршрутизация.
- **HTTP/HTTPS** — протокол передачи гипертекста; HTTPS = HTTP поверх криптографии SSL/TLS.
- **FTP** — передача файлов; **POP3** — почта.

## 3. HTTP — язык, на котором говорит весь курс

Так как REST, GraphQL, WebSocket и gRPC-транспорт живут поверх HTTP (или рядом с TCP), зафиксируем механику.

### 3.1 Структура запроса и ответа

```
Запрос:                              Ответ:
GET /api/products/5 HTTP/1.1         HTTP/1.1 200 OK
Host: localhost:8080                 Content-Type: application/json
Accept: application/json             
                                     {"id": 5, "name": "Молоко 2.5%"}
[тело — только у POST/PUT/PATCH]
```

- **Метод** — что делаем; **путь** — к какому ресурсу; **заголовки** — метаданные (формат, кэш, авторизация); **тело** — данные.
- Ответ: **статус-код** — результат; заголовки; тело.

> ❓ **Вопрос по ходу чтения:** «Но ведь можно отправить любой метод с телом — например GET с body? Это же только семантические ограничения, принятые подходы, показавшие себя на практике?»
>
> **Ответ.** Да, интуиция верна — это семантика, а не синтаксис, **но с важной оговоркой**. RFC 9110 прямо говорит: тело GET «не имеет определённой семантики» — формально не запрещено, но и никто не обязан его понимать. А дальше в дело вступает экосистема, построенная на этой семантике:
> - кэши и прокси имеют **право** выбросить тело GET при пересылке;
> - часть серверов/фреймворков отвергает GET с телом ошибкой;
> - классический контрпример: Elasticsearch API строил запросы как GET с телом — и это регулярно ломалось о прокси, пришлось добавлять дублирующие POST-варианты (`_search` доступен и через `POST`).
>
> Инженерный вывод: полагаться на неопределённое поведение = контракт на песке. «Практика, показавшая себя» здесь — это не вкусовщина, а совместимость с посредниками (прокси, кэши, балансировщики), которых ты не контролируешь. Тело GET работает «у тебя на ноуте» и ломается у первого нетипичного прокси на пути.

### 3.2 Методы и их свойства

| Метод | CRUD | Идемпотентен? | Безопасен (не меняет состояние)? |
|---|---|---|---|
| GET | read | да | да |
| POST | create | **нет** | нет |
| PUT | update (замена целиком) | да | нет |
| PATCH | update (частично) | нет по стандарту | нет |
| DELETE | delete | да | нет |

**Идемпотентность** — повторный вызов даёт тот же результат, что и первый. `PUT /books/5` с одним и тем же телом хоть 100 раз — состояние одно и то же. `POST /books` — 100 раз = 100 книг.

> ❓ **Вопрос по ходу чтения:** «Как так получается, что PUT идемпотентен, а PATCH — нет?»
>
> **Ответ.** Всё в определении самого метода:
> - **PUT** = «установи состояние ресурса равным X (целиком)». X в запросе и **не зависит от текущего состояния**. Применил дважды — состояние всё равно X: `f(f(s)) = f(X) = X`. Идемпотентность встроена в семантику полной замены.
> - **PATCH** = «примени изменение, вычисляемое **относительно текущего состояния** (delta)». Пример неидемпотентного патча: `{"op": "add", "path": "/tags", "value": "sale"}` — каждое применение добавляет ещё один элемент; то же с «инкремент количества». `f(f(s)) ≠ f(s)`.
>
> Нюанс на плюс (любят спрашивать): PATCH **может быть** идемпотентным, если патч выражен абсолютно — `{"name": "Новое"}` — «set», а не «modify». Метод не *гарантирует* идемпотентность (RFC 5789 формулирует именно так), поэтому клиент обязан считать PATCH неидемпотентным и не повторять его вслепую. Практический вывод: автоматические ретраи PATCH без защиты (ETag/If-Match, версия сущности) — источник дублей.
>
> **«Абсолютный» vs «относительный» патч — на примерах.** Аналогия с термостатом: «сделай 20°» — повторишь хоть 10 раз, будет 20°; «добавь 2°» — каждое повторение греет дальше. Так и с патчем:
>
> ```jsonc
> // ОТНОСИТЕЛЬНЫЙ (delta): значение вычисляется от текущего состояния.
> // Результат зависит от того, сколько раз и в каком порядке применяют.
> PATCH {"quantity": "+5"}                        // количество +5 → неидемпотентно
> [{"op": "add", "path": "/tags", "value": "sale"}]  // добавить в массив → неидемпотентно
> ```
>
> ```jsonc
> // АБСОЛЮТНЫЙ (set): в запросе — ЦЕЛЕВОЕ значение, не зависящее от текущего состояния.
> // Результат один и тот же при любом числе повторов → идемпотентно.
> PATCH {"quantity": 5}                            // «количество = 5»
> [{"op": "replace", "path": "/name", "value": "Кефир"}]  // «имя = Кефир»
> ```
>
> Критерий одним предложением: **патч абсолютен, если из тела запроса однозначно читается итоговое состояние поля, не глядя на текущее состояние ресурса**. Твой `PatchProductRequest` — абсолютный (все ветки «set»): даже `{"category": null}`... точнее «category отсутствует = не трогать» — повторная отправка ничего не портит. Неидемпотентным его делает только логика «модифицируй относительно текущего».

💡 Это свойство критично для лекций 5–6: в асинхронных системах с гарантией **at-least-once** дубликаты сообщений неизбежны, и единственная защита — **идемпотентные потребители**. Запомни этот мостик.

### 3.3 Статус-коды

Пять классов:

| Класс | Смысл | Примеры |
|---|---|---|
| 1xx | информационные | **101 Switching Protocols** (рукопожатие WebSocket, лекция 8!) |
| 2xx | успех | 200 OK, **201 Created** (+ заголовок Location), **204 No Content** |
| 3xx | перенаправление/кэш | 301, 304 Not Modified |
| 4xx | **ошибка клиента** | 400 Bad Request, 401 Unauthorized (не аутентифицирован), 403 Forbidden (не уполномочен), **404 Not Found**, 405, 409 Conflict, 422 |
| 5xx | **ошибка сервера** | 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable |

❗ Экзаменационная деталь: 401 vs 403 — «кто ты?» против «я знаю, кто ты, но тебе нельзя». И 502 Bad Gateway — статус, который ставит **посредник**, а не твой сервер: первое доказательство того, что статус-коды управляются не только приложением.

## 4. REST: архитектурный стиль

### 4.1 Откуда он взялся

**REST (Representational State Transfer, «передача представления состояния»)** — архитектурный стиль, описанный **Роем Филдингом в 2000 году в диссертации** (один из авторов протокола HTTP). Это не стандарт и не протокол — набор принципов, поверх HTTP/URL/JSON/XML. REST API вытеснил SOAP и WSDL и стал самым распространённым способом организации API.

REST позволяет получать и модифицировать данные и состояния удалённых приложений HTTP-вызовами через сеть.

### 4.2 Принципы REST ❗ (выучить все семь, уметь объяснить каждый)

1. **Client-Server** — отделение клиента от сервера. Код запросов — у клиента, код доступа к данным — у сервера. Даёт независимую эволюцию сторон и масштабируемость хранения.
2. **Stateless** — сервер не хранит состояние клиента между запросами. Каждый запрос самодостаточен: вся нужная информация в нём самом (токен в заголовке, а не «сессия на сервере»). Следствие: любой сервер кластера может обработать любой запрос → балансировка без «липких сессий».
3. **Cacheable** — в ответе явно указано, можно ли кэшировать данные (Cache-Control, ETag). Клиент/прокси могут переиспользовать кэш вместо повторных запросов.
4. **Uniform Interface** — единообразие интерфейса: данные запрашиваются через стандартные протоколы по предсказуемым URL. Внутри принципа — разделение **ресурса** (что) и **представления** (как отдаём: JSON, XML).
5. **Layered System** — сервера могут стоять на разных уровнях; каждый взаимодействует только с ближайшими. Клиент не знает и не должен знать, говорит ли он с реальным сервером, прокси или балансировщиком.
6. **Code on Demand** (опциональный) — сервер может отправлять исполняемый код (например, JS-скрипт) — расширяет функциональность клиента по требованию.
7. **Starting with the Null Style** — клиент знает только одну точку входа; дальнейшие возможности обеспечиваются сервером. ❗ Это фундамент HATEOAS (лекция 2): из нулевого знания клиент «наращивает» знание из ответов сервера.

### 4.3 Уровни зрелости Ричардсона (Richardson Maturity Model) ❗❗

Стандартный экзаменационный вопрос. Модель показывает, насколько API «RESTовый»:

| Уровень | Что умеет | Пример |
|---|---|---|
| **0** | Один URL на всё, всегда POST | `POST /api {"action": "getAuthor", "id": 1}` |
| **1** | Отдельные URL на ресурсы | `GET /authors/1` |
| **2** | HTTP-глаголы + коды ответов | `DELETE /authors/1 → 204 No Content` |
| **3** | HATEOAS — ссылки в ответе | ответ содержит `_links` |

JSON-иллюстрация уровней 1 и 3:

```json
// Уровень 1: данные есть, навигации нет
{ "id": 1, "firstName": "Лев" }

// Уровень 3: сервер подсказывает, куда можно идти дальше
{
  "id": 1, "firstName": "Лев",
  "_links": {
    "self":       { "href": "http://localhost:8080/api/authors/1" },
    "books":      { "href": "http://localhost:8080/api/books?authorId=1&page=0&size=20" },
    "collection": { "href": "http://localhost:8080/api/authors?page=0&size=20" }
  }
}
```

**Ключевая фраза уровня 3:** «Клиент знает наизусть **один** URL. Все остальные получает из `_links`».

💡 Здесь спрятан главный конфликт курса, который преподаватель любит разворачивать в билетах: HATEOAS **переносит знание структуры API с клиента на сервер**. Клиенту проще — серверу дороже (лекция 2 раскроет цену).

### 4.4 Методы REST API и CRUD

Четыре метода покрывают стандартный набор действий над данными:

- **GET** — получение информации/списка
- **POST** — добавление
- **PUT** — регулярное обновление (замена)
- **DELETE** — удаление

Взаимодействие **синхронное**: клиент ждёт ответа. Это важно как контраст с лекцией 5: брокер сообщений — **асинхронная** модель, где отправитель не ждёт получателя.

### 4.5 Форматы сообщений

REST передаёт не только текст: XML, JSON, Protobuf (бинарный — о нём лекция 7). Формат фиксируется заголовками `Content-Type`/`Accept`.

### 4.6 Плюсы, минусы, сценарии ❗

**Преимущества:**
- простота реализации;
- широко используемый «стандарт» (де-факто);
- надёжный;
- технологически «агностик» — клиент на любом языке;
- удобное тестирование (Postman, Insomnia).

> ❓ **Три уточнения к преимуществам** (твои вопросы по ходу чтения):
>
> **«Надёжный — за счёт синхронности?»** — Да, по сути. Надёжность REST = два слоя: (1) TCP под HTTP — гарантированная доставка байтов с подтверждениями и ретрансмиссиями; (2) синхронная модель «запрос-ответ»: **на каждый запрос есть явный ответ со статусом** — отправитель всегда знает результат (дошло/ошибка/таймаут). Сравни с fire-and-forget отправкой «в никуда». Цена этой надёжности — задержка (первый из недостатков ниже).
>
> **«Технологически агностик — за счёт общих форматов?»** — Да: транспорт — HTTP (есть в любой ОС и языке), форматы — открытые стандарты (JSON/XML). Чтобы дёрнуть REST API, достаточно `curl`; никакого SDK, компилятора схем и рантайма. Контраст: gRPC требует сгенерированных заглушек и protobuf-библиотек на каждой стороне.
>
> **«Удобное тестирование — за счёт человекочитаемости?»** — Да: текстовый протокол + текстовые тела можно читать глазами, тестировать из браузера (GET), curl'а, Postman'а без единой строчки кода. С бинарным gRPC отладка превращается в «нужен grpcurl + .proto и всё равно видно мусор» (лекция 7 назовёт это в критике).

**Недостатки:**
- HTTP медленный, надёжность добавляет задержку (каждый запрос — рукопожатия, заголовки);
- таймауты: сервер думает долго — соединение закрывается;
- если сервер упал, клиент узнает не скоро (особенно без health-check'ов — мостик к Consul, лекция 9);
- **over-fetching** (отдаём больше полей, чем нужно) и **under-fetching** (нужны новые эндпоинты под каждый экран) — из этих двух слов рождается GraphQL, лекция 3.

> ❓ **Два вопроса к недостаткам** (твои по ходу чтения):
>
> **«Как жить с таймаутами, если запрос честно долгий, но хочется остаться на REST?»** — Классический паттерн **асинхронный REST**:
> 1. Клиент шлёт `POST /reports` → сервер **сразу** отвечает `202 Accepted` + заголовок `Location: /reports/42/status` (работа принята, идёт в фоне).
> 2. Клиент **поллит** `GET /reports/42/status`.
> 3. Готово → `303 See Other` на результат или готовое тело в статусе; альтернатива — **webhook**: клиент при старте передаёт callback-URL, сервер сам дёргает его по завершении.
>
> Выкручивание таймаутов (read timeout клиента, idle timeout балансировщика) — костыль: латентность и занятые соединения остаются. А куда уходит «фоновая» работа? Обычно в очередь — мостик к лекции 5: тяжёлая задача кладётся брокеру, воркер обрабатывает, статус — в БД.
>
> **«Сервер упал — клиент узнает не скоро. Почему? Только по таймауту?»** — Да: без health-check'ов падение сервера проявляется **только в момент обращения** — connection refused, таймаут или 5xx. Если в этот момент никто не обращается — никто и не знает. Хуже: балансировщик со статическим конфигом **продолжит слать трафик в мёртвый инстанс**, пока запросы туда не начнут падать. Отсюда решение из лекции 9: Consul с активными health-check'ами выгоняет мёртвые адреса из выдачи — трафик перестаёт идти туда **до** того, как клиенты пострадают.

**Сценарии использования:** CRUD, resource/data-driven сервисы; **когда REST лучше GraphQL**: простые CRUD с предсказуемой структурой, публичные API, **когда HTTP-кэширование критично** (CDN, прокси), опыт команды.

> ❓ **Два вопроса к сценариям** (твои по ходу чтения):
>
> **«Почему для публичных API не GraphQL?»** — Три причины:
> 1. **Поверхность атаки.** Внутренним GraphQL-клиентом управляет твоя же команда (запросы предсказуемы, можно persisted queries). Публичные потребители шлют **что угодно** → обязательны depth/complexity-лимиты, cost analysis, белые списки запросов — инфраструктура защиты, которую надо построить и поддерживать (лекция 3, раздел 7).
> 2. **HTTP-кэш и CDN не работают** (см. следующий вопрос) — для публичного API с большим трафиком это потеря главного бесплатного ускорителя.
> 3. **Порог входа и стабильность.** Публичный API — это чужие разработчики: им проще стандартный HTTP + OpenAPI-документация + лимитирование «на эндпоинт». Схема GraphQL становится публичным контрактом, который нельзя менять без ломания незнакомых тебе клиентов.
>
> Контрпример для эрудиции: **GitHub GraphQL API** — публичный и живой; но он потребовал серьёзных вложений в защиту и рассчитан на подготовленных потребителей. Правило: GraphQL публичен там, где гибкость для потребителя важнее простоты эксплуатации для провайдера.
>
> **«А разве у других технологий нет кэширования? У GraphQL же есть кэш»** — Важно разделять **три уровня** кэша:
>
> | Уровень | Пример | Кто использует | Работает для GraphQL? |
> |---|---|---|---|
> | **Сетевой HTTP-кэш** | браузер, прокси, **CDN** — по URL + Cache-Control | все клиенты мира, **бесплатно и прозрачно** | **нет**: все запросы — POST на один и тот же `/graphql`, посреднику нечего различать по URL; Cache-Control неприменим «по ресурсам» |
> | **Клиентский кэш приложения** | Apollo/Relay cache | один экземпляр одного приложения, в памяти | да — но это кэш нормализованных объектов в клиенте: **не разделяется** между пользователями и не разгружает сервер |
> | **Кэш текстов запросов** | Persisted Queries | клиент+сервер | да, но кэшируется **текст запроса** (экономия трафика и парсинга), а не ответы |
>
> Итог: «у GraphQL есть кэширование» = клиентский кэш внутри приложения. Но **сетевой** кэш — который бесплатно отгружает ответы миллионам пользователей с CDN-края, не дотягиваясь до твоего сервера, — это эксклюзив URL-ориентированного GET, то есть REST. gRPC по той же причине (POST-подобная семантика) сетевого HTTP-кэша тоже лишён.

### 4.7 Лучшие практики и инструменты

- HTTPS всегда;
- спецификация: **OpenAPI (Swagger)**, Stoplight;
- валидация схемы: JSON Schema;
- тестирование: **Postman**, Insomnia;
- как можно больше разнообразных HTTP-кодов (а не «всё 200/500»).

> ❓ **Три вопроса к best practices** (твои по ходу чтения):
>
> **«HTTPS всегда — почему? Чем отличается от HTTP?»** — HTTPS = HTTP **поверх TLS**. Три добавки:
> 1. **Шифрование** — конфиденциальность: никто на пути (Wi-Fi, провайдер, прокси) не читает тела и заголовки — а там `Authorization: Bearer ...`, токены, персональные данные в каждом запросе.
> 2. **Целостность** — посредник не может подменить ответ или вставить своё.
> 3. **Аутентификация сервера** — сертификат доказывает, что ты говоришь именно с `api.example.com`, а не с подставным узлом.
>
> Технические отличия: рукопожатие TLS перед HTTP-запросом (лишняя латентность на старте, лечится keep-alive и переиспользованием соединений), порт 443 вместо 80, сертификаты (Let's Encrypt — бесплатно). Почему «всегда»: браузеры метят http как «Not Secure», HTTP/2 у браузеров фактически только по TLS, а токен в открытом http на публичном Wi-Fi перехватывается за секунды.
>
> **«JSON Schema — это что?»** — Стандарт (json-schema.org) для **описания и валидации структуры JSON-документа**: типы, обязательные поля, ограничения значений.
> ```json
> {
>   "type": "object",
>   "required": ["name"],
>   "properties": {
>     "name":     { "type": "string", "maxLength": 100 },
>     "category": { "type": ["string", "null"] }
>   }
> }
> ```
> Применение: валидация запросов/ответов (в тестах и шлюзах), генерация документации и кода, проверка контрактов. Разница с OpenAPI: **OpenAPI описывает весь API** (эндпоинты, методы, коды ответов), а формы отдельных JSON-документов внутри него выражаются как раз в формате JSON Schema. В Java-мире ту же нишу занимает Bean Validation (`@NotBlank`, `@Size`) на DTO — аннотации вместо внешней схемы.
>
> **«Разнообразные коды — это RFC?»** — Да: RFC 9110 (HTTP Semantics) — реестр статус-кодов. Смысл практики: **точный код = машинночитаемая инструкция** для клиента и инфраструктуры. `429 Too Many Requests` → «ретрай с Retry-After», а не «баг»; `503` → «временно, попробуй позже»; `409 Conflict` → «конкуренция за ресурс»; `422` → «данные не проходят семантическую валидацию». «Всё 200/500» отбирает у клиента возможность реагировать по-разному, а у мониторинга — считать реальные метрики.

## 🔍 Разбор твоих ответов (первое прочтение, 22.09)

Ты ответил на вопросы 1–4, 6–8. Разбор по пунктам — сверься и дочитай, где были пробелы.

**1. Клиент и сервер — роли.** ✅ Верно по сути. Уточни формулировку: роль определяется **в рамках одного взаимодействия** — кто инициирует запрос, тот в этом взаимодействии клиент; кто отвечает — сервер. Твой пример (межсервисное обращение) — правильный.

**2. 3-tier vs 2-tier.** ⚠️ Почти. Масштабируемость — да. Но «проще дебажить» — **наоборот**: больше звеньев = больше сетевых хопов, сложнее трассировка (поэтому и придумали Correlation ID — лекция 10). Три преимущества из лекции: **гибкость/масштабируемость, безопасность (изоляция уровней), производительность (распределение задач)**. Цена — точнее так: **дополнительные сетевые вызовы (латентность) и сложность развёртывания/отладки**.

**3. Stateless и балансировка.** ✅ Отлично — суть схвачена: нет «липких сессий», балансировщик может отправить запрос любого клиента на любой инстанс и распределять равномерно. Добавь: упавший инстанс не «теряет» сессии пользователей — следующий запрос просто пойдёт на живой.

**4. Семь принципов REST.** ⚠️ Суть назвал, но **вперемешку и не по именам** — на экзамене спрашивают именно имена. Канонический список для сверки: **Client-Server, Stateless, Cacheable, Uniform Interface, Layered System, Code on Demand, Starting with the Null Style**. Твоя формулировка «единая точка входа» — это Null Style; «разделение того, что отдаём и как» — это Uniform Interface (точнее: разделение ресурса и представления). Выучи пары «имя → суть».

**5. Ричардсон — запрошенный пример «4 запроса × 4 уровня».** Вот он, запоминай на продукте `Молоко` (id=5):

| Операция | Уровень 0 | Уровень 1 | Уровень 2 | Уровень 3 |
|---|---|---|---|---|
| создать | `POST /api {"action":"createProduct", "name":"Молоко"}` → 200 | `POST /products {"name":"Молоко"}` → 200 | `POST /products {"name":"Молоко"}` → **201 + Location: /products/5** | то же + тело с `_links` (self, collection) |
| прочитать | `POST /api {"action":"getProduct", "id":5}` | `GET /products/5` → 200 | `GET /products/5` → 200 (или **404**, если нет) | то же + `_links`: self, `items` на суб-ресурс |
| обновить | `POST /api {"action":"updateProduct", ...}` | `POST /products/5 {"name":"Кефир"}` | `PUT /products/5 {...}` → 200 | то же + `_links` |
| удалить | `POST /api {"action":"deleteProduct", "id":5}` | `POST /products/5/delete` | `DELETE /products/5` → **204 No Content** | то же + до удаления в `_links` есть `self`, после — нет |

Пойми логику переходов: **0→1** — у каждого ресурса свой URL (но глагол один, POST); **1→2** — правильные HTTP-глаголы и честные коды (201/204/404 вместо «всегда 200»); **2→3** — в каждый ответ сервер вкладывает ссылки на возможные следующие действия. Уровень 3 = уровень 2 + HATEOAS.

**6. Идемпотентность и брокеры.** Определение и методы ✅ (GET/PUT/DELETE + HEAD/OPTIONS; POST — нет; PATCH — не гарантирована, см. ответ в разделе 3.2). **Почему это важно брокерам — объясняю:**
- В лекции 6 гарантией доставки будет **at-least-once**: брокер и потребитель могут не успеть договориться об обработке (потребитель обработал, упал до подтверждения — брокер после рестарта доставит **то же сообщение снова**). Дубликаты — не авария, а штатный режим.
- Теперь представь твоего consumer'а, который обрабатывает `ProductEvent.Created`: обработка №1 — уменьшил счётчик «продуктов на складе»; дубликат №2 — уменьшил ещё раз. Данные **испорчены** без всякой ошибки в коде.
- Защита — **идемпотентный потребитель**: результат обработки не зависит от числа повторов. Механика: дедупликация по `EventEnvelope.metadata.eventId` (хранить обработанные ID; дубликат — ack без обработки) или идемпотентные операции («upsert» вместо «insert», «set X» вместо «increment»).
- Формула: **at-least-once доставка → неизбежные дубликаты → выживают только идемпотентные потребители.**

**7. 502.** ⚠️ Частично. Поправка: дело не в том, что «браузер должен возвращать 5хх». Класс 5xx — «ошибка на стороне сервера», но **502 Bad Gateway конкретно ставит посредник** (nginx, API Gateway, балансировщик): «я получил запрос, передал его бэкенду — а он недоступен или ответил мусором». То есть код сгенерирован **не твоим приложением** — твой сервис вообще мог быть мёртв, а 502 клиенту выставил стоящий перед ним шлюз. Отсюда вывод билета Б1.1: кодами ответа управляет вся цепочка, а не только твоё приложение.

**8. Сценарии REST vs GraphQL.** Недостатки ✅ (заголовки/метаинформация на каждый запрос + фиксированная форма ответа без гибкости — это over/under-fetching). Сценарии: «стабильная структура» — ✅. «Публичный API — но не уверен почему» — теперь уверен, смотри развёрнутый ответ в разделе 4.6: защита от произвольных запросов, неработающий CDN-кэш, порог входа для чужих разработчиков.
