# Лекция 10. Эволюция контрактов и наблюдаемость

> Финальная лекция собирает всё воедино: API не статичны — они меняются, и вопрос «как менять без поломок» — самый практический вопрос всей дисциплины. Плюс «обвязка» production-системы из практик СОП 5 и 12: Correlation ID, MDC, распределённая трассировка, метрики. Здесь же — два экзаменационных сюжета: миграция контракта при смене фреймворка (❗Б2.4) и переименование поля с валидацией (❗Б3.3).

---

## 1. Теория эволюции API

### 1.1 Какие изменения ломают клиентов

| Изменение | Ломает? | Почему |
|---|---|---|
| Добавить **новое поле** в ответ | нет | толерантные клиенты игнорируют неизвестное |
| Добавить **новый эндпоинт** | нет | старые пути на месте |
| Добавить **опциональное поле** в запрос | нет | старые клиенты его не шлют — это ок |
| **Переименовать** поле | **да** | клиент шлёт старое имя / не находит новое |
| **Удалить** поле или эндпоинт | **да** | клиент читает несуществующее / ловит 404 |
| Сделать опциональное поле **обязательным** | **да** | старые клиенты не шлют — ловят 400 |
| Сменить **тип** (number → string) | **да** | парсинг/валидация падают |
| Сменить **семантику** без смены формы | **да, страшнее всего** | всё «работает», смысл искажён |

Вывод: **безопасное изменение — аддитивное** (добавление). Всё остальное — ломающее и требует протокола миграции.

### 1.2 Протокол: аддитивность → депрекация → удаление ❗❗

Единый цикл для любого ломающего изменения:

1. **Аддитивный шаг**: добавить новое **рядом со старым** (новое поле рядом со старым, старое поле остаётся приниматься). Ничего не ломается.
2. **Депрекация**: пометить старое устаревшим (в OpenAPI — `deprecated: true`; в GraphQL — `@deprecated(reason: ...)`), **объявить дату заката**, уведомить клиентов. Сервер временно поддерживает оба варианта.
3. **Перевод клиентов**: каждый клиент мигрирует **в своём темпе**.
4. **Удаление** после окна депрекации. Формально ломающее — но к этому моменту им никто не пользуется.

**Анти-паттерн:** «переименуем всё разом в новом релизе» — гарантированная молчаливая поломка всех, кто не успел.

### 1.3 Tolerant Reader ❗

Оборотная сторона аддитивности: **клиенты обязаны быть толерантными** — не падать от неизвестных полей ответа. В Jackson:

```java
@JsonIgnoreProperties(ignoreUnknown = true)          // на классе DTO
// и/или глобально:
spring.jackson.deserialization.fail-on-unknown-properties=false
```

Если клиент сгенерирован из OpenAPI под старую схему, а сервер уже шлёт новые поля — толерантный клиент живёт, нетолерантный падает. **Правило: клиент настраивается на «читаю, что знаю; не знаю — игнорирую».**

### 1.4 Версионирование

Способы: в URL (`/api/v1/...`), в заголовке (`Accept: application/vnd.myapi.v2+json`). Смысл один: **параллельная жизнь двух контрактов** на переходный период. Дорого (двойная поддержка), поэтому: крупные версии — редкие и страшные, мелкие изменения — только аддитивные.

## 2. Миграция контракта при смене фреймворка ❗❗ (Б2.4)

### 2.1 Что случится

Контракт — Maven-модуль, интерфейсы со **Spring-аннотациями** (`@GetMapping`, `@PathVariable`, `@Valid`). Сервер реализует через `implements`. Команда решает переписать сервер на **Quarkus или Micronaut**. Клиенты используют тот же модуль.

1. **Маппинги умрут**: `@GetMapping` на интерфейсе сработает только там, где фреймворк понимает Spring-аннотации. Quarkus — нативно Jakarta REST (другие аннотации), Micronaut — свои. `implements ProductApi` не даст маппингов.
2. **Клиентам достанется лишний Spring**: контракт транзитивно тянет `spring-webmvc`, `spring-boot-starter-hateoas`, swagger-аннотации, Lombok. Клиенту не на Spring — мусор в classpath; `RepresentationModel` в DTO — Spring-тип в «чистом» модуле.
3. **Вывод:** контракт, зацепленный за фреймворк, переиспользуем только внутри этого фреймворка. Это цена решения, которое в курсе подавалось как преимущество — умей это признать.

🔗 Посмотри `smart-fridge-api-contract/pom.xml`: там `spring-webmvc`, `spring-boot-starter-hateoas`, swagger-annotations, Lombok. Твой контракт — «зацепленный». В учебном мире, где все на Spring, компромисс оправдан — умей объяснить, почему в индустрии поступили бы иначе.

### 2.2 Стратегия миграции (требования: клиенты работают, сервер меняет фреймворк, новые поля — без блокировки)

**Шаг 1. Расслоить контракт: ядро + привязки.**

```
contract-core        чистые DTO (records), исключения, enum'ы
                     зависимости: только jakarta.validation-api + jackson-annotations
     ▲                              ▲
contract-spring-web          contract-resteasy
(старые интерфейсы           (JAX-RS аннотации для
с @GetMapping, HATEOAS)      Quarkus)
```

Обе привязки реализуют одно ядро; клиенты зависят от ядра + нужной привязки. Это масштабирование принципа из лекции 2: «в контракте простой record (никаких зависимостей Spring Data)» — теперь **в ядре вообще ничего фреймворкового**.

**Шаг 2. Крупное версионирование и параллельная жизнь.** Spring-привязку **заморозить как v1**: только критические фиксы, статус deprecated + дата заката. Новый сервер живёт на v2 (Quarkus/JAX-RS). Переходный период: обе версии работают — либо новое приложение держит старые эндпоинты через адаптер, либо старое и новое приложения параллельно за общим шлюзом/балансировщиком.

**Шаг 3. Аддитивная эволюция ядра.** Новые поля — только добавлением опциональных; все клиенты — **Tolerant Reader** (1.3). Тогда «новые поля добавляются без блокировки»: никто никого не ждёт, каждый мигрирует в своём темпе. Переименования/удаления — только циклом 1.2.

**Шаг 4. Нейтральные ссылки.** HATEOAS-`RepresentationModel` из ядра убрать: в ядре — свой тип `Link`; конвертация в Spring HATEOAS — внутри spring-привязки.

**Шаг 5. Контрактные тесты** (consumer-driven: Spring Cloud Contract / Pact) — страховка, что обе привязки удовлетворяют ожиданиям клиентов весь переходный период.

## 3. Миграция валидации: переименование `isbn` → `productIdentifier` ❗❗ (Б3.3)

### 3.1 Кто сломается

Валидация через Bean Validation (`@NotBlank`, `@Size`, `@Email`), `@Valid` запускает проверку, при провале — 400 со списком `fieldErrors`. Клиент показывает пользователю: «Поле isbn: некорректный ISBN».

- **Сервер не сломается**: он честно валидирует новое поле и отдаёт новое имя в ошибках.
- **Клиент сломается — и молча**: он маппит `fieldErrors[].field` на инпут формы **строковым совпадением**. После переименования: подсказки перестают показываться (никто не заметил в QA — сценарии с ошибками редко тестируют), а если переименовано и поле запроса — старый клиент шлёт `isbn`, получает 400 «productIdentifier: не должно быть пустым» и **не может понять, что чинить**.
- Также ломаются: сгенерированные из OpenAPI клиенты, контрактные тесты, мониторинг, зацепленные за имена.

Ломается **неявное соглашение**: «имя поля в ошибке = имя поля формы = имя поля запроса».

### 3.2 Три места изменений

1. **Контракт/сервер**: DTO (`isbn` → `productIdentifier`), аннотации, OpenAPI-схема, сообщения валидации — и главное **формат ErrorResponse**: сейчас `FieldError(field, rejectedValue, message)` — имена полей и тексты хрупки.
2. **Клиент**: маппинг `field → input`, подсказки, отправляемое имя поля.
3. **Всё остальное, зацепленное за имена**: тесты, дашборды, документация.

### 3.3 Порядок миграции (главный ответ) ❗

1. **Аддитивный шаг** (ничего не ломает):
   - в `ErrorResponse.FieldError` добавить машиночитаемый **`code`** (`"REQUIRED"`, `"ISBN_INVALID"`, `"SIZE_EXCEEDED"`) — код не зависит от имён полей и переживает любые переименования;
   - в DTO добавить `productIdentifier`, **оставив** `isbn` как deprecated-алиас: сервер принимает **оба**, валидирует оба, в ошибке отдаёт и имя, и код.
2. **Перевод клиентов**: клиенты (а) переходят с `field` на `code` при отображении ошибок, (б) шлют `productIdentifier`. Каждый — в своём темпе.
3. **Удаление** `isbn` после объявленного окна депрекации.

💡 Смысловой итог: клиенты должны зацепляться за **стабильные семантические коды**, а не за имена полей. Имя — деталь; код — контракт.

## 4. HATEOAS и UI: примирение (Б4.4)

Проблема (лекция 2, раздел 6.4): ссылки появляются/исчезают **по состоянию в рантайме**, а UI проектируется заранее: все кнопки, disabled-состояния, тултипы должны существовать в макетах. «Нет ссылки» — **скрытое состояние**, которое дизайнер не может нарисовать. Плюс клиент всё равно знает список rel — часть связности вернулась.

Три способа примирить «сервер диктует действия» и «дизайнер хочет кнопку всегда»:

**Способ 1. Сервер отдаёт ссылку всегда + метаданные доступности:**

```json
"publish": {
  "href": "/api/manuscripts/5/publish",
  "allowed": false,
  "reason": "MANUSCRIPT_REJECTED"
}
```

Клиент рисует кнопку disabled с тултипом из `reason`. Договорённость фиксируется в контракте. Цена: контракт толстеет, сервер обязан вычислять доступность для всех действий.

**Способ 2. Клиентский реестр rel.** UI знает **список rel** (часть контракта, стабильнее URL): ссылка есть — кнопка активна; ссылки нет — рисуем disabled. Сервер меняет бизнес-правила (когда доступно), не меняя UI. Цена: по rel жёсткость — новый rel требует обновления UI.

**Способ 3. BFF/UI-composition слой.** Промежуточный слой переводит гипермедиа в **view-model с флагами** (`canPublish: false`, текст тултипа). UI-команда живёт по-старому (флаги — простые), гипермедиа не протекает в компоненты. Цена: ещё один слой с его поддержкой (и всеми уязвимостями BFF — лекция 3, Б1.2).

Общий знаменатель всех трёх: **сервер — источник истины о том, МОЖНО ли действие; клиент — о том, КАК его изобразить.**

## 5. Наблюдаемость: Correlation ID (СОП 5)

### 5.1 Проблема

В распределённых системах один запрос проходит через несколько сервисов. Произошла ошибка — **в каком из пяти сервисов** и какие события ей предшествовали? Без сквозного маркера логи — перемешанная каша от сотен параллельных запросов.

**Correlation ID (Request ID / Trace ID)** — уникальный идентификатор, присваиваемый запросу **на границе системы** и передаваемый через все сервисы, участвующие в обработке. Фильтруешь лог по ID — видишь путь запроса через всю систему.

### 5.2 Реализация: Servlet Filter + MDC

Фильтр (сквозная задача, cross-cutting concern — решается не в контроллерах, а одним местом):
1. Проверяет заголовок **`X-Request-ID`** входящего запроса.
2. Есть — берём его значение (запрос идёт изнутри системы, идемпотентно продолжаем трассу).
3. Нет — генерируем **UUID** (запрос извне).
4. Прописываем ID в **ответ** (клиент тоже знает) и в **MDC**.

**MDC (Mapped Diagnostic Context)** — инструмент SLF4J/Logback: по сути **`ThreadLocal Map<String, String>`**. Один раз `MDC.put("correlationId", id)` в начале обработки — и фреймворк логирования **автоматически добавляет ID во все лог-сообщения этого потока** (через паттерн `%X{correlationId}` в конфиге). Не надо протаскивать ID через каждый `log.info`.

❗ **Критически важно очищать MDC в `finally`**: потоки переиспользуются пулом — без очистки correlationId «утечёт» в чужой запрос, обработанный этим же потоком позже, и трассировка будет врать.

💡 Связь с лекциями 5–6: `EventEnvelope` — тот же принцип в мире сообщений: события несут eventId/source — «correlation ID для асинхронного мира».

## 6. Распределённая трассировка и метрики (СОП 12)

### 6.1 Пролог: а что в продакшене

«В продакшене у вас не будет доступа к консоли IDE. У вас будет 50 контейнеров на разных серверах. Как понять, почему запрос тормозит? Где ошибка, если логов гигабайты? Хватает ли памяти?»

Ответы: структурированные логи → **трассировка** → **метрики**. Три столпа наблюдаемости (observability).

### 6.2 Micrometer Tracing ❗

Самописный фильтр Correlation ID — **учебный** приём. Индустриальный стандарт со Spring Boot 3 — **Micrometer Tracing**, который автоматически:
1. Генерирует **TraceId** (общий ID всей цепочки) и **SpanId** (ID конкретной операции; спаны вкладываются — получается дерево вызовов).
2. Прокидывает их через **HTTP-заголовки** (стандарт W3C Trace Context).
3. Прокидывает через **заголовки сообщений RabbitMQ** и **метаданные gRPC**.
4. Отправляет данные в систему визуализации: **Zipkin**, **Jaeger**.

Что даёт по сравнению с самописным correlationId: **иерархия** (не просто «один запрос», а «внутри него — вызов в БД 120 мс, вызов в analytics 900 мс»), автоматизм (никто не забыл фильтр), интеграция со всеми транспортами.

### 6.3 Метрики: Actuator + Prometheus

**Spring Boot Actuator** даёт операционные эндпоинты; `/actuator/prometheus` отдаёт метрики в формате **Prometheus** (система мониторинга собирает их по расписанию): латентности, счётчики ошибок, память JVM, размеры пулов. На метриках строятся дашборды (Grafana) и **алерты** («доля 5xx > 1% → разбуди дежурного»).

### 6.4 Docker-контекст

Сервисы живут контейнерами; значит: логи — **в stdout/stderr** (собирает инфраструктура), состояние — наружу через health-check'и и метрики, а не через «зайти на машину и открыть файл». Отсюда же важность того, что все наши сервисы конфигурируются переменными окружения (`spring.rabbitmq.host` и т.п.).

## 7. Чего нет в smart-fridge — честная дорожная карта (умеешь назвать = плюс)

| Отсутствует | Что добавить |
|---|---|
| Фильтр Correlation ID + MDC | `OncePerRequestFilter`: X-Request-ID → MDC → response header, очистка в finally |
| Трассировка | micrometer-tracing + bridge-brave + zipkin-reporter; автопрокидывание через HTTP и RabbitMQ |
| Метрики | spring-boot-starter-actuator, endpoint /actuator/prometheus |
| Outbox | таблица outbox + релизер + publisher confirms (лекция 6) |
| Идемпотентность audit | дедупликация по `EventEnvelope.metadata.eventId` |
| DLQ / manual ack | dead-letter-exchange + `acknowledge-mode=manual` (лекция 6) |
| DataLoader | `@DgsDataLoader` по productId (лекция 4) |
| Чистое ядро контракта | расслоение api-contract (лекция 10, раздел 2) |
