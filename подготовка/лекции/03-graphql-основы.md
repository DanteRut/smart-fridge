# Лекция 3. GraphQL: язык запросов и схема

> GraphQL придумали для одной проблемы: клиент знает, какие данные ему нужны, а REST заставляет его собирать их из нескольких «глупых» эндпоинтов, таская лишнее. GraphQL — один «умный» эндпоинт, форма ответа = форма запроса. В этой лекции: SDL, query/mutation/subscription, variables и почему они существуют (❗экзамен), безопасность через depth/complexity (❗экзамен).

---

## 1. Проблема: почему REST перестал хватать

### 1.1 Избыточность данных (over-fetching) ❗

Задача: список постов, под каждым — лайки с именами и аватарами.

```http
GET /api/posts            # возвращает ВСЕ поля поста
GET /api/posts/1/likes    # возвращает лайки с ПОЛНЫМИ объектами пользователей
```

Клиент получает 15+ полей пользователя, хотя нужны только `name` и `avatar`. На мобильных это критично: лишний трафик, медленный парсинг, выше энергопотребление.

### 1.2 Недостаток данных (under-fetching) ❗

Сделали два эндпоинта: `GET /api/posts` (без лайков) и `GET /api/posts?include=likes` (с лайками). Но теперь нужны комментарии, автор поста, рекомендации — **количество эндпоинтов растёт экспоненциально**. При этом данные размазаны по хранилищам:

- посты — PostgreSQL
- лайки — Redis
- рекомендации — ML-сервис
- комментарии — MongoDB

Клиент сам делает множество запросов = **«N+1 проблема на уровне HTTP»**. Три последовательных запроса по 800 мс = 2.4 секунды ожидания (это буквально сценарий билета Б1.2).

### 1.3 Решение Facebook

**Вместо множества «глупых» эндпоинтов — один «умный» эндпоинт**, способный работать со сложными запросами и **придавать данным форму, какую запрашивает клиент**. Один запрос описывает полную структуру нужных данных — один ответ с данными из всех источников.

История: Facebook, 2012, внутренний проект; опенсорс с 2015; владелец — GraphQL Foundation (под Linux Foundation); спецификация — spec.graphql.org.

## 2. Архитектура: три части

| Компонент | Роль |
|---|---|
| **Schema** | контракт: какие типы данных доступны, какие операции возможны |
| **Resolvers** | функции, которые «знают», откуда взять данные для каждого поля |
| **Data Sources** | источники: SQL/NoSQL БД, REST API, gRPC, файлы, кэш |

Запомни этот слайд — он же ответ на «как GraphQL агрегирует микросервисы»: резолвер одного поля может ходить в PostgreSQL, резолвер соседнего — в Redis, схема их соединяет для клиента в один ответ.

## 3. Schema Definition Language (SDL)

### 3.1 Скалярные типы

| Тип | Описание | Пример |
|---|---|---|
| `Int` | 32-битное целое | `age: Int` |
| `Float` | число с плавающей точкой | `price: Float` |
| `String` | строка UTF-8 | `name: String` |
| `Boolean` | true / false | `active: Boolean` |
| `ID` | уникальный идентификатор, сериализуется как строка | `id: ID` |

### 3.2 Модификаторы (обязательность и списки)

```
String        — nullable строка
String!       — non-nullable (обязательное)
[String]      — nullable список nullable строк
[String!]     — список, элементы обязательны
[String!]!    — обязательный список обязательных строк
```

💡 Читай слева направо: `!` сразу после типа — про элемент, `!` после скобки — про сам список.

### 3.3 Пользовательские типы и связи

```graphql
type User {
  id: ID!
  name: String!
  email: String!
  age: Int
  posts: [Post!]!       # связь с другим типом
  createdAt: DateTime   # custom scalar
}

type Post {
  id: ID!
  title: String!
  content: String!
  author: User!         # обратная связь
  likes: [User!]!
  comments: [Comment!]!
}
```

Связи — просто поля с типами других объектов. Как резолвятся — забота сервера (лекция 4).

### 3.4 Input types и Enum

**Input type** — структурированные аргументы (для мутаций и фильтров):

```graphql
input CreateUserInput {
  name: String!
  email: String!
  age: Int
}

input UserFilter {
  nameContains: String
  minAge: Int
  maxAge: Int
}
```

**Enum** — фиксированный набор значений:

```graphql
enum Role { ADMIN MODERATOR USER }
enum SortOrder { ASC DESC }
```

### 3.5 Interface и Union — полиморфизм

```graphql
interface Node { id: ID! }

union SearchResult = User | Post | Comment
```

## 4. Язык запросов: три концепции ❗

| Концепция | Аналог | Особенность исполнения |
|---|---|---|
| **query** | read | поля обрабатываются **параллельно** |
| **mutation** | CUD (create/update/delete) | **последовательно**, сверху вниз — ради целостности данных |
| **subscription** | push-подписка | сервер присылает данные каждый раз при событии |

### 4.1 Query: определение в схеме

```graphql
type Query {
  users: [User!]!
  user(id: ID!): User
  posts(filter: PostFilter): [Post!]!
}
```

### 4.2 Query: запрос клиента и ответ

```graphql
query GetUserWithPosts {
  user(id: "42") {
    name
    email
    posts {
      title
      likes { name }
    }
  }
}
```

Ответ — **точно та же структура**:

```json
{
  "data": {
    "user": {
      "name": "Иван Петров",
      "email": "ivan@example.com",
      "posts": [
        { "title": "Введение в GraphQL", "likes": [{"name": "Анна"}, {"name": "Мария"}] }
      ]
    }
  }
}
```

💡 Это главное свойство GraphQL: **форма ответа повторяет форму запроса**. Клиент получил ровно то, что попросил — ни больше, ни меньше.

### 4.2 Аргументы

Пары «ключ-значение», привязанные к полю. Могут быть на **любом поле любого уровня вложенности**, именованные, обязательные или опциональные:

```graphql
query {
  user(id: 1) {
    name
    posts(first: 5, orderBy: { field: CREATED_AT, direction: DESC }) {
      title
    }
  }
}
```

### 4.3 Variables ❗❗

```graphql
query GetUser($userId: ID!, $postsLimit: Int = 10) {
  user(id: $userId) {
    name
    posts(first: $postsLimit) { title }
  }
}
```

Переменные передаются **отдельно**, обычно JSON:

```json
{ "userId": "42", "postsLimit": 5 }
```

**Экзаменационный вопрос: зачем variables, если значения можно захардкодить в строку query?** Технические причины (не «читаемость»!):

1. **Запрос становится константой → его можно кэшировать на сервере.** Разбор (parse) и валидация запроса — дорогие шаги. Если текст запроса постоянен, сервер делает parse+validate **один раз**, кэширует скомпилированное представление и исполняет его с разными variables. Точный аналог **prepared statements в SQL**.
2. **Persisted Queries** (см. 7.3): клиент шлёт не текст, а **хэш** запроса из белого списка. Это возможно только потому, что текст запроса постоянен — иначе хэш не идентифицировал бы запрос.
3. **Типобезопасная сериализация значений:** значения едут по типам схемы (`$userId: ID!`) — не надо конкатенировать строки, нет проблем экранирования кавычек/переводов строк внутри JSON-строки `query`, нет «GraphQL-инъекций» (текст, подставленный в строку запроса, мог бы изменить его структуру; через variables это просто значение).

### 4.4 Mutations

```graphql
type Mutation {
  createUser(input: CreateUserInput!): User!
  updateUser(id: ID!, input: UpdateUserInput!): User!
  deleteUser(id: ID!): Boolean!
}

mutation CreateNewUser($input: CreateUserInput!) {
  createUser(input: $input) { id name email }
}
```

Разница с query — **порядок исполнения**: query-поля можно считать параллельно (они читают), mutation-поля исполняются **строго последовательно**, чтобы обеспечить целостность (мутация 2 не должна начаться до завершения мутации 1).

### 4.5 Subscriptions

Pub/Sub, встроенный в GraphQL: клиент «слушает», сервер присылает данные **каждый раз** при срабатывании условия — аналог push-нотификаций, но в одной системе с query/mutation. Транспорт — **WebSocket и SSE** (лекция 8!). Клиент может аргументами задать, при каком условии приходят данные.

```graphql
type Subscription {
  postCreated: Post!
  userOnline(userId: ID!): UserStatus!
  commentAdded(postId: ID!): Comment!
}

subscription OnNewPost {
  postCreated { id title author { name } }
}
```

## 5. Fragments и директивы

### 5.1 Fragments — DRY для наборов полей

```graphql
fragment UserBasicInfo on User {
  id name email avatar
}

query {
  user(id: 1) {
    ...UserBasicInfo
    posts { title }
  }
  admins {
    ...UserBasicInfo
    role
  }
}
```

### 5.2 Директивы

| Директива | Описание |
|---|---|
| `@include(if: Boolean!)` | включить поле, если true |
| `@skip(if: Boolean!)` | пропустить поле, если true |
| `@deprecated(reason: String)` | пометить поле устаревшим (эволюция схемы!) |
| `@defer` (2024+) | отложенная доставка поля |
| `@stream` (2024+) | потоковая доставка списков |

```graphql
query GetPosts($withComments: Boolean!) {
  posts {
    title
    comments @include(if: $withComments) {
      text
      author { name }
    }
  }
}
```

### 5.3 @defer и @stream — инкрементальная доставка

Проблема: запрос возвращает и быстрые, и медленные данные — клиент ждёт самого медленного поля. `@defer` отдаёт быстрые поля сразу, тяжёлые — вторым пакетом:

```graphql
query GetDashboard {
  user(id: 1) {
    name                 # быстро — из кэша
    analytics @defer {   # медленно — тяжёлый расчёт
      totalViews revenue conversionRate
    }
  }
}
```

`@stream` — то же для списков: элементы приходят по мере готовности.

## 6. GraphQL vs REST ❗

### 6.1 Когда GraphQL

- фронтенд требует **гибких структур данных**;
- **мобильные приложения с ограниченным каналом** (over-fetching = деньги и батарея);
- **агрегация данных из нескольких микросервисов (BFF-паттерн)** — ❗ это ответ билета Б1.2;
- сложные, глубоко связанные модели данных;
- нужна быстрая итерация фронтенда.

### 6.2 Когда REST

- простые CRUD-операции с предсказуемой структурой;
- **публичные API для сторонних разработчиков**;
- **HTTP-кеширование критично (CDN, прокси)** — GraphQL кэшировать по URL нельзя: всё POST'ится в один эндпоинт;
- у команды большой опыт с REST.

💡 Умей назвать главный структурный компромисс: REST — множество эндпоинтов, каждый с фиксированной формой, зато URL-кэшируемость и простота; GraphQL — один эндпоинт с полной гибкостью, но кэширование и лимитирование приходится изобретать заново (см. ниже).

## 7. Безопасность GraphQL ❗❗

GraphQL по умолчанию **более уязвим, чем REST, из-за гибкости запросов**. Нужны явные защитные меры.

### 7.1 Query Depth Limiting

Атака бесконечной рекурсией:

```graphql
query {
  user(id: 1) {
    posts { author { posts { author { posts { ... } } } } }   # глубина ∞ → DoS
  }
}
```

Защита: ограничение максимальной глубины (например, 20 — так в твоём проекте).

### 7.2 Query Cost / Complexity Analysis ❗ (экзаменационно)

**Depth — слабая метрика**: он меряет *вертикаль* запроса, а не стоимость. Как положить сервер при глубине 5:

1. **Огромные списки:** `products(first: 100000) { name }` — глубина 2, нагрузка колоссальная.
2. **Дорогие резолверы:** поле, за которым поход в ML-сервис или тяжёлую агрегацию, — «один уровень», а стоит секунд.
3. **Алиасы:** `a: book(id:"1") b: book(id:"2") … z: book(id:"26")` — 26 подзапросов на одном уровне: глубина не растёт, стоимость растёт.
4. **Introspection:** выгрузка всей схемы через `__schema` — неглубоко, но тяжело.

**Вывод:** глубина меряет форму документа, а нагрузку создают данные и резолверы. Нужен **cost analysis**: каждому полю назначается «вес» (cost), у списков — множитель по запрошенному лимиту; перед выполнением считается суммарная стоимость; запросы с cost > threshold отклоняются.

### 7.3 Persisted Queries (сохранённые запросы)

Клиент отправляет **не текст запроса, а хэш**; сервер исполняет только запросы из «белого списка». Эффекты: минус трафик (хэш меньше запроса), плюс защита — **произвольные запросы полностью блокируются** (работает связка с variables: запрос-константа + переменные-параметры).

## 8. Federation (обзорно)

В крупных организациях один GraphQL-сервер становится узким местом. **Federation** — архитектурный паттерн распределённого GraphQL: несколько подграфов (по доменам), единый шлюз-роутер собирает из них одну схему для клиентов. Уровень «GraphQL-шины» над микросервисами.

## 🔗 В проекте smart-fridge

- `schema.graphqls` — все элементы SDL: Query (`product`, `products`, `item`, `items`), Mutation (полный CRUD двух сущностей), типы `Product`/`FridgeItem` со связью, `Connection`-типы и `PageInfo` (пагинация по-graphql'овски), три input-варианта на сущность (Create/Update/Patch — ровно как REST'овские DTO!), скаляры `Date`/`DateTime`.
- `GraphQLSecurityConfig` — `MaxQueryDepthInstrumentation(20)` + `MaxQueryComplexityInstrumentation(200)`.
- Заметь: в схеме `PatchProductInput` все поля nullable — та же семантика PATCH, что в REST-части, но без ловушки null-vs-absent (в GraphQL отсутствие аргумента и `null` различимы!).
